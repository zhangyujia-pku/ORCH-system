# orch：你出计划，orch 干活

## 命令怎么调（不用先 cd）

命令一律用 `orch ...`。它由 `python scripts/install_cli.py` 装成一个垫片，
在任何目录都能用——**不要**假设当前目录是 orch 仓库，也不要 `cd` 过去。

如果报 `command not found`，说明这台机器还没装：

```bash
python "<orch 仓库>/scripts/install_cli.py"
```

装完再试；仍不行就用等价的 `python -m orch.<模块>`，但那要求当前目录在 orch 仓库里。

## 你的角色

只做三件事：**写计划 → 交出去 → 汇报**。

不要自己改文件，也不要"先自己拆着做一遍再交"。执行和修补交给便宜模型，
但**控制权留在你手上**：项目现状、约定、验收标准必须由你掌握——见下面「你管控制，不管干活」。

## 什么时候用

**先数单元**：这个需求能拆成几个互不可省的交付单元（就是计划里的 task 数）。

| 单元数 N | 实测（D 相对 Codex 单干 A） | 怎么做 |
|---|---|---|
| 1 | 省 57%，但一定更慢（1.02×） | 自己做 |
| **2–8** | **12 次里 11 次更便宜**（均值省 47%–73%，个别运行省 86%） | **交给 orch** |
| ≥ 9（尤其 16） | 反而贵 1.4×～4.8×，N 越大越贵 | 自己做 |

数据来自 sc 阶梯五档（N=1/2/4/8/16）各跑 3 次，D/A 逐次比值：
N=1 时 0.38/0.53/0.92，N=8 时 0.22/0.86/0.94，N=16 时 1.37/2.96/4.82。

**N≤8 是第一道门，也是唯一的硬门。共享上下文不再是"不交"的理由。**

如果每个单元都要先读同一套约定、框架或共享层（比如 31 个文件加一份 `CONVENTIONS.md`），
每个 worker 会重读一遍，代价是**时间优势消失**，不是变得不划算：

| 形态 | 金额 D/A | 时间 D/A |
|---|---|---|
| 4 模块 + 共享一份 CONVENTIONS | **0.30×**（省 70%） | 1.03×（打平） |
| 5 领域 × 4 层，共享 31 个文件约定 | **0.77×**（省 23%） | 1.65×（慢 65%） |

所以判据从"共享就自己做"改成两问：

> **钱要不要省？** 要 → 交。共享也交，只是别指望更快。
> **时间卡不卡？** 卡 → 只有「大单元 + 互相独立 + k≥2」才交，其余自己做。

**用**（N 在 2–8）：
- 跨 3～8 个文件的实现、重构、迁移
- 多份互不相关的产出物（比如 5 篇稿子各自改写）
- 一个需求里有多个可独立交付的部分（接口 / 实现 / 测试 / 文档），且各部分的验收互不依赖
- **多个单元共享同一份约定/框架**——照样交，预期时间打平

**不用**（这时直接自己做）：
- 单元数 > 8——规模越大编排越亏，没有"批量摊薄"这回事
- 单文件改动、改配置、改文案
- 纯问答、代码解释、review 意见
- 探索性任务（"这个项目怎么组织的"）——那需要读，不需要拆
- 时间卡得很死、单元又短（41 行 × 4 那种）：金额仍省，但会慢一倍

## 你管控制，不管干活：读什么、不读什么

D 的意义是**Codex 保留对项目的控制权，把劳动力外包**。不是"Codex 不看项目、只转发需求"——
那是一个残缺的 A，不是 D。所以规划阶段要读，只是要读对地方。

| 该读（控制面） | 不该读（执行面） |
|---|---|
| 需求原文、验收标准 | 要改的那几行的完整实现 |
| 项目结构、约定、schema、接口契约 | 样板代码、重复实现 |
| 被拆单元的签名级现状：有哪些函数、入出参、谁调用谁 | 与本任务无关的模块 |
| 上一轮报告里的失败原因 | worker 各自负责的细节 |

一句话：**你要它判断"拆得对不对、验收够不够"，就读；你要它判断"这行怎么改"，就不读。**

非代码场景同理：你读的是"要求、现状、格式约定"，不是"每一条内容"。
比如 12 份材料要统一改写，你该读的是风格规范与它们的结构，不是把 12 份全文读一遍。

### 别自己来回翻，把资料一次给全

| 做法 | H 侧输入 token（实测） |
|---|---|
| 只给路径清单 | 17,754 |
| 全仓正文一次拼进 prompt | 22,569（+27%） |
| 让它自己 `ls` / `cat` / `grep` | 106,528（6×） |
| 边读边试边改（27 条命令） | 1,415,264（80×） |

机制：**每次工具调用都会把整个上下文重发一遍**。所以贵的不是"读"，是"一轮一轮地翻"。
资料一次给全，比放它去探索便宜一个数量级。

仓太大一次装不下时：让便宜模型先产一份结构摘要（谁在哪、导出什么、约定是什么），
你读摘要 + 点名要的那几个文件的签名。仍然不要让 H 自己去逐个打开。

## 第一步：写计划

**按上面的边界读：控制面要读，执行面不读。** 拿不准边界时，宁可多要一份约定文档，
也不要放自己进仓库里翻——翻的成本是读的十倍。

产出一个 JSON 文件：

```json
{"mode": "single", "spec_md": "## 要做\n…", "tasks": [
  {"id": "t01", "goal": "把 A 改成 B", "writes": ["src/a.py"], "reads": [], "deps": [],
   "acceptance": ["python -m pytest -q tests/test_a.py 退出码 0"]},
  {"id": "t02", "goal": "…", "writes": ["src/b.py"], "reads": [], "deps": ["t01"],
   "acceptance": ["文件断言：src/b.py 含 `handle_login`。"]}
]}
```

`mode` 是对执行形态的承诺：`single`（只有一个任务）/ `parallel`（互不依赖、可同层）/
`chain`（严格串行，后一步要看前一步的结果）/ `auto`（不填，按依赖自动分层）。
写错会被 E021/E022/E023 打回——**不要为了"看起来成体系"而乱标**。

`chain` 时每个非首任务还要写 `inputs_from: ["t01"]`（读哪个任务的产物）。
只写 `deps` 不够：它只保证先后，不保证下一阶段读了什么。

三条最容易踩的规则（完整字段与错误码见 `schema/tasks.schema.json`）：

1. **判据必须可判定**——只有三种合法形态：可执行的命令、命令加期望输出、带锚点的文件断言。
   "体验良好""代码整洁"这类会被 **E014** 直接拒掉。
2. **`writes` 不能重叠**——两个任务写同一文件会被 **E013** 拒掉。真有先后关系就写成 `deps` 链。
3. **判据里要有可定位的东西**：文件名、路径、数字、反引号里的符号。

**判据由你写，不要让用户提供。** 用户只给需求；把需求翻译成可执行判据是你的工作。
不要问"验收标准是什么"、不要让用户贴命令、也不要把"用户确认过"当成通过——
验收的判据必须能自己跑出退出码。用户最多告诉你"这个东西以前是怎么验的"，
那也只是你的参考材料，最终落进 `acceptance` 的必须是你能执行的东西。

派发前自己先确认一次：**目标文件夹在不在**。路径写错时 orch 会立刻停下并指出是哪个路径
（`错误：目标文件夹不存在：<绝对路径>`），不要靠它兜底——你手上有一手信息，先看一眼更省事。

不拆时返回 1 个任务，这是正常且常见的正确输出——**不要为了显得忙而硬拆**。

但注意：**N=1 不该 dispatch**。按上面的表，单任务走编排只会多付一层计划费。
单任务计划只在用户明确要求"走 orch 跑一遍"时才交，否则自己做并 `orch bypass` 记账。

## 第二步：交出去

```bash
orch dispatch "<用户原话>" --repo <仓库绝对路径> --plan <plan.json 绝对路径>
```

**原话照传，不要总结、不要润色。** `intent.md` 是这次运行的证据；改写过的需求会让失败无法归因。

## 第三步：汇报

`orch dispatch` 是**同步**的：命令跑完，DISPATCH 报告就在工具输出里，你这一轮直接读、转述，
用户在同一轮里就看到结果。**不需要等投递，也不要问"结果在哪"**——
只有后台/serve 模式（长时间批次）才会用 `codex queue` 把报告推回会话，那时报告不在输出里，才需要等。

照 DISPATCH 报告原样转述：任务数、通过情况、产物位置、失败原因。

**报告末尾的「成本核算」块必须原样转述**：估计节省的额度（D/A）与金额（正负号都要说）。
如果块里出现「当前为试验模式」，必须原样提醒用户，并说明可以让我关闭对照组
（`orch control-arm off`）——真实运行时每多跑一次 A，就多一份时间和额度。

**每个任务的「验收 X/Y 通过」和失败判据的证据行（`rc=…` + 输出首行）必须一起转述。**
用户靠这两行判断要不要自己复核；压成一句"都通过了"，等于把验收责任直接甩给用户。
不要替用户补全，也不要说"应该没问题"。

**报告里有一行「执行者：<档位> / <模型>」，必须一起转述。**
资源行里的 token 也要转述（输入 / 缓存 / 输出）；写成"未采集"就照说未采集，不要估。
它回答的是"这次到底谁干的、烧的谁的钱"——不写这一行，用户没法判断
是走了便宜模型还是烧了 Codex 额度。

报告里如果有 **「提示（不阻断）」**（比如 `W006 判据都不是命令型`），要一并转述——
它说明这次验收可能验不到行为，用户有权在跑之前改判据。

## 验收没过怎么办（你只有 1 次返工权）

报告里出现 `FAIL` 时，先看证据行：`验收 X/Y 通过`、失败判据的 `rc=` 和输出首行。
按这三种情况判断，不要一律上报：

| 现象 | 判断 | 怎么做 |
|---|---|---|
| `rc=2`、找不到文件、命令语法错 | **判据/环境写错了**，不是活错了 | 改判据，重跑 |
| 判据比 goal 更严、或没覆盖 goal | **判据写错了** | 改判据，重跑 |
| worker 只做了一半、改动对不上 | **活没干完** | 原判据重跑 |

返工用这一条命令（不要重新 dispatch 整份计划）：

```bash
orch retry <run_dir> --tasks t03
orch retry <run_dir> --tasks t03 --plan fix.json   # 要改判据时，传一份只含该任务的计划
```

每次 retry 都会**新起一个 run**，旧的 trace 与 diff 原样保留，可以直接对比。

三条红线：

1. **最多 1 次**。第二次仍失败就停手，把证据和你的判断交给用户，不要自己再试。
2. **改判据必须报备**：改了什么、为什么改，写进汇报。判据就是验收标准，偷偷放宽等于作弊。
3. **不许自己下场改代码**。想自己改，说明这次不该走编排——先问用户。

## 汇报时必须说清"验证到哪"

只报"8/8 通过"是不够的：判据没覆盖的地方，你并没有验证。固定用这三行收尾：

```
我验证了：<跑了哪几条判据、结果如何>
我没验证：<超出判据的部分，例如并发、性能、对外接口兼容>
剩余风险：低/中/高 —— <一句话原因>
```

## 计划没过校验会怎样

分两层，你只需要知道结果：

| 情况 | 谁处理 |
|---|---|
| 初版被拒，错误可机械修补（补锚点、拆任务） | **orch 自己交给便宜模型改**，你不用管 |
| 连修 2 轮还不过 | **退回给你**，报告里有完整 E0xx 清单 |

退回时，把错误码和 `→` 提示贴给用户，让他决定是补需求还是放弃。
**不要自己动手改文件来"绕过"校验**——那等于废掉整个系统的意义。

## 办公产物：别让它自由发挥

排版是确定性的活。让模型现写 python-docx / openpyxl / python-pptx 脚本，
既费 token 又不稳定，而且本机根本没有这几个库。一律三步：

| 产物 | 先写 | 再转 | 再断言 |
|---|---|---|---|
| `.docx` | 同名 `.md` | `docxgen.py` | `docxcheck.py --min-chars N` |
| `.xlsx` | 同名 `.csv` 或含管道表的 `.md` | `xlsxgen.py` | `xlsxcheck.py --min-rows N --cell A1=值` |
| `.pptx` | `.md` 大纲（`#` 封面 / `##` 内容页 / `-` 条目）| `pptxgen.py` | `pptxcheck.py --min-slides N --require-title` |

**判据直接写成这条命令**，不要写"看起来专业"这种话——模型判不了，你也判不了。

支持范围是故意小的，遇到超范围要照实说，不要硬塞：

- docx：标题/段落/列表/加粗；无图片、表格
- xlsx：只写单元格值；无列宽、字体、条件格式、图表
- pptx：一页标题 + 条目；无配色、动画、图片、表格

生成器写完会自己做一次**结构自检**（内容类型、关系目标、r:id 引用），
不合格直接报错——所以"生成成功"本身就意味着包是完整的。
但它不保证 PowerPoint 打开后好看，那部分仍然要人看。

`orch tools` 看有哪些已核验的工具；没标 ✓ 的不会被自动选中。

## 长批次先估一下

```bash
orch eta --tasks 12
```

预计 **超过 8 分钟**时：
- 前台（默认）会一直阻塞，超过 `--timeout`（默认 900 秒）会被掐断——这段时间用户的对话框都在等
- 想异步就 `--mode serve`（需要宿主在跑），跑完用投递推回窗口
- 宿主没跑又硬跑，会被掐断：**先提醒用户启动宿主**，或者把需求拆小

## 结果怎么落到用户工作区

**成功时 orch 已经自动合并好了**：报告里有一行「工作区：已自动合并到当前分支（N 个文件）」。
所以用户不需要再说一句"合并吧"，也不需要开终端。

报告里那行如果写的是下面几种，照原话转述，**不要自己补一句"已合并"**：

| 报告里写的 | 含义 | 你该说什么 |
|---|---|---|
| 工作区有 N 处未提交改动 | 用户手上还有没提交的东西 | 让用户先提交或 stash，再 `orch apply <run_id>` |
| 合并冲突，已回滚 | 产物和用户当前分支冲突 | 已自动回滚、仓库没被弄脏；产物在集成分支，需要人工看 |
| 自动合并已关闭 | 加了 `--no-apply` 或设了 `ORCH_AUTO_APPLY=off` | 需要时 `orch apply <run_id>` |

`orch undo <run_id>` 只做清理：保留证据，删本次运行的分支与工作树，
**不会撤回已合并到当前分支的内容**。确实要撤回已合并内容时，先核对合并提交
（`git log --oneline --merges --grep "orch: apply <run_id>"`），再由人决定是否 revert；
不要承诺 undo 会替用户撤回。
**任何情况下都不要手动拷贝文件**——手抄没有冲突检测、不留记录，事后没人知道谁改的。

运行记录默认落在 `<仓库>/.orch-runs/`，已自动写进 `.git/info/exclude`，
不会把工作区弄脏。不用手动传 `--runs-dir`。

## 自己动手的时候，记一笔

决定不走编排、自己做完时，动完手跑一次：

```bash
orch bypass --kind <类型> --spots <位置数> --note "为什么自己做" --repo <仓库>
```

类型只有六种：`提问解释` / `单点修改` / `探索` / `多点修改` / `批量同构` / `跨文件改动`。

位置数是"改了几处连续位置"，不是行数。**不记账的自干视为违规**——
没有这个数，就答不出"额度到底省没省"，而那正是这套东西存在的理由。

## 卡住不动的时候

先看判定，不要直接杀：

```bash
orch cleanup <run_id> --dry-run      # 看它判成什么
```

判成 `alive`（心跳新鲜）就等；判成 `dead`（锁已释放）就回收；
判成 `stale`（锁还握着但心跳停了）才是真卡住，此时加 `--force`——
它会先核对进程命令行里有没有这个 run id，核对不过会拒绝，别绕过它。

批量收尸：`orch cleanup --stale`。

## 撤销

用户说"这个结果我不要了"：

```bash
orch undo <run_id> --runs-dir <runs目录>
```

删该次运行的分支与工作树，**保留 `runs/<id>/` 下的证据**（trace、diff、验收记录）。
它只清理 orch 自己留下的分支与工作树，**不会撤回已经合并到当前分支的内容**。
如果这次运行已经 apply/自动合并，人工撤回要先核对合并提交
（`git log --oneline --merges --grep "orch: apply <run_id>"`），再决定是否 revert。

## 不要做的事

- 不要用你自己的子 agent 模拟这套流程。你的子 agent 共享你的上下文，
  而 orch 的执行者是隔离进程 + 独立 worktree，失败模式完全不同。
- 不要在 orch 之外手工建 `tasks.json` 喂给 worker。计划的唯一来源是你（planner）。
- 不要改 `trace.jsonl`，它只追加。
- 不要把 `--max-agents` 调得很大来"提速"——写集重叠的任务本来就只能串行，调大只会让计划更难通过校验。

## 常驻宿主（只在长批次时需要）

默认不需要。`dispatch` 会当场跑完再返回（实测单次命令可跑 10 分钟以上）。

只有两种情况才需要宿主：批次预计超过 15 分钟，或者用户明确说"跑完再叫我"。
此时告诉用户：

> 编排器的常驻宿主没在跑。双击 `orchestrator\start-orch-serve.vbs` 启动它，
> 之后的需求就能后台跑完再回传。

宿主必须由对话之外启动——这一轮对话里 fork 的进程活不过命令结束（已实测）。
