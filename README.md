# orch · 多 Agent 编排引擎

> Codex 的前台批处理层：**Codex 只做理解和交代，干活外包给便宜算力。**
>
> 任务拆解写成可校验的契约，执行在独立 worktree 里，验收由命令判、不由模型判。  
> 运行时纯标准库、零第三方依赖。版本 `v1.9.7`（2026-11-13），源码公开、非商业使用。

---

## 一、面向谁

- **用 Codex 桌面端干活、且不打算换客户端的独立开发者。**
- 订阅额度吃紧：一个中等任务动辄读掉几十万 token，额度比钱更早见底。
- 手里的需求**能拆成 2–8 个互不依赖的交付单元**（几个模块、几份文档、几组素材）。
- 愿意接受一个前提：**把"怎么拆、怎么算过"写成可执行的判据**，而不是靠模型自觉。

不适合：把 orch 当成"更强的模型"。它是调度层，不提升任何单个模型的能力。

## 二、解决什么问题

一句话：**在不换客户端的前提下，把"读仓库、改文件、跑命令"这些执行成本，从 Codex 的额度里挪到便宜模型上；同时不失去控制权。**

具体是三个一直在打架的目标：

| 目标      | 朴素做法的问题                   | orch 的做法                                         |
| ------- | ------------------------- | ------------------------------------------------ |
| **省额度** | Codex 每轮都要重读仓库，读得越多越贵     | Codex 只读"控制面"（结构、约定、契约），执行面交给 worker；规划输入与仓库大小无关 |
| **省钱**  | 便宜模型直接干（单模型），质量没保证、改坏了没人拦 | 拆成契约任务，每个任务在独立 worktree 里改，越界就废掉，验收由命令判          |
| **不失控** | 让模型自己判断"做完了没有"，会出现假通过     | 判据必须是命令或文件断言；引擎负责跑、负责拦、负责留证据                     |

代价写在第七节。

## 三、适用的场景

先数单元，再看三条边界：规模、判据、以及要不要接受单模型。

| 判断                     | 结论                          | 依据（实测）                         |
| ---------------------- | --------------------------- | ------------------------------ |
| 单元数 **N = 1**          | 自己做。省一点钱，但一定更慢              | D/A 金额 0.43、时间 1.02×           |
| **N = 2–8**，单元独立       | **交给 orch**。钱、额度、时间三项都占优    | N=4 时 0.18× / 0.55×，额度只用 2.7%  |
| **N ≥ 9**（尤其 16）       | 自己做。worker 底座 ×N 反噬         | N=16 时金额 1.37×、时间 4.42×        |
| 单元之间**共享同一份全局约定** | **仍然编排**。金额照省，时间打平或变慢 | 4 模块共享：金额 0.30× / 时间 1.03×；5 领域跨层：0.77× / 1.65× |
| 单元**很短**（几十行）          | 自己做。A 读得快，D 的固定开销摊不掉        | 4×41 行：金额 0.37× 但时间 1.95×      |
| 判据**写不成命令**            | 先改判据。写不成就会返工                | 规划返工一次，计划费 17.9k → 81.6k token |
| **只用便宜模型就够**（B 的质量可接受） | **不要编排**。D 恒比 B 贵 2.7–11.1× | 见第七节                           |

一句话：**"该不该编排"按"愿不愿意接受单模型"和"时间卡不卡"判，不按"比 Codex 单干省多少钱"判**——
后者在 11 个同构格里 9 个都成立，等于没有区分度；共享上下文只影响第二个问题：
它让时间打平甚至变慢，但从没让金额翻正。

## 四、安装与验证

### 安装（一次性，需要终端）

```bash
git clone https://github.com/zhangyujia-pku/orch-codex-orchestrator.git
cd orch-codex-orchestrator
python scripts/install_cli.py
```

这一条命令做两件事：

1. 在 `~/bin` 放 `orch` 垫片 → 之后任意目录可用，不用 `cd` 到仓库
2. 把 `skill/SKILL.md` 复制到 `~/.codex/skills/orch/` → **Codex 在对话里才知道有 orch**

然后**重启 Codex**（skill 在启动时加载）。检查装没装好：

```bash
python scripts/install_cli.py --check    # 命令和 skill 分别报状态
```

### 验证（先不花钱，再花一次小钱）

```bash
python scripts/preflight.py
```

七项检查，全部不调用模型：Python、git、orch 能否导入、codex 二进制与版本、  
**这个 codex 版本的 `exec` 是否支持 orch 用到的参数**、沙箱能不能起子进程、凭据与 worker 注册表。

机器本身的完整性（约 8 分钟，多数是真 git 操作）：

```bash
python -m pytest tests -q        # 本快照实测 402 passed, 1 skipped
```

最后跑一次最小端到端（会花钱，约 $0.03–0.05）：

看到下面四样东西就算通了：

## 五、理想工作状态

**用户只说话，不碰终端、不看目录、不判断"做完了没有"。**

```
你：把这个仓库里 src 下四个模块的日志都改成结构化输出
      ↓ （同一轮对话，同步等待 2–4 分钟）
Codex：判断能不能拆 → 写计划 JSON（任务、读写文件、验收命令）
      → 调 orch dispatch
      ↓
orch：隔离执行 → 命令验收 → 合并到你的分支
      ↓ （同一条命令的返回值）
Codex：把报告原样转述：几条过、谁干的、额度省多少、钱是正是负
```

四条是这个状态的定义：

1. **入口只有一个**：对话。不需要记路径、不需要背参数。
2. **结果自己回来**：报告就是这次工具调用的返回值，同一轮读完即可，不靠"再去查一次"。
3. **产物自己落地**：成功后自动合并到当前分支；工作区脏或冲突时不合并、也不弄脏仓库，并说明原因。
4. **账目当场结清**：报告里固定有"额度省了多少、金额是正是负"，是实测对照，不是估算。

## 六、基本运行机制

```
你的话
  │
  ├─ intake        原话存档（intent.md），不改写
  ├─ plan          Codex 产出计划 JSON：spec + tasks[] + 验收判据
  ├─ validate      静态校验 E0xx：写集重叠、判据可判定、依赖完整…不过就打回重写（≤3 次）
  ├─ 分层          按 deps 分层，同层并行
  │
  ├─ 每个任务
  │   ├─ worktree   独立工作树，基线钉死在 intake 时的 commit
  │   ├─ worker     便宜模型执行（只给它这个任务的上下文）
  │   ├─ 越界检查   改了 writes 之外的文件 → 整个 attempt 作废，不提交
  │   ├─ commit     先提交（提交不了就不该继续）
  │   ├─ uncommit   退回未暂存：否则 `git diff` 类判据在干净工作区里全是空
  │   ├─ 验收       跑判据命令；验收命令敢改产物 → 直接判失败
  │   └─ commit     通过后按 worker 实际改动清单重新提交（不带验收垃圾）
  │
  ├─ 整合          各任务分支在独立目录里顺序合并，不动你的工作区
  └─ apply         成功后自动合并到你的当前分支（工作区脏/冲突则不合并并说明）
```

三个设计决定，都来自踩过的坑：

- **契约而不是聊天**：任务必须写清 reads / writes / 验收判据 / 禁改范围，否则"做完了"无法判定。
- **命令验收而不是模型验收**：模型判"看起来对"会放过空实现；命令只认退出码和输出。
- **隔离而不是就地改**：每个任务一个 worktree，越界和冲突都在合并前暴露，不污染你的分支。

## 七、实验数据

口径：每个形态 **n=3**，同机同批题；金额按 `config/prices.json` 的公开单价从 token 重算  
（deepseek 有峰谷，gpt 无），**下表为空闲价**；额度 = D 的 Codex 侧计划输入 ÷ A 的全量输入；  
时间 = 墙钟秒数之比。11 个同构格全部 resolved。

### 对照组（A 臂）默认开，可以关

要在报告里写"省了 63%"，就得有个"不编排会花多少"的数。这个数不能拍脑袋——
所以 orch 默认每次派发**额外跑一遍 Codex 单干**（A 臂）：同需求、同仓库、同一基线，
再把两边的 token 和金额摆在一起算 D/A。

- **代价**：多一次模型调用，多 30–90 秒（报告里"对照耗时"那行就是它）。
- **收益**：金额与额度都是**本轮实测**，不是拿题库数字套。
- **关掉**：`orch control-arm off`；`on` 再开；`status` 看当前在哪一档、为什么。
- **临时关**：`ORCH_CONTROL_ARM=off`，优先级高于配置文件，适合 CI 或一次性实验。
- **关掉之后**：A 的数字仍然给，但会注明"来自题库基线，不是本轮实测"，
  节省结论降一级，只作参考。

```bash
orch control-arm status     # 开/关 + 原因（停止哨兵 / 环境变量 / 持久配置）
orch control-arm off        # 下一次派发不再跑 A
orch control-arm on
```

优先级：`~/.orch/CONTROL_ARM_STOP` 哨兵 > `ORCH_CONTROL_ARM` 环境变量 >
`~/.orch/config.json` 的 `control_arm` > 默认开。

默认开着的理由很直接：**不实测就没有 D/A**。第一次用就想看到真实对比，只能默认开；
嫌慢嫌贵可以关，但要知道关掉之后那个百分比的可信度降一档。

### 优势最明显的四组

| 形态               | 单元 | A 金额   | D 金额   | **D/A 金额**       | **额度 D/A**         | **时间 D/A**     |
| ---------------- | -- | ------ | ------ | ---------------- | ------------------ | -------------- |
| 4 个独立模块（372 行/个） | 4  | $0.297 | $0.043 | **0.14×**（省 86%） | **0.012×**（省 81 倍） | **0.49×**（快一倍） |
| 规模阶梯 N=4         | 4  | $0.171 | $0.031 | **0.18×**（省 82%） | 0.027×             | **0.55×**      |
| 规模阶梯 N=2         | 2  | $0.105 | $0.026 | **0.25×**        | 0.065×             | 0.82×          |
| 规模阶梯 N=8         | 8  | $0.184 | $0.051 | **0.28×**        | 0.031×             | 0.99×          |

三条可以直接引用的结论：

- **金额**：11 个同构格里 **9 格更便宜**，中位 **0.37×**（省 63%）；换高峰价是 8 格便宜、中位 0.54×。
- **额度**：中位只用 Codex 的 **6.5%**（省 15 倍），范围 1.2%–25.3%（**省 4–81 倍**）；  
  A 读得越多这个数字越好看——它随形态变化 20 倍，不能当常数。
- **时间**：中位 1.03×（基本打平），最好 **0.49×**，最差 4.42×。**这是唯一会翻负的指标**。

### 代价与边界（同批数据，不挑着放）

前三行是**仍然该编排**、只是有代价的形态；最后一行才是真正的边界。

| 形态             | D/A 金额            | 时间    | 说明                     |
| -------------- | ----------------- | ----- | ---------------------- |
| 规模阶梯 N=16      | 1.37×             | 4.42× | worker 底座 ×16 反噬       |
| 6 份短文档（40 行/份） | 1.18×             | 2.74× | 单元太短，6 个 worker 各付一次底座 |
| 跨层共享同一份约定（5 领域 × 4 层） | 0.77× | 1.65× | 仍省 23%，但变慢；共享影响的是时间，不是金额 |
| **对便宜模型单干（B）** | **D/B 2.7–11.1×** | —     | 若 B 的产物质量可接受，任何形态都别编排  |

### 两个必须一起说的数

- **返工是有价格的**：文档题加一次返工，金额从 $0.078 → $0.113（+45%），时间 177s → 329s（+86%），  
  3 次里只救回 2 次。机制在期望上为正（净收益随任务价值上升，阈值约 $0.05），但它是**风险支出，不是保险**。
- **质量只做到"没观测到下降"**：33 组 A/B/D 全部通过判据，但判据只验格式与字段，  
  **验不出"写得好不好"**。不能据此声称质量等价。
