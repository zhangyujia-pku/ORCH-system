# 冻结规则与仿真模式（轨道 B）

## 一、先把问题说清：尺子确实被改过

正式批还没开始，轨道 B 的题已经改过三次，每次都让此前数据失效：

| # | 改了什么 | 为什么改 | 影响 |
|---|---|---|---|
| 1 | 参考解的「空串」判定（`== ""` → `strip() == ""`） | 判据把全空白也算空串，参考解过不了 | 此前的 b1 自检结果作废 |
| 2 | 验收脚本补 `sys.path.insert(0, ".")` | b2 的 `import scripts.*` 找不到仓库根 | 此前的 b2 自检结果作废 |
| 3 | seed 加 `.gitignore` | worker 跑验收生成 `__pycache__`，被判"越界写入"，8 个任务废掉 4 个 | **你跑的那次 b3/D（4/8）作废** |

前两次是题本身不自洽（自检没过的题本来也不能用），第三次是跑了之后才发现的。
共同点是：**每次都在"跑出数据之后"才发现**——这就是"一直在改尺子"的实感来源。

## 三、验收做实的三关（已通过）

| 撞法 | 期望 | 结果 |
|---|---|---|
| 空补丁（什么都不改） | 0 通过 | ✓ b1 0/10、b2 0/12、b3 0/8 |
| 参考解 | 全通过 | ✓ 10/10、12/12、8/8 |
| **把仓库里的 checks 改成永真** | 仍判不通过 | ✓ 三批都 `resolved=False` |

第三关是关键：它证明**被验收者改不了标准**——评分时用的是题库里的副本，覆盖仓库里的同名文件。
这一条如果不成立，前面所有"通过"都没有意义。

## 四、变更规则（写死，不再例外）

1. **冻结之后，任何改动都算新版本**：`taskset-v2`，并声明"v1 的数据不得与 v2 合并"。
2. **一次跑批内不许改**：题、验收、`workers.json`、codex 版本，任何一项变了就停批。
3. **发现题有错怎么办**：停批 → 改 → 升版本 → 从第一格重跑。**不许"只补跑受影响的那几格"**——
   因为你无法证明"不受影响"。
4. **失败不重跑到通过**：失败就记 `False` / `timeout`，重跑会系统性高估通过率。

## 五、仿真模式：输入与验收在 Codex，脚本只采集

这一次把驱动方式也定下来，避免"跑法"再变一次。

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **你** | 在 Codex 里发那句需求；看它汇报 | 不改题、不改验收 |
| **Codex** | 自己执行；**自己跑 `checks/unit_XX.py`** 并把结论贴出来 | —— |
| **脚本** | 建仓库（prep）、打印原话（goal）、采集与独立复核（collect） | 不喂 prompt、不驱动模型、不参与判定 |

### 每格三步

```powershell
# ① 建这一格（从 seed 铺文件 + 一次初始提交 + 记基线 sha）
python scripts\sim.py prep --task b3 --arm A

# ② 在 Codex 里发原话（内容就在 runs\exp\b3\A\r1\GOAL.txt）
#    方式一：终端（能采到 token，推荐）
cd runs\exp\b3\A\r1
codex exec --json --dangerously-bypass-approvals-and-sandbox "<GOAL.txt 的内容>" > ..\..\..\sess-A-b3.jsonl
#    方式二：客户端窗口（最贴近真实使用，但拿不到 token，只能记墙钟与复核结果）

# ③ 采集（取补丁 + 独立复核 + 追加一行）
python scripts\sim.py collect --task b3 --arm A --session runs\exp\sess-A-b3.jsonl
```

### 采集器记录什么

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `usage` / `turns` | Codex 会话的 token 与轮次 | 主指标（H 额度比）的分子 |
| `worker_usage` | D 臂 worker 的 token（读 `.orch-runs` 的 `run.usage`） | 执行被移出 H 的部分 |
| `units_ok` / `units` | **独立复核**的单元通过数 | 唯一可信的判定 |
| `claimed` | Codex **自报**的结论（自称通过/未通过/未表态） | 与复核对照：不一致本身就是数据 |
| `patch_bytes` | 补丁大小 | 判断"是不是真改了" |
| `taskset` | 冻结版本与哈希 | 证明这一行是在哪把尺子下量的 |

> `claimed` 与 `units_ok` 不一致时，脚本会打一行提示，但**不改判**。
> "它说做完了"和"实际做完了"是两件事，这正是实验要量的东西。

### A 臂与 D 臂的区别只有一句话

同一个原话，**D 臂额外允许 Codex 使用 orch**（skill 已在 `~/.codex/skills/orch`）。
它用不用、怎么拆，由它自己决定——那才是"仿真"，而不是脚本替它决定。

若 D 臂这次没调用 orch，如实记录（这也是一种真实结果：模型判断"不需要拆"）。

## 七、两个已经踩过的环境坑（都不在题里，但会让题看起来是坏的）

| 坑 | 现象 | 真因 | 处置 |
|---|---|---|---|
| `__pycache__` 被判越界 | 编排报 `task.out_of_scope`，完成数 4/8、FAIL | worker 跑验收时 Python 写字节码缓存，被算成"改了范围外的文件" | seed 放 `.gitignore`（`__pycache__/`、`*.pyc`、`.pytest_cache/`） |
| `UnicodeDecodeError: 'gbk' ...` | 审计脚本抛一堆 thread 报错 | 中文 Windows 的 `subprocess` 默认用 gbk 解码，而仓库内容与验收输出是 UTF-8 | 所有外部进程调用显式 `encoding="utf-8", errors="replace"`；补丁按字节读再解码 |
| 管道里中文变乱码 | `python x.py \| Select-Object` 输出成"鍙傝€冭В" | Python 按 UTF-8 输出，终端控制台按 GBK 解读 | 会话开头两行：`$env:PYTHONIOENCODING="utf-8"`；`[Console]::OutputEncoding=[Text.UTF8Encoding]::new()` |

这两条之所以值得写下来：**它们的表现都像"模型/题不行"，实际是环境默认值**。
