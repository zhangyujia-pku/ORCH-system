# 第一步：状态、动作与报告一致性——只读梳理

日期：2026-11-07。状态：本文原为只读设计，现已获用户授权进入第一步实施。以下保留实施前证据与验收设计；实际改动和测试结果见 [第一步实施验收](第一步_实施验收.md)。

配套总路线：[实施路线图](实施路线图.md)。源码位置按文件与函数标识，避免后续行号变化造成误导。所有拟议字段与事件名称均为设计建议，不表示已有实现。

## 1. 本步的目标和取舍

目标：一次运行的实际动作、机器状态、事件证据和面向用户的报告一致。

第一步建议采用保守而具体的行为：

1. 规划不通过就停止，明确“尚未执行”；真正的单 Agent 降级留到第四步。
2. 已声明的路由硬约束不能被默认 worker 绕过；任何任务不可派发，整次计划在执行前停止。
3. 起点不可确认就停止，不悄悄使用当前版本替代。
4. 提交不成功不进入验收和合并；没有改动须单独判断，不能一律当提交失败。
5. 只完成规划标为“计划就绪”；通知失败与任务失败分开。

本步不修依赖成果传递、不实现 worker 重试、不实现真实降级、不添加澄清模块。它们分别属于后续步骤。

## 2. 先理解的概念

| 概念 | 本项目中的含义 | 例子 |
|---|---|---|
| 计划与执行 | 计划描述将做什么；执行才产生改动 | 输出 `tasks.json` 不代表功能已实现 |
| 状态 | 现在处于什么阶段或结果 | 计划就绪、执行中、失败 |
| 事件 | 某时发生了什么，作为证据追加保存 | 提交成功，且得到提交标识 |
| 报告 | 给人看的状态解释 | “规划失败，未启动 worker” |
| 退出码 | 命令返回的机器可读结果 | `0` 表示该命令按约定成功；plan 命令成功不等于执行成功 |
| 硬约束 | 不满足就不能执行的条件 | 要求数据库能力，候选却没有 |
| 兜底与降级 | 兜底是默认选择；降级是有规则地改走另一条实际流程 | 换成默认模型不能自动满足缺失能力 |
| 基线 | 本次运行约定使用的仓库版本 | 同一实验两次必须从同一提交开始 |
| Provider | 调用具体后端的适配层，不等于模型本身 | 路由选中后端，但程序无法启动时仍不能执行 |
| 兼容性 | 新代码仍能正确解释旧字段和旧记录 | 旧 `fallback` 只能说明旧流程规划未通过，不能证明单 Agent 已执行 |
| 故障注入 | 用可控方式制造失败，检查系统如何处理 | 让提交命令返回失败，看是否还报告成功 |

需要自己讲出的例子：订单已生成不等于货物已送达；同理，计划就绪不等于任务完成。程序需要依据实际动作更新状态，报告再表达这些状态。

## 3. 改动 A：规划失败不能写成“已降级执行”

### 当前证据

- `orch/planner.py`：`PlanResult` 使用 `fallback`；`plan_run()` 最后写 `plan.failed.json` 和 `plan.fallback`，没有调用单 Agent 执行器。失败 reason 用的是最大次数，不一定是实际尝试次数。
- `orch/cli.py`：`cmd_plan()` 输出“已降级为单 agent 直接执行”，随后返回 3。
- `orch/dispatch.py`：`run_job()` 在规划失败分支直接 `_finish(..., 3)`；日志及 `_render_plan_failed()` 仍声称已降级执行。
- `scripts/intent_features.py`：把未通过的计划显示为“降级”。
- `README.md`、`RUNBOOK.md`、`AGENTS.md`、`docs/e2e-test-plan.md` 也含有相关操作说明。

### 建议改哪里、为什么

| 位置 | 拟改内容 | 原因 |
|---|---|---|
| `planner.py::plan_run()` | reason 改为实际尝试数和真实停止原因，明确执行尚未开始 | 调用故障可能第一次就停止，不能报告“三次全失败” |
| `cli.py::cmd_plan()` | 输出“规划未通过，未执行”，保留失败退出码语义 | 终端结果必须符合动作 |
| `dispatch.py::run_job()`、`_render_plan_failed()` | 日志、报告与结束状态一致 | 不让后续对话误以为已有实现产物 |
| `scripts/intent_features.py::plan_stats()` | 新旧失败记录展示为规划未通过，不能统计成真实降级执行 | 避免污染研究指标 |
| 当前操作文档 | 修正上述承诺；历史经过用“当时记录/旧称”注明 | 保留研究历史，更新现行行为说明 |

兼容建议：本轮先保留 `fallback`、`plan.fallback` 机器标识，并在新增记录中明确 `fallback_executed=false`、执行是否启动和停止原因；消费者不能再仅凭名称推断发生过降级。真实降级实现时另设明确的开始、结束证据。既有 E/W 错误码不改，历史 trace 不改写。

### 怎样验收

- 连续三次坏计划：实际尝试三次，worker 调用为零，无验收及合并，非零退出码，报告“未执行”。
- 第一次 Provider 故障：报告实际一次尝试和调用错误，不写“三次均未通过”。
- 前坏后好：正常生成计划，不被失败分支影响。
- 旧 `plan.fallback` 记录仍可读取，统计为规划未通过，不声称执行过降级。
- 后台测试 mock 通知，验证报告内容但不实际发消息。

涉及测试：扩展 `tests/test_planner.py`；建议新增 `tests/test_dispatch.py`、`tests/test_cli.py`，为统计消费者补针对性测试。既有 `TestFallback` 需补行为断言，不能只断言字符串存在。

## 4. 改动 B：路由硬约束贯穿到实际调用

### 当前证据

- `workers.py::route_one()` 对能力缺口返回 C09、对未核验后端返回 C10。
- `runner.py::run_plan()` 遇到不可路由任务仍可能用备选或 `ladder[-1]` 继续分派。
- `workers.py::route_one()` 中 `fits` 为空时仍选择 `widest` 并返回 R04；此时可能不只是文件数问题，也可能是代码或语义支持不符合。`Assignment.routable` 仅检查 gap 与 C10，因此仍可能放行。
- `providers.py::build_router()` 只要至少一个适配器构建成功就返回 router，其他失败分派仍可能留在表中，到执行时才报错。
- `WorkerRouter.name_for()` 对缺失任务分派默认使用 default，可能掩盖不完整分派表。
- `cli.py::_record_routes()` 另算一遍路由，和 runner 的真实执行分派存在两套来源。

### 建议改哪里、为什么

1. `workers.py::Assignment` / `route_one()`：明确区分能力缺失、未核验、规格不满足；不可执行结果不通过 `routable`。已有 R04 也用于合法的大写集任务，不要把全部 R04 一刀切判失败；保留旧理由码，增加明确的可执行标记及阻断原因。
2. `runner.py::run_plan()`：执行前检查全部任务；任何阻断则不启动 worker，不创建任务工作目录；记录任务和具体原因，不走默认强派。
3. `providers.py::build_router()`：检查所有已分派任务对应的适配器是否构建齐全，部分可用不能冒充全计划可运行。
4. `WorkerRouter`：执行计划使用严格分派，遗漏任务直接报告配置错误；若其他调用仍需 default，明确区分两种用途，不能让执行悄悄兜底。
5. `cli.py::_record_routes()` / `cmd_run()`：真实执行事件依据最终分派结果；独立试算明确标为预测，不能当实际调用记录。

本步只保证配置及适配器层的门禁一致。注册表宣称具备能力，不等于已验证外部平台真的可用；真实可用性探测与异构冒烟验收放在第四步。

### 怎样验收

| 输入情况 | 期望结果 |
|---|---|
| 任务需要 db，所有后端都不具备 | 整次计划阻断，worker 调用为零，报告任务及缺失能力 |
| 唯一候选 argv 未核验 | 阻断，不自动给默认后端 |
| 候选有能力但都不满足文件数或代码支持规格 | 阻断，并准确说明规格原因 |
| 两项分派中一个适配器构建失败 | 执行前阻断，另一任务也未开工 |
| 分派表缺少计划中的任务 | 明确失败，不走 default |
| 两个任务分别有合格后端 | 路由表、实际调用、trace、报告一致 |

涉及测试：扩展 `tests/test_workers.py`、`tests/test_providers.py`、`tests/test_runner.py`；调整现有“缺任务走默认”的测试，使其覆盖兼容用途和严格执行用途。用模拟 Provider 验证，不调用真实模型。

## 5. 改动 C：基线不可用时停止，不静默更换实验起点

### 当前证据

- `intake.py::git_head()` 记录短 HEAD；失败时返回空字符串，未保留具体原因。
- `runner.py::run_plan()` 的 `recorded or manager.base_sha()` 会给缺记录的运行使用当前 HEAD；记录的提交不可用时也退回当前 HEAD，仅发 `run.base_missing` 事件。
- 已有 `TestBasePinning` 检查有效基线重复使用，没有覆盖基线缺失、无效和静默替换。

### 建议改哪里、为什么

- `intake.py::git_head()` / `intake()`：新记录尽量保存完整提交标识；取得失败保留原因，仍可存档自然语言需求。非 Git 场景可以记录需求，但当前依赖 Git 的执行流程不能继续。
- `runner.py::run_plan()`：预检查缺失、非法或不可访问的基线；执行前停止，报告需重新建立基线。不要自动替换成当前 HEAD。
- 旧记录若是有效短标识，可解析成完整提交并记录；空值或不可解析值须明确处理，不覆盖旧 intent。
- 检查应先于有副作用的工作目录管理器初始化，避免预检查失败已创建任务目录。

### 怎样验收

有效基线、有效旧短标识正常运行；基线空值、记录提交不存在、非 Git 目录都在 worker 调用前停止，报告原因。原需求和基线记录不被悄悄改写。保留现有“同一次运行重复使用同一起点”的测试。

涉及测试：`tests/test_intake.py`、`tests/test_runner.py`，使用临时仓库和模拟失败，不操作 demo 仓库。

需要讲清：Git 的 HEAD 是当前位置；记录基线是约定起点。当前 HEAD 前进后，改用它就相当于给实验组换了题目背景。

## 6. 改动 D：提交成功必须有证据

### 当前证据

- `worktree.py::commit()` 对 `git commit` 使用 `check=False`，随后读 HEAD。
- `runner.py::_run_one()` 不检查返回结果就发 `task.committed` 并进入验收。
- 若提交失败但旧 HEAD 仍存在，读取 HEAD 不能证明这次提交成功。

### 建议改哪里、为什么

- `worktree.py::commit()`：区分成功创建提交、确实无新改动、提交失败；保存命令结果与提交前后标识。不要简单把所有非零返回值一律归为一种错误。
- `runner.py::_run_one()`：只在确认新提交成功后发 `task.committed`；失败记录具体原因、终止该任务，不调用验收、不接纳该分支。
- 没有新改动时记录“无新提交”，是否满足任务仍需验收；不能伪造提交成功。worker 自行提交导致工作区干净的完整核验放到第二步，本步至少不把它误报成框架新建提交。
- 单任务 Git 故障需要转成可记录的任务失败，避免只抛出异常使整次运行没有清晰结尾。保留其他独立任务的实际结果；依赖该任务的后续阻断。

错误呈现使用已有项目错误机制，实施时统一审查；不在本步擅自改写稳定 E/W 代码，也不要求对所有底层异常做全仓重构。

### 怎样验收

- 真实临时仓库正常提交：能确认新提交并记录其标识。
- 注入提交失败：旧 HEAD 可读取，但不能发 `task.committed`，不能调用验收或合并该任务。
- 无改动：记录无新提交，按验收结果决定任务结果。
- 一任务提交失败，另一个独立任务已有结果：保留两者事实，整体不报成功。

涉及测试：建议新增 `tests/test_worktree.py`；扩展 `tests/test_runner.py`。不要依赖本机 Git 身份恰好未配置来制造故障，应受控模拟提交返回结果。

## 7. 改动 E：阶段完成、执行结果和通知结果分开

### 当前证据

- `dispatch.py::_finish()` 以 `code == 0` 统一设置 `state=done`，规划-only 成功与实际执行成功使用相同状态。
- `_render_done()` 标题固定为“完成”，即使 `summary.ok` 为假。
- `cli.py::cmd_status()` 展示事件计数和最后事件，没有明确区分计划就绪与执行完成。
- 当前 `_finish()` 已分别记录 `delivered` 和 `delivery_detail`，这部分应保留，不能倒退为通知失败等于任务失败。
- planner 和 runner 分别计算 session，状态展示不能假定数字相同就代表同一次完整执行。

### 建议改哪里、为什么

最小状态约定：

| 情况 | 人可读结果 | 必须包含的事实 |
|---|---|---|
| 仅规划成功 | 计划就绪，尚未执行 | 计划结果、执行未启动 |
| 规划失败 | 规划失败，尚未执行 | 实际尝试次数和原因 |
| 执行前门禁失败 | 执行被阻断 | 基线或路由原因，worker 未启动 |
| worker、验收或合并失败 | 执行失败或部分完成 | 失败阶段与各任务真实结果 |
| 当前执行流程成功 | 执行成功 | 当前验收范围；第三步前不宣称通过合并后整体验证 |
| 任务成功但回传失败 | 执行成功，通知未送达 | 执行与通知两个独立结果 |

建议 `dispatch.py::_finish()` 接收明确阶段和结果，而不是仅由退出码猜测；渲染函数依据事实选择标题；`cmd_status()` 使用同一口径解释状态。plan 命令成功仍可返回 0，但报告必须说明成功的是规划。

给新事件和结束记录提供明确的本次调用关联依据；不把 planner/runner 各自 session 强行视为全局执行编号。若引入新的关联字段，保留旧字段并明确缺字段的旧记录只作兼容展示，不推断完整恢复能力。第一步不建设完整事件重放或恢复系统。

### 怎样验收

规划-only、规划失败、路由阻断、提交失败、任务成功、任务成功但通知失败，各自的返回值、状态文件、事件和报告无矛盾。重复规划再执行的情况下，查询不把上一次成功当成此次结果。所有通知用 mock，不能实际写入别的聊天。

涉及测试：建议新增的 `tests/test_dispatch.py`、`tests/test_cli.py`；必要时为共享状态解释逻辑增加测试。当前没有这两个测试文件。

## 8. 建议实施顺序和拟修改文件

1. 先约定状态、停止原因及兼容策略，写出关键行为验收用例。

4. C：基线完整预检查，取消静默替换。

6. E：统一各出口和查询含义，覆盖完整入口到报告链路。
7. 更新现行说明，运行相关测试和全套测试，形成实施前后对照记录。

## 9. 第一步完成标准

- [ ] 所有未执行的降级都没有被报告成已执行。
- [ ] 任何不可路由或适配器未构建齐全的计划均在 worker 启动前阻断。
- [ ] 无法确认基线时没有静默换起点。
- [ ] 提交失败不能产生提交成功事件、验收或接纳分支。
- [ ] 无新提交与提交失败有区别。
- [ ] 规划就绪、执行失败、执行成功和通知失败可清楚区分。
- [ ] 新旧记录可读，旧错误码和历史 trace 未改写。
- [ ] 正常规划、正常分派、正常提交与现有核心测试仍通过。
- [ ] 完整测试使用仓库约定：`python -m unittest discover -s tests -t . -v`。
- [ ] 以上是未来实施验收清单，本轮没有运行，不能提前勾选通过。

## 10. 学习与讲解清单

建议依次阅读 `intake → planner → runner → worker/worktree → verifier → dispatch/cli`，用一个失败场景练习追踪，不要求一开始掌握全部 Python。

最低限度读懂函数参数和返回值、条件分支、字典/列表、异常、类与 dataclass；看到调用链时知道谁负责决策、谁负责执行、谁负责报告。

能独立回答以下问题，才算讲清这一步：

1. 规划失败为什么不能自动叫“降级成功”？真实降级还需要哪些动作？
2. 为什么更强的模型也不能替代缺失的数据库能力？配置声明和真实可用又有什么区别？
3. 为什么旧 HEAD 还能读出来，也可能根本没提交成功？
4. 为什么单次 plan 退出码为 0，用户要求的功能仍可能完全没执行？
5. 为什么通知失败不应让已完成任务变成失败？
6. 如果缺失基线自动改用当前代码，实验结果为什么难以比较？
7. 测试怎样证明“没有启动 worker”，而不是只检查报告里写了这句话？

## 11. 用户审阅重点

本方案建议确认的三项范围取舍：第一步规划失败如实停止；执行前任一硬约束失败就阻断整次计划；保留旧 `fallback` 标识但消除“已执行”的错误含义。真正降级、部分计划继续执行策略及完整恢复机制留到第四步。

用户现已授权按此方案修改第一步代码并测试；本轮使用模拟后端、不发送实际通知。第二步及以后仍不在本次实施范围。
