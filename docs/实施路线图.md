# 多 Agent 协同框架实施路线图

日期：2026-11-07（路线建立日），2026-11-08 更新。状态：第一至第三步已实施并通过验收；第四步实现已落地，真实模型联合验收尚待本机后端环境修复。工程优先、版本冻结后开展语言学研究。

本路线最初依据静态阅读制定；第二节保留实施前能力快照。当前能力以各步实施说明及本页进度为准，第一至第四步均已获用户授权实施。语言学研究继续等待工程验收与版本冻结。

## 1. 最终目标与范围

最终产品是一套完整的多 Agent 协同框架，支持自然语言需求、任务拆解、依赖协作、并行执行、验收、有限返工、合并、整体验证和过程追踪。计算语言学研究嵌入框架的真实协作环节。

推进安排：先完成工程前四步并验收，再冻结一个可复现的研究基线版本。语言学选题、机制设计和正式实验从版本冻结后开始；开发期间只保留案例、故障依据和设计记录，不启动新的语言学实验，也不把工程调试结果直接作为研究结论。

研究候选暂存：自然语言需求中的约束，在任务拆解与 Agent 交接中怎样被遗漏、误解或改变；约束追踪与必要澄清能否改善结果，代价是多少。该题目尚未确定，冻结后结合积累的案例再选择，不要求当前开发围绕它增加研究功能。

框架的完整性与研究结论分别验收：功能走通不等于具有研究创新；某次实验有效也不等于整个框架可靠。

暂缓新增大量后端、工具生态和复杂界面。保留已有接入，不以功能数量衡量进度。

## 3. 实施顺序与里程碑

### 第一步：统一状态、动作和报告

目标：实际行为、状态、事件和报告一致；不把未执行的动作写成已完成。

内容：规划失败如实停止；路由硬约束阻断；缺失基线不静默替换；提交失败不误报；区分规划就绪、执行失败和通知失败；更新当前操作文档与结果统计口径。

验收：用模拟模型、模拟通知和临时 Git 仓库，注入规划失败、路由缺口、基线缺失和提交失败，确认没有错误执行、错误验收或错误成功报告。

掌握：计划与执行的区别、状态与事件、退出码、硬约束、版本基线、兼容性。

详细审阅材料见 [第一步梳理](第一步_状态与行为一致性梳理.md)。本步通过后再进入第二步。

### 第二步：依赖成果传递

目标：后续任务真正使用前置任务成果。

建议第一版沿用分层调度：一层任务验收后形成整合版本，下一层从该版本创建工作目录；记录每个任务实际起点。明确该策略会让下一层看到此前整层已接纳成果，并在实验中固定这一策略。

同时检查已提交修改是否进入修改范围核验；明确无改动、已有提交和新建提交的处理规则。

验收：A 建接口、B 调用、C 测试；B 启动时能读取 A 的成果；A 失败阻断后续；独立任务仍并发。记录起点与实际文件证据。

掌握：提交、分支、工作目录、依赖图、层间屏障。能解释“等它完成”为什么不等于“拿到它的成果”。

本步梳理、实现及概念说明见 [第二步依赖成果传递](第二步_依赖成果传递.md)。

### 第三步：可信验收与整合

目标：成功有证据，局部成功不能冒充整体成功。

内容：正确使用预期退出码；用完整输出做匹配，摘要仅用于展示；独立整合目录与合并后测试；区分 worker 可修改测试和固定最终检查；区分运行命令失败与被测行为失败。

验收：预期退出 1 的正反例；输出前部有多余内容的反例；各任务通过但组合错误的反例；范围外修改；“声称完成但行为未满足”。所有反例必须被正确分类。

掌握：单元与集成测试、测试预期、误判通过、误判失败、独立评价。

实际改动、配置格式与验收说明见 [第三步可信验收与整合](第三步_可信验收与整合.md)。

里程碑 A：可靠执行核心。此时还不能宣称完整恢复或成熟框架。

### 第四步：恢复、资源限制和异构闭环

目标：失败有去向，恢复有上限，运行可控制。

顺序：worker 有限返工 → 合格备选接替 → 真实单 Agent 降级或有限重新规划 → 信息不足暂停澄清 → 取消、总时限及中断恢复。

本轮选择有限重新规划，未新增单 Agent 降级。现已实现有限返工与合格替补、共享资源上限、用户问答暂停、取消及按层恢复；不确定整合或残留进程会拒绝自动继续。具体修改、验收矩阵、配置和概念见 [第四步说明](第四步_恢复资源与异构闭环.md)。

预算区分模型申报预算、估算费用、实际费用和可执行资源上限。无法取得真实计费时，不宣称实现精确美元熔断；先限制调用次数、尝试次数和总时长。

统一命令行与后台入口配置；已有路由接入完成可靠化后，用至少两个真实后端核对实际分派。

当前可控的两个独立 CLI 进程已通过接替与最终验收测试；这不代替两个真实模型后端验收。本机 Codex 文本调用报路径错误，CodeBuddy 文本调用报模块缺失，均未完成模型任务。保留失败记录，修复环境后再完成独立并行、依赖协作、失败恢复三个真实演示，第四步整体通过后再冻结版本。

验收：第一次失败第二次成功、上限停止、无合格备选停止、取消后不发新任务、宿主重启后可解释恢复或失败、不重复接纳成果；每次尝试证据独立。

掌握：状态转换、幂等性、重试与返工区别、超时与取消、能力约束、资源计量。

里程碑 B：完整框架第一版。至少展示独立并行、有依赖协作、失败恢复三个场景。

### 工程与研究之间的关口：冻结研究基线版本

前四步验收通过后，检查以下条件，再进入语言学研究：

- 依赖任务能取得前置成果，任务验收与合并后整体验证可靠。
- 失败能明确停止或有限恢复；独立并行、依赖协作、失败恢复三个场景可以重复运行。
- 原始需求、实际使用的仓库版本、模型配置、提示词与规则、运行结果可追溯。
- 为通过验收的框架版本保留固定提交或发布标签，并保存运行说明、测试结果和已知限制。

冻结指确定一个可追溯的实验起点，不要求停止全部工程开发。后续工程可以继续推进；研究使用固定基线，研究机制在单独、明确的版本上实现。有无机制的对照须共享相同基础工程与配置，仅改变待研究因素。

正式实验前还要冻结研究材料、评价规则及各实验条件对应的代码版本。研究期间若修改影响实验的逻辑，另立版本、另批运行；不把不同版本的结果无说明地混在一起。CLI 版本与模型版本分别记录，未知项明确标未知。

### 第五步：冻结后选题与语言机制探索

启动条件：工程前四步和研究基线冻结检查已完成。先审阅开发期间保存的案例，再决定具体研究问题；以下约束追踪方案作为候选，不作为当前工程阶段的必做功能。

目标：原需求中的对象、条件、否定、禁止事项和交接要求可追溯。

内容：原文片段 → 约束条目 → 负责任务 → 交接内容 → 验收证据；区分用户明说、模型推断和系统默认；允许多个合理计划；仅在影响执行的歧义上请求具体澄清。

原话单独保留；澄清及回答追加记录；不要用模型改写覆盖原需求。

验收：人工案例覆盖条件、否定、指称、跨任务要求；系统指出遗漏或误解时能引用原文；检查误报和凭空新增约束；存在多解时允许标为需澄清。

掌握：指称、歧义、条件和否定的作用范围、语用推断、构念与操作化。

### 第六步：预实验与对照验证

启动条件：研究基线已冻结，第五步已明确问题、待检验机制和评价办法。开发阶段的调试检查仍可正常开展，但与本步语言学预实验和对照数据分开。

研究问题：约束追踪能否减少拆解和交接中的需求遗漏、误解？增加多少运行和交互成本？

基础对照：相同模型、任务、资源与机械校验，比较有无约束追踪。若同时加入澄清，需明确研究的是组合机制；要分别归因，再增加条件拆分检验。

先用十来个基础任务、每条件重复数次检查流程。正式样本量根据波动、资源和指导意见制定。冻结材料与规则后评估；留出未用于调规则的任务，避免在同一批案例上反复调到通过。

指标：遗漏、对象误解、无依据新增约束、最终完成率、调用/耗时/澄清成本。重写次数作为次要指标。评价者尽量不知实验条件，对一部分结果独立标注。

如主张多 Agent 本身优于单 Agent，再加入明确资源条件的单 Agent 对照。先在受控仓库做预实验，再在不同任务或第二个仓库检查适用范围。

验收：材料、配置、全部运行和标注可追溯；能解释分歧、异常与不支持假设的结果；结论强度与证据相符。

掌握：变量、混淆、配对、重复测量、标注一致性、不确定性；未发现效应不等于证明没有效应。

### 第七步：形成进组展示作品

交付：可安装框架、三个可复现演示、简短研究报告、架构图、贡献与 AI 使用说明。

验收：未参与项目者按说明复现一个案例；本人在十分钟内解释拆解、成果传递、验收、恢复及实验结论，并能回答一个失败案例。

掌握：讲清工程与研究各自贡献、适用范围、未解决问题，以及哪些判断由本人承担。

## 4. 工程开发期间先保留的记录

记录随实际开发产生，允许先写“待判断”，不要求现在作语言学归因。

| 记录类型 | 最少保留什么 | 用途与边界 |
|---|---|---|
| 原始案例 | 原始需求、必要上下文、计划、任务交接、输出及验收证据的路径 | 保留成功、失败和存在歧义的案例，冻结后再筛选研究对象 |
| 运行条件 | 日期、运行标识、框架版本、目标仓库基线、模型及配置、提示词或规则版本 | 解释案例发生条件；无法取得的信息标未知 |
| 故障初步分类 | 工程故障、疑似模型理解问题、验收问题、混合原因或待判断，以及判断依据 | 只是排查标签；不把模型自述或表面失败直接当作最终归因 |
| 设计记录 | 遇到什么问题、有哪些证据、考虑过哪些方案、为何选择当前方案、如何验证及遗留限制 | 保存增加字段、调整校验、改变交接策略等决定的理由 |
| 改动关联 | 对应案例、改动前后版本和验证结果 | 防止修复后丢失原始失败现场；同版本成功案例也可作为参照 |

原始记录与后续解释分开，修复或重新分类时追加说明，不覆盖旧证据。当前阶段不为跑出结论额外组织语言学批量实验；已有探索性实验保留历史身份，不自动并入未来正式数据。

## 5. 推进规则

- 每步以验收通过为结束条件，不以新增文件数量或一次模型成功为结束条件。
- 小改动先用可控模拟验证，再做少量真实后端检查；演示不能替代系统测试。
- 保留历史实验，不改写旧记录；新规则与旧结果明确分开。
- CLI 版本、模型标识、提示词版本、代码版本分别记录，未知项明确标未知。
- 前四步以工程验收为主，同步保存案例与设计记录；语言学研究从工程基线冻结后开始。
- 冻结后开发与研究可分别推进，研究结果必须标明对应的固定版本；影响实验的改动另立批次。
- 第一至第四步已获用户授权；本轮推进第四步，不启动第五步语言学研究。自动验证使用模拟后端、可控 CLI 及临时 Git 仓库，实际模型探测保留单独记录，不发送实际通知。
