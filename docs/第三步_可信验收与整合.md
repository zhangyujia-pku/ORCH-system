# 第三步：可信验收与独立整合

状态：已实现并通过回归及专项验收。仅第三步，不实施自动重试、返工、替换后端或预算熔断。

对应总路线：[实施路线图](实施路线图.md)。本轮原话存档：`runs/20261107-220838-de81/intent.md`。框架自身尚无 Git 基线，按用户直接实施的授权修改，不用自编执行计划冒充 Planner 产物；测试均使用模拟后端及真实临时 Git 仓库。

## 1. 先梳理：问题与修改位置

| 原问题 | 修改位置 | 原因 |
|---|---|---|
| 解析了预期退出码，实际仍只认 0 | `orch/verifier.py::split_command()`、`run_command()`、`verify_task()` | 正确拒绝非法输入时返回非零，也可能是正确行为 |
| 输出只检查最后 600 字符 | `run_output_command()`、`Check` | 摘要可以截断，判定证据不能据此截断 |
| 命令中的逗号、分号被当说明分隔符 | `command_of()` | 引号里的代码必须原样执行，只剥离末尾的判据说明 |
| 命令未启动、超时与断言失败混在一起 | `Check.status` 与命令执行路径 | 三种情况的归因与处理方向不同 |
| 合并会切换用户目录的分支 | `orch/worktree.py::merge_all()` | 独立整合不应覆盖用户未保存的工作 |
| 每个任务分别通过便报告整体成功 | `orch/runner.py::run_plan()` | 组合行为可能不兼容，需要额外的固定整体检查 |
| worker 能修改自己的测试 | 新增 `orch/verification.py` | 测试通过有可能只是检查被放宽，必须有独立的标准 |
| 验收命令能改产品后返回成功 | `assert_snapshot()`，任务验收与整体验收后调用 | 需要证明通过的是保存的那个版本，而非被检查过程改出来的另一个版本 |
| 各入口与旧脚本不携带新配置 | `cli.py`、`dispatch.py`、两份实验脚本的 prepare() | 命令行、后台、子进程和批次复制需保持配置一致 |
| 比较与成本脚本只按首任务的 done 计成功 | 两份脚本的结果统计 | 首任务通过不能掩盖固定整体验收失败，改为采用 `RunSummary.ok` |

没有更改 Task 的字段、任务 schema、E/W 错误码或静态校验逻辑。

## 2. 新的执行与成功条件

```text
用户维护 verification.json
  ↓ 执行前读取、校验并保存配置摘要与版本依据
worker 在各自目录完成任务
  ↓ 范围检查 → 保存版本 → 任务验收 → 检查验收未改动版本
独立整合目录按层接纳任务成果
  ↓ 所有任务及整合成功
执行固定整体验收
  ↓ 检查固定文件与版本完整性
全部通过才报告整体成功
```

成功现在要求：所有任务通过、所有整合通过、用户配置的固定整体验收通过。缺少整体检查配置时，在启动 worker 前阻断，不自动生成一条“永远通过”的命令。

局部任务失败时，仍保留独立成功成果及证据，但整次运行失败；整体检查不在不完整产物上执行并冒充最终结论。整体检查失败只报告，不自动修复。

## 3. 怎样配置固定检查

默认读取该运行目录的 `verification.json`，也可显式提供：

```powershell
python -m orch run <run_id> --verification <用户维护的JSON路径>
python -m orch dispatch "原始需求" --repo <目标仓库> --verification <用户维护的JSON路径>
```

配置示例见 `examples/verification.example.json`：

```json
{
  "checks": [
    {"command": "python checks/check_all.py", "expected_exit": 0}
  ],
  "protected": ["checks/**"]
}
```

- 命令在整合目录中运行，路径相对目标仓库。示例要求目标仓库基线中已有 `checks/check_all.py`，不能原样用于没有这个文件的仓库。
- `checks` 至少一条，`command` 非空，`expected_exit` 为整数且默认 0。配置未知字段会报错。
- `protected` 可选。用于声明固定检查文件或目录，至少命中基线中的一个已跟踪文件。也可用内联 `python -c` 断言，不依赖检查文件。
- 固定检查由用户维护，不让 Planner 或 worker 为自己决定最终标准。命令是否真正覆盖需求，需要维护者负责，框架不能从退出码证明测试充分。
- 固定文件以运行的原始基线为准记录 Git 对象标识；worker 不能声明或实际修改这些文件。目录保护也覆盖新文件，避免新增配置或测试钩子改变检查行为。
- 配置在 worker 启动前读取到内存，并保存路径、SHA-256 摘要、命令及保护范围。运行中改写原配置文件，不会改变已经加载的检查。
- CLI、前台后台入口、队列子进程都传递 `--verification`。后端比较与成本脚本复制运行输入时同步复制 `verification.json`，不重新发起测量。
- 老运行缺少此配置时必须补齐，不能以旧的任务验收记录代替整体验收。

## 4. 独立整合如何工作

整合目录为 `runs/<run_id>/integration/<operation_id>/`，整合分支也带本次调用标识。

同层任务仍从共同版本开始；上一层整合完取得独立目录的版本标识，再传给下一层。新增 `merged_worktree` 用来告诉用户产物在哪里。原始目标目录的 HEAD、分支、未提交内容和未跟踪文件保持原状。

每次运行使用不同整合目录与分支，保留此前结果，避免重复运行时旧生成物混进新检查。任务工作目录仍按已有保留选项管理，整合产物保留便于审阅；本步不做恢复或清理策略重构。

整合成功只说明 Git 接纳了修改。Git 不知道接口是否匹配、功能是否正确，这些交给随后运行的整体检查。

## 5. 验收证据怎样记录

每个 `Check` 保存：原判据、类型、通过与否、状态、完整 stdout、完整 stderr、实际退出码、预期退出码和简短证据。输出匹配使用完整 stdout；stderr 单独保存，不拿错误信息冒充正常输出。

| status | 含义 |
|---|---|
| `passed` | 按当前判据通过 |
| `failed` | 命令运行了，但退出码或输出不满足预期，或模型明确判失败 |
| `launch_error` | 初始工具不存在、命令格式错误或进程无法启动 |
| `timeout` | 检查未按时完成，已请求终止本次检查进程树 |
| `unsupported` | 缺少配置的判断能力，无法判定，不算通过 |
| `judge_error` | 模型验收器调用、解析或结果结构失败 |
| `mutation` | 验收过程中修改了已保存版本、暂存区或跟踪文件 |

这里只能可靠区分初始工具启动失败；被调用程序内部依赖失败，仍可能表现为普通非零退出，需要结合完整 stderr 判断。保留这种解释边界，不把所有非零退出都归因于功能错误。

命令中的工具路径在启动前解析为绝对位置，避免整合目录新增 `python.bat` 等文件替代检查工具。超时处理只用于停止本次检查，不引入自动重试。

任务证据继续保存在 `artifacts/<task>-a1.verify.json`；配置快照为 `verification-<operation_id>.config.json`；最终证据为 `final-<operation_id>.verify.json`。事件增加最终验收开始及结果，查询、报告和后台结束记录都包含整体验收状态。

## 6. 涉及概念

### 预期失败也是一种成功

非法输入应被拒绝时，程序返回 1 可以满足验收；本来应该成功却返回 1，则不满足。判定需要比较实际与预期，不能只看是否为 0。

### 任务测试与整体测试

A 的服务端口是 8000，B 的客户端口是 8001，两者各自的局部断言都可能通过，但组合无法通信。整体检查要核对这种模块间关系。

### 检查标准与被检查者分开

worker 编写的测试有价值，但不能作为唯一最终依据。如果它把断言改成 `assert True`，测试仍会通过。用户维护的固定检查用于提供独立判断依据；保护测试文件本身仍不代表测试覆盖充分。

### 版本完整性

验收是对一个确定版本做判断。若检查命令把文件改好后返回 0，但保存的分支仍是旧代码，报告通过就不可信。因此任务验收、最终验收都检查 HEAD、暂存区和已跟踪文件未被改动。普通未跟踪缓存与测试产物不自动保存到发布分支。

### 工作副本与交付产物

用户原目录可以继续保留未保存的工作，框架在另一个目录整合和验收。报告给出的分支、目录才是本次候选产物；不会自动把它覆盖回用户原目录。

### 证据与摘要

摘要帮助人阅读，完整输出支持判定和复查。尤其是“输出只能含某些内容”，不能丢掉前半段后再判断没有多余信息。

## 8. 本步边界

固定命令来自维护者的配置，保护和版本检查是工程完整性措施，不是操作系统安全边界。它们无法证明不存在恶意代码、测试之外没有缺陷，也不能自动验证模型给出的任意证据是真实的。

整体判断不依赖模型打分，但局部文件断言仍可使用模型验收器，保留其不确定性。真正结果依赖用户制定的最终标准。
