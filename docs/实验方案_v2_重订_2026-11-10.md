## 3　三个轨道

### 轨道 A · 体验保持型降本（主轨道）

**臂**：A（Codex 端到端）／C（Codex 规划 + Codex 执行）／D（Codex 规划 + DS 执行）

**题库**：24 题，三档各 8 题

| 档 | 形态 | 来源 | 规模约束 |
|---|---|---|---|
| S | 单文件、1–2 函数 | 自建（参数化生成） | ≤1 文件 / ≤40 行 |
| M | 3–5 文件、可并行 | 真实提交回退（more-itertools / boltons） | ≤150 行 |
| L | 6–10 文件、有依赖链 | 真实功能提交回退 | ≤400 行 |

**每格 1 次**：24 × 3 = **72 格**。
**方差子集**：8 题（S3/M3/L2）× 3 臂 × 追加 2 次 = **48 格**。
合计 **120 格**。

**指标**（按优先级）

| 指标 | 定义 | 用途 |
|---|---|---|
| H 额度比 | D 的 Codex 侧输入 token ÷ A 的 | **主指标**（订阅制下唯一硬成本） |
| Δresolved | D − A 的通过率差（配对） | 质量非劣 |
| 影子金额比 | 按 `config/prices.json` 折算 | 辅助，跨模型可比 |
| 墙钟比 | D ÷ A | 体验代价 |
| 人工介入次数 | 用户额外输入/确认的次数 | 定义"体验不变" |

**判定（预注册，跑之前定死）**

- **支持**：H 额度比 < 0.5 **且** Δresolved 的 95% 区间下界 > −10pp → D 可作默认路径
- **有条件支持**：额度比 0.5–0.8 → 只在轨道 B/C 的场景开 D，单点任务仍走 A
- **否定**：额度比 > 0.8，或 Δresolved 下界 < −10pp → D 不成立，只保留 C

### 轨道 B · 批量同构修改

**形态**：一条需求，N 个同构单元，每个单元有自己的验收。

| 批 | 需求形态 | N | 验收 |
|---|---|---|---|
| B1 | 给 N 个函数统一加参数校验 + 错误码 | 10 | 每单元一个断言脚本 |
| B2 | N 个脚本统一改日志格式 | 12 | 每单元跑一次 dry-run 比对输出 |
| B3 | N 个 loader 统一加超时与重试 | 8 | 每单元模拟超时，断言重试次数 |

**臂**：A（Codex 一次做完 N 个）／D（1 份计划拆 N 个任务 + N 个 worker）

**格数**：3 批 × 2 臂 = **6 格**（每格内部有 N 个单元，按单元统计）

**指标**：每单元成本（总额 ÷ N）、每单元通过率、H 额度比、墙钟。
**判定（2026-11-11 二次修订：金额口径）**

> **不能用 token 数比较。** A 的消耗是 H（$2/百万输入、缓存 $0.1、输出 $10），
> worker 是 L（$0.15 / $0.003 / $0.60）。同一件事 L 的 token 计数本就是 H 的 2 倍多，
> 单价又差 13 倍——直接相除得到的是"汇率"，不是成本。
> b3 实测：token 差 **19.6 倍**，折成钱 worker 反而**便宜 45%**。

| 步骤 | 规则 | 不过怎么办 |
|---|---|---|
| **预判门槛（金额）** | 用参考样本的 `worker 每单元成本`（b3 实测 $0.00526/尝试）与 A 的每单元成本比；若 `A/单元 ≤ worker/单元` → 执行侧就省不下来 | 不跑 D |
| **保本 N** | `N ≥ 计划成本 ÷（A/单元 − worker/单元）`。b3 实测：$0.0507 ÷ $0.00427 ≈ **12 个单元** | N 远超实际批量（>20）则不跑 |
| 主判定 | 跑 D 后：`D 总成本 < A 总成本` **且** 通过率不低 → 批量场景成立 | 否则记为"本批 N 不足以摊薄规划" |

两个必须一起报的分母：worker 成本按**尝试数**和按**成功落库数**算出来的每单元成本可能差一倍
（b3 是 $0.00526 vs $0.00921，因为 7 次尝试只落了 4 个）。只报前者会高估收益。

> 方向：**N 越大 D 越省**（worker 每单元比 A 便宜，节省随 N 线性累积，计划费只付一次）。
> E18/E19 里"N 越大越亏"的说法基于 token 相除，已作废，见实验日志 E21。

### 轨道 C · 文字/文档任务

**形态**：10 个文档任务，全部有确定性验收（不靠模型打分）。

| 任务类 | 例 | 验收方式 |
|---|---|---|
| 技术说明 | 依据仓库 README + 代码，写一份 1500 字模块说明 | 必备小节齐全、字数区间、术语表条目数、不得出现占位符 |
| 变更说明 | 依据 git log 写 CHANGELOG 条目 | 每条对应一个提交、格式正则、不得遗漏区间 |
| 结构化改写 | 把 12 段笔记改写成统一体例 | 段落数、每段字数上限、禁用词表、编号连续 |

**臂**：A／D（各 10 格 = 20 格）
**指标**：合格率、输出 token、影子成本、墙钟。
**判定**：D 成本 < A 的 0.6 **且** 合格率 ≥ A → 文字场景成立。

## 5　执行顺序

1. **P0 工程前置**（半天，不烧额度）
   - 冻结 codex 版本与 `workers.json`（记录 hash 到 `env-manifest.json`）
   - `--reps` 支持与断点续跑校验
   - 429 退避重试（`glm-5.3-flash` 备用档用得上）
   - 题库版本化：每题记 `sha256(seed)`，防止跑批中途改题
2. **P1 轨道 B（先做）**：单元数固定、结构最干净，最容易看出摊薄效应
3. **P2 轨道 C**：写题成本低（模板化），能快速验证"输出价差"这一条
4. **P3 轨道 A**：最重，放最后；题库已在前两步跑顺后再上量
5. **P4 汇总**：三张表 + 一页判定结论

**为什么 B 先于 A**：如果批量场景都不成立，A 的 120 格只是在确认一个已知的弱收益；反之若 B 成立，A 的结论会更有分量（说明"该开的时候能开对"）。

## 6　三个必须提前写清的边界

1. **不做非劣确认。** n=24，配对二元终点在 15% 不一致率下，95% 区间半宽约 **±15pp**（n=30 也只到 ±13pp）。
   只报"观测差 + 区间"，不写"确认非劣"。要确认得 120 题以上，那是另一个预算。
2. **金额是影子价。** 订阅拿不到逐次账单，所有美元数都是等价 API 折算，只用于相对比较。
3. **任务族限制外部效度。** 全部跑在本机（无容器、无网络隔离），结论限定在"这套任务族 + 这套环境"。

## 7　止损规则（跑之前定）

| 触发 | 动作 |
|---|---|
| 某题 3 次计划均被拒 | 记 `plan_rejected`，不计入通过率分母，单独报数 |
| 某臂失败率 > 50% 且失败原因集中在同一处 | 暂停该轨道，先查管线（历史上 5 次"模型失败"全是管线 bug） |
| 单格 H 输入 > 2M token | 强杀，记 `over_budget` |
| 连续 3 格 429 | 暂停 1 小时；仍失败则换 `glm-5.3-flash` |
| 中途 codex 版本变化 | **立即停批**，重跑 preflight，记入 `env-manifest.json` |

### 路由臂为什么延后

路由的价值是"把批量任务导给 D、把非批量导回 A"。B 不成立，就没有可路由的东西，
所以顺序上必须先有 B 的结论。真要做得单独设计：

- **形态**：同一批混合任务（3 S + 3 M + 2 L 交错），比较"路由版 / 固定 D / 固定 A"的总成本与总通过率
- **难点**：路由本身有判断错误率，会与机制效应混在一起；需要先固定判断器（例如按文件数阈值），把它当常量

## 9　明确不做

- 不用 ollama / 本地模型（工具调用不可靠，且与 B 共用 L 无法分离效应）

- 不把 B 当主对照（不是可选方案）

- 不在跑批中途改题、改 workers、升 codex
