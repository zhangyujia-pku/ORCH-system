## 架构：为什么不是最初设想

原计划是「dispatch 起个后台进程，跑完回传」。实测这个环境里做不到：

| 尝试 | 结果 |
|---|---|
| `DETACHED_PROCESS` | 进程能起，命令一结束就被父级 Job Object 清掉，连 4 秒都活不到 |
| `CREATE_BREAKAWAY_FROM_JOB` | `PermissionError [WinError 5]`，job 不允许脱离 |
| `schtasks` 计划任务 | 在程序安全黑名单里，且明确禁止换 shell 绕过 |
| `explorer` 启 vbs / `cscript` | 沙箱内被拦（后者判为 LOLBin） |

结论：**任何依附于那条命令的进程，都活不过那条命令**，而一次 run 要 5–15 分钟。

所以改成常驻宿主：

```
Codex 窗口
  ↓  dispatch：intake + 写 ~/.orch/queue/<run_id>.json（毫秒级返回）
    ────────────────────────────────────────────
orch serve（常驻，由对话之外的终端/VBS 拉起）
  ↓  每 3 秒轮询，取到任务起子进程执行
    python -m orch.dispatch --job <run_id>
  ↓  plan → validate → run → verify → merge
codex queue --thread <T> --message <报告>
  ↓  桌面端消费队列，消息以 user 身份进入会话
同一个窗口看到【orch 完成】
```

**为什么 serve 要起子进程而不是自己跑**：见下面第 1 个故障。

## 五次失败，五个不同层面的根因

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `ImportError: cannot import name '_OUT_SPEC'` | serve 00:56 启动时把旧版 `contract` 读进内存；01:08 有人改了 `verifier.py` 要用新符号，01:09 导入失败。磁盘上一致，漂移的是长驻进程的内存态 | serve 不再自己执行，每任务起子进程 |
| 2 | `thread 没认出来`（等满 45 秒） | Codex 记的 `CommandExecution.process_id` 是它启动的 pwsh，但真正执行命令的是中间层 `codex-command-runner`。祖先链到不了 pwsh，pid 这层在桌面端必然失配 | 加命令文本指纹层 |
| 3 | `越界 [drafts/01-/345/247/225/250/250/200.md]` | git `core.quotepath` 把中文路径转成八进制转义，和契约里声明的 `writes` 对不上 | `_run` 统一加 `-c core.quotepath=false` |
| 4 | 三个任务都 `committed` 却全 `verify=false` | 验收判据是全局的（要求 3/3），但验证在单个 worktree 里做，另外两份还是原稿 | `check_all.py` 支持单份参数 |
| 5 | Planner 自己加了「全部任务完成后跑 check_all.py」 | 同上，且它把这条写进了每条 acceptance | 脚本改为按「近期改动涉及的文件」自适应 |

前三个是 orch 的缺陷，后两个是判据设计问题。

### 故障 2 的证据链

```
Codex 记录:   process_id = 6840   (它启动的 pwsh)
日志候选:     [1020, 1168, 1292, 2864, 4352, 9952, 34940, 37224]
按数值排序:   6840 应落在第 6 位，实际第 6 位是 9952  → 6840 不在链里
```

用 pwsh 单独启 python 测得 `ppid_in = True`，说明 `ancestor_pids()` 本身没错；错在「Codex 记录的 pwsh 就是命令父进程」这个假设。

最终方案：取原话前 20 个「非噪声字符」（剥掉标点/空格/引号/反斜杠），在会话记录的命令文本里做子串匹配。

```
原话  用 orch 把这件事交给编排器：按 standards/写作规范.md 润色…
指纹  用orch把这件事交给编排器按stand
命中  01a1b1fa-9393-7653-bdd6-d15ec7bfda91   method=fingerprint  high
```

优先级：`pid → fingerprint → nonce → cwd(medium)`。

## Codex 侧的通道（实测结论）

| 发现 | 意义 |
|---|---|
| `codex queue --thread <UUID> --message <TEXT>` | 官方「往指定会话投消息」接口，消息落 `~/.codex/queue_1.sqlite` 的 `queued_items` |
| 不需要 `--resume`，不需要 daemon | 桌面端自己订阅队列，活跃时立即消费（实测 4.4 秒起一轮） |
| 会话记录里 `turn_trigger: "queue"` | 可精确区分「外部注入」和「用户说话」，实验数据可过滤 |
| `$CODEX_THREAD_ID` 在桌面端**为空** | 只在 exec-server 沙箱里注入，走 `pwsh -Command` 时没有 |
| `originator: codex_work_desktop` / `codex_exec` | 能区分对话窗口和引擎后台会话 |

**限制**：窗口不活跃时消息会留在队列里，切回该窗口才显示。不会丢，但不是实时推送。

## 讨论过但**未实施**的

**仓库契约下沉。** 现在用户要在对话里手写「改哪些文件 + 禁区 + 验收命令」，这不是自然语言。讨论结论：

- 不该把格式写进 skill（只是把负担从人挪到提示词）
- 该把「怎么算完成」下沉到仓库（`AGENTS.md` / `.orch/verify.md`），skill 只做「发现 / 转达 / 提醒」
- 前提是**原话照旧一字不改存进 `intent.md`**，契约只作为 Planner 的上下文，否则会污染「含糊度 → 重写次数」这个自变量的实验

配套要改：`planner.py` 的 prompt 注入契约、`SKILL.md` 只写三条职责、可选 `orch init` 扫仓库生成草案。

## 还欠着的

- **路由没接线**：`workers.json` 里 5 个档（local / dsh / cbc / codex / codex-ds）只用于 `orch route` 试算，`dispatch` 写死 codex。所谓「多智能体」现在是「同一个 Codex 并开三份」
- **`--ephemeral`**：worker 不落会话历史，事后查不到它用的具体模型
- **vbs 未验证**：沙箱里 `explorer` / `cscript` 都被拦，终端启动是唯一实测过的路径
- **无 toast 提醒**：窗口不活跃时消息静默排队
- **任务级 / 集成级验收未分层**：现在靠脚本自适应绕过去，contract 里没有 `integration` 字段
