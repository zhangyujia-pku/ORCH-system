# 第一步实施与验收说明

日期：2026-11-07。范围：状态、动作、事件、报告一致性。结果：151 项测试通过。

对应设计：[第一步梳理](第一步_状态与行为一致性梳理.md)。本记录解释本轮实际修改，梳理文档保留实施前观察。

## 1. 每处改动及原因

| 位置 | 实际改动 | 为什么这样改 |
|---|---|---|
| `orch/planner.py::plan_run()` | 失败记录实际尝试数、停止原因、`execution_started=false`、`fallback_executed=false`；重规划前归档旧计划与规格 | 规划没通过不等于已经换模式执行；旧计划不能冒充新计划 |
| `orch/cli.py::cmd_plan()`、`orch/dispatch.py` 的规划失败分支 | 明确报告尚未执行，保留失败退出码 | 文字和动作一致 |
| `scripts/intent_features.py::plan_stats()` | 旧 `fallback` 事件解释为规划未通过 | 历史名称不能证明真实降级；不改写历史数据 |
| `orch/workers.py::Assignment`、`route_one()` | 增加明确阻断原因；不满足规格时拒绝；保留合法大写集的 R04 | 理由码相同不代表能否执行相同，不能把全部 R04 一律拒绝或放行 |
| `orch/runner.py::run_plan()` | 在创建任务目录、调用 worker 前完成基线、计划和完整分派检查；缺能力、未核验、规格不符或适配器缺失均阻断 | 已经花钱开工后才发现派不出去，会产生不完整且难解释的结果 |
| `orch/providers.py` | 工厂构建的执行路由严格要求每个任务有分派，任何适配器构建失败都拒绝；显式旧用途仍可使用非严格默认路由 | 保留兼容用途，同时防止真实执行悄悄兜底 |
| `orch/intake.py` | 记录完整 Git 提交标识及获取失败原因 | 起点是实验条件，不能丢失失败原因 |
| `orch/runner.py` 的基线检查 | 兼容有效旧短标识，解析并记录完整标识；缺失或不可用就停止，不覆盖原始记录 | 换起点会改变任务背景；旧记录仍需可读取 |
| `orch/worktree.py::commit()` | 返回“是否创建新提交”与版本标识；无改动独立处理；提交失败明确抛出 GitError | 旧 HEAD 能读取，不证明这一次提交成功 |
| `orch/runner.py::_run_one()` | 提交失败记录任务失败，不验收、不接纳；没有新提交记录 `task.no_commit` 并继续按任务判据验收 | 提交证据和功能证据是不同的判断 |
| `orch/runner.py` 的结果收集 | 单任务异常保留为失败，独立任务结果仍可记录；整体不能因部分完成而成功 | 一项失败不应抹去其他事实，也不能被其他成功掩盖 |
| `orch/trace.py`、新增 `orch/status.py` | 新事件带 `operation_id`；查询按本次调用关联，旧记录仅保守显示最近阶段 | planner 和 runner 的 session 各自计数，不能拼成统一运行编号 |
| `orch/dispatch.py::_finish()` | 先记录明确阶段、执行结果，再独立记录通知结果；仅规划成功标为 `planned` | 计划就绪不等于执行完成；通知没送达也不等于任务失败 |
| `orch/cli.py::cmd_status()` | 输出最近调用的真实状态与独立通知状态；移除执行前重复路由记录 | 避免旧成功结果和预测分派冒充当前事实 |
| 当前操作文档 | 更新失败、路由和状态口径，保留历史过程说明 | 后来的用户和 AI 不应继续依据旧承诺操作 |

直接指定一个 Provider、但任务声明了外部能力且未提供 workers 配置时，也会阻断：没有注册信息就不能声称已确认该后端具备能力。注册表声明通过不等于外部平台真实可用；真实能力探测仍属后续异构闭环。

## 2. 涉及概念，用例子解释

### 规划与执行

生成计划像写好实验步骤，执行像真正做实验。规划命令返回 0，说明计划生成成功；功能可能还没开始写。因此 `planned` 和 `done` 必须分开。

### 硬约束与默认选择

任务需要数据库访问，换成推理更强但不能连数据库的模型仍然做不了。先确认资格，再选择后端。资格不满足时停止，是如实表达系统能力。

### 基线

基线是约定的代码起点。同一句需求分别在旧代码和新代码上执行，不是同样的条件。缺失时自动换成当前 HEAD，会破坏可追溯性。

### 提交、无改动和验收

提交是把修改保存为一个 Git 版本。提交成功并不证明功能正确，还需要验收；没有新改动也不一定错误，例如目标行为本来就存在。两种情况分别记录，再按实际判据判断。提交失败则不能把未可靠保存的修改接纳为完成成果。

### 状态、事件和关联标识

状态回答“现在怎么样”；事件记录“发生过什么”。`operation_id` 将本次规划、执行和报告串起来；旧 session 保留，但不再把不同阶段碰巧相同的数字当成同一次运行。

### 故障注入与没有发生的动作

测试让模型返回坏计划、让提交失败，然后检查 worker、验收器、合并函数的实际调用次数。只断言报告写了“没有执行”并不足够；还要验证相应函数确实没被调用。

## 3. 验收覆盖

新增 `tests/test_step1.py`，扩展 `tests/test_providers.py`。核心检查：

- 三次坏计划与一次调用故障：实际尝试数正确，未启动执行器。
- 重新规划失败：旧成功计划归档，查询显示本次失败。
- 能力缺失、未核验、规格不符、分派缺失、适配器部分失败：整次计划在 worker 启动前阻断。
- 有效双后端分派：实际 Provider 调用与路由事件一致，使用模拟后端。
- 空计划、缺失/非法/不存在基线、非 Git 目录：不误报成功，不创建任务工作目录。
- 有效旧短基线：正常解析，不覆盖原记录；原有重复运行基线测试保留。
- 提交失败：不发成功事件，不验收、不合并该任务；独立任务成功仍保留。
- 无改动与真实新提交：分别记录，使用临时真实 Git 仓库核验。
- 仅规划、执行阻断、执行成功、通知失败：状态和报告一致；实际通知始终模拟或禁用。
- 新调用不受旧 session 数字影响，旧 fallback 记录仍可解释。

原有测试基线：122 项，4 项失败、6 项错误。基线记录位于 `.step1-review/baseline-tests.txt`。其中缺少 `shutil` 导入导致适配器构建报错，失效可执行路径无法正确回退；本轮修复。原输出测试依赖 `cat`，在 Windows 命令环境不可用，改为使用 Python 读取同一测试文件，仍走实际命令验收路径；没有提前修改验收器功能。

测试临时目录设置为工作区内 `.step1-review/tmp`，避免当前运行环境的默认临时目录访问失败。仅修改本次命令的环境，不更改用户系统设置。

最终运行仓库约定的 `python -m unittest discover -s tests -t . -v`，151 项全部通过，耗时 70.935 秒。完整记录见 `.step1-review/final-tests.txt`。相对原有 122 项，增加 29 项测试。

本次不是对真实模型性能或外部平台可用性的评测；模拟响应保证故障可控，临时 Git 仓库验证实际文件与版本行为。与修改前副本对比，`contract.py`、`verifier.py`、`worker.py`、`prompts.py`、任务 schema 及新增成本测量脚本均未变更。

## 4. 本轮边界与保留事项

- 未实施依赖成果传递、合并后整体验证、worker 返工、真实单 Agent 降级、运行期预算控制或语言学研究模块。
- `fallback` 和 `plan.fallback` 保留兼容；新记录明确没有执行降级。旧 E/W 错误码及原始历史事件不改写。
- 任务提交失败时拒绝该任务，但已有独立成功任务仍可能合并；整体结果明确失败。事务式全有或全无整合不在本步。
- 当前执行成功只覆盖已有的任务验收与合并，不能据此宣称通过尚未实现的整体验证。
- 本轮没有真实模型质量或浏览器能力验收，没有发送实际聊天通知。
