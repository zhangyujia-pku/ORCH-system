## 2026-11-10

### E1　基线脚本 + 第一次成本对照（13:5x）

**做了什么**：写 `scripts/baseline.py`，让 Codex 独自做同一件事，用与 orch 相同的 `--json` 口径采 token。

**为什么**：orch 侧数字有了（v1.9.3），但“省了多少”缺另一半。两边口径不同就没法比。

**结果**（1 行任务、同模型 `deepseek-flash`、都为 1 轮）：

| | 输入 | 未缓存输入 | 输出 | 墙钟 |
|---|---|---|---|---|
| Codex 独自 | 121,071 | 751 | 217 | 68.5s |
| orch worker | 167,941 | 2,437 | 583 | ~94s |
| 比 | 1.39× | **3.24×** | **2.69×** | 1.37× |

**判断**：这个规模编排是亏的。worker 的 prompt 要带 spec、验收标准、仓库规则，固定开销摊不掉。
与“单点修改自己干”的既有规则一致。

**注意**：同一任务前一次 orch 跑出 394k 输入 / 3,315 输出（轮次更多）。**单次不可下结论**，正式实验 n≥5 并记录轮次。

**踩坑**：`--json` 下 worker 侧曾出现 `turns: 0`——`turns` 不在 `tokens_` 前缀里，被 `resources` 覆盖逻辑丢掉了；已修并加回归测试。

### E2　功效模拟：120 题在 −5pp 上够不够（14:1x）

**做了什么**：按配对四格参数化模拟，算“真值无差”时确认非劣效的概率。

**为什么**：SWE-Bench 方案默认 120 题 + −5pp 非劣。想先知道这个组合有没有把握，再谈预算。

**结果**（不一致率 15%、A 通过率 0.45）：

| n | −5pp | −8pp | −10pp |
|---|---|---|---|
| 120 | **31%** | 63% | 81% |
| 240 | 52% | **89%** | 98% |
| 480 | **81%** | 99% | 100% |

**判断**：120 + −5pp 会得到一个大概率给不出主结论的设计（区间半宽 6.9pp > 边界 5pp）。
三条出路：480 题保 −5pp / 240 题放宽到 −8pp / 120 题只做区间估计。

**踩坑**：第一版模拟写错了——两臂独立抽样时不一致率约 50%，不是 15%。改成按配对四格直接参数化才对。

### E5　BugsInPy Windows 探针（14:29–14:42，结论：不可用）

**做什么**：在 Windows 上试跑 BugsInPy 的 bug，看能否复现“buggy 失败 / fixed 通过”。

**为什么**：这是唯一可能同时满足“真实项目、多文件、本地可跑”的现成基准。成了就用它做锚，自建题降级为机制诊断。

**过程（全部失败，但每一步的失败原因不同）**：

| 步骤 | 结果 |
|---|---|
| clone `soarsmu/BugsInPy` | ✅ 17 个项目 |
| youtube-dl bug 1 元数据 | py 3.7.0 · buggy `99036a1` · fixed `1cc47c6` · 测试 `test_match_str` |
| `git clone --filter=blob:none` | ❌ `invalid index-pack output`（Windows 上部分 clone 过滤器不兼容） |
| 普通 clone youtube-dl | ❌ 600s 未完成（仓库历史过大），超时终止 |
| 改下载 commit 源码包（codeload） | ✅ 1.35MB，两版本都拿到 |
| **youtube-dl bug 1 A/B** | ⚠️ **两个版本都通过**（`Ran 1 test ... OK`）→ 该 bug 在 Python 3.13 上不复现 |
| PySnooper bug 1 元数据 | py 3.8.1 · 测试 `tests/test_chinese.py::test_chinese` |
| **PySnooper bug 1 A/B** | ❌ **buggy 提交里根本没有这个测试文件**（测试随修复提交一起加入，需 harness 应用 test patch）；fixed 提交直接 `ImportError: cannot import name 'Mapping' from 'collections'`（3.10 起已移除） |
| 取旧解释器：python.org 3.7.9 | ❌ 180s 超时 |
| 取旧解释器：nuget `python/3.7.9` | ❌ 无产物（下载未落地） |
| 取旧解释器：`uv python install 3.9` | ❌ uv 不在 PATH |
| 取旧解释器：`pip install uv` | ❌ 超时中断 |

**判断**：BugsInPy 默认假设两件事——**每个 bug 有专属旧解释器（3.6–3.8）、且由 harness 施加测试补丁**。
在这台机器上两个前提都破了：现代 Python 让旧代码 import 就失败，而旧解释器四条获取路径全断。

**结论**：**BugsInPy 在 Windows + 现代 Python 上不可直接使用。** 要用它，得手动装 3.7/3.8 安装包并为
17 个项目逐 bug 配依赖——工作量与自建任务族相当，只换来“外部认可度”这一项收益。

**决定的依据**：探针成本约 15 分钟，换来的是一个确定的“不行”，以及“为什么不行”的具体位置。
这比“凭印象认为跑不了”有价值得多。

**做什么**：按“我是脚本、你是实验者”的分工写四个脚本，用 3 个任务（2 个 S + 1 个 M）× 4 臂试跑。

**结果（每格 1 次，串行）**：

| 臂 | resolved | 中位墙钟 | 平均输入 token | 备注 |

3. **整合验收起作用了**：D 的 t03 四个任务各自都过（任务级只测一格样例），

### E9　查 token 异常 + 接单价 + 复验管线（18:35–18:53）

**一、D 臂 token 为什么高（结论：跨模型 token 不可比）**

做法：同一句提示词（“只回一个字：ok”）、同一仓库、同一外壳，分别用 A（H）和 B（L）跑一次。

| 臂 | 模型 | 输入 token | 缓存 | 输出 |
|---|---|---|---|---|
| A | gpt-6.1-sol | **17,147** | 16,256 | 5 |
| B | deepseek-flash | **40,683** | 40,448 | 2 |

**同一内容，L 的 token 计数是 H 的 2.4 倍。** 而实际任务里 C（H 执行）79,833 vs D（L 执行）636,987，
差 8 倍——超出 2.4 倍那部分，无法从现有日志区分是「tokenizer 差异」「内部重试」还是「上下文计价口径」。

**因此定三条规矩**：
1. **不做跨模型的 token 数比较**，只比折算后的金额；
2. 各臂成本按各自单价分别算（H：$2/$0.1/$10；L：$0.15/$0.003/$0.6 或高峰翻倍）；
3. 要彻底拆开这个差异，得有 provider 侧 request 级日志——本轮不做，记为局限。

**二、单价表（2026-11-10 查证）**

| 模型 | 输入 / 缓存输入 / 输出（每百万 token） | 备注 |
|---|---|---|
| gpt-6.1-sol | $2.00 / $0.10 / $10.00 | 统一价 |
| deepseek-flash 空闲 | $0.15 / $0.003 / $0.60 | — |
| deepseek-flash 高峰 | $0.30 / $0.006 / $1.20 | UTC 周一至周五 01–04、06–10 |

已写入 `config/prices.json`；`cost_of()` 按模型 + 运行时刻自动选档（高峰差一倍，混算会错 30%+）。
注意：这是**等价 API 单价**，不是订阅实付。

**三、管线复验（t02 一题四臂，`runs/exp/smoke.jsonl`）**

| 臂 | resolved | 墙钟 | 输入 token | 成本（估算） |
|---|---|---|---|---|
| A（H 端到端） | ✅ | 65s | 123,986 | **$0.0467** |
| B（L 端到端） | ✅ | 56s | 346,420 | **$0.0025** |
| C（H 规划 + H 执行） | ✅ | 106s | 93,700 | **$0.0354** |
| D（H 规划 + L 执行） | ✅ | 107s | 372,266 | **$0.0135** |

四条都通，成本能正常算出，且 **D 比 A 便宜 3.5 倍、两者都通过**。

**但这是 1 题 1 次，不能当结论**。它只证明：管线能产出「质量 + 成本 + 时间」三者同表的数据。
另外注意 A 比 C 便宜不了多少（都是 H），但 C 慢 63%——**编排的时间开销在小题上是纯亏**，
这与 E1 的结论一致。

**四、又修的两个坑**

### E10　M 档真实题 + B 的天花板（19:05–19:35）

**一、探针：真实仓库能不能在本机跑**

| 仓库 | Windows + 3.13 | 测试 |
|---|---|---|
| **more-itertools** | ✅ | 771 passed / 31s |
| **boltons** | ✅ | 620 passed / 6s |
| humanize | ⚠️ | 需 `pip install -e .` + freezegun，未继续 |

**二、造题方法（关键）**

直接 `git revert` 会把测试一起撤掉，题就没有判据了。正确做法是**只回退源码**：

```
git show <commit> -- <源文件> | git apply -R
```

测试留在修复后的状态 → 跑起来必失败 → 这道题有判据。
参考解就是原提交的源码改动，正向 `git apply` 一遍即可验证"可解"。

已封装成 `scripts/make_task_from_commit.py`（自动抓失败用例、生成 checks、双向验证）。

**产出**：t04（chunked_even 边界校验，2 条判据）、t05（bucket 假值校验，1 条判据）。
t06 因"回退后测试不过"被丢弃——说明自动验证在起作用。

**三、B（L 端到端）会不会有跑不出来的题**

**目前 5/5 全过**：t01、t02、t03、t04、t05。

| 任务 | 类型 | B 结果 |
|---|---|---|
| t01 | 自建 S：三个统计函数 | ✅ |
| t02 | 自建 S：修时长解析 bug | ✅ |
| t03 | 自建 M：四模块 | ✅ |
| t04 | **真实** M：more-itertools chunked_even | ✅（2 passed） |
| t05 | **真实** M：more-itertools bucket | ✅（1 passed） |

**结论：便宜模型单独就能修真实 bug。** 单文件、判据明确的任务，B 没有天花板缺口。
这意味着 **D 臂的前提（任务超出 L 能力、但可拆给 L）在 S/M 档不成立**——D 只能比 B 更贵。

**四、又一个"看起来像模型失败"的管线 bug**

首轮 t04/t05 都记成 resolved=False，报错是"找不到 checks 脚本"。
真因：`score()` 把 checks 拷到了仓库根，而 accept 里写的是 `python checks/xxx.py`。
修好后离线重评：**两题都通过**。

如果没查这一步，会得出"B 连真实题都解不了"的完全相反结论。
**这是本周第 4 次同类事故**：管线 bug 伪装成被测对象的失败。

**下一步的两条路**：

1. **往上加难度**：造 L 档（跨模块、接口变更、需要改 3+ 文件），看 B 是否开始失败；
2. **接受负结论**：在"单文件、判据明确"的任务族上，编排无经济价值——这与 E1 一致，

### E11　同一批题上 B 与 D 的对比（19:25–19:43）

**一、先修一个出题的坑**

D 第一次跑 t04/t05 全挂，`patch=0`。原因不是模型：**规划器把 goal 里的
"验收跑 python checks/check_t04.py" 原样抄进 acceptance，而仓库里没有 checks/ 这个目录**，
worker 的验收直接"找不到文件"。

修法：`make_task_from_commit.py` 现在把 checks **同时写进 seed**（打分时仍用题库副本覆盖）。
题自洽了，agent 也能自测。

**二、修好后的同题对比（各 1 次）**

| 题 | 臂 | resolved | 墙钟 | 成本 | 补丁 |
|---|---|---|---|---|---|
| t04 | B | ✅ | 102.6s | **$0.0065** | 442 B |
| t04 | D | ✅ | 130.0s | $0.0368 | 442 B |
| t05 | B | ✅ | 64.7s | **$0.0032** | 506 B |
| t05 | D | ✅ | 127.2s | $0.0625 | 506 B |

**两题都通过，D 贵 5.6× / 19.8×，慢 1.3× / 2.0×。**

**三、拆开看，结论完全变了**

| 题 | D 的规划成本 | D 的执行成本 | B 的端到端成本 |
|---|---|---|---|
| t04 | **$0.0315**（86%） | $0.0052 | $0.0065 |
| t05 | **$0.0595**（95%） | $0.0030 | $0.0032 |

**执行侧其实更便宜**（$0.0052 < $0.0065）：编排把任务收窄了，L 干得更省。
**但规划一次要 $0.03–0.06，是整件事的 5–20 倍。**

原因是价格结构：H 输入 $2/百万，规划要读仓库（t04 用了 ~480k 输入 token）；
L 修完全程才 $0.006。**一次规划的价钱 ≈ 十次 L 的执行。**

**四、这改变了实验单位**

D 要成立，规划成本必须被摊薄。三种可能：
1. **一个计划带 N 个任务**（t03 就是 1 计划 4 任务）——任务越多，单任务摊到的规划费越低；
2. 规划复用（同一仓库的后续需求）；
3. 规划改用便宜档。

所以「一道小题」不是合适的比较单位，**「一次需求」才是**：
真实使用是"我要这个功能"，它自然拆成 3–6 个任务，规划只付一次。

**下一步建议**：把 L 档题改成"一次需求 = 多任务"（例如给 more-itertools 加一个新 recipe，
涉及实现 + `__init__` 导出 + `.pyi` 存根 + 文档 + 测试），在那种题上比 B 与 D。

**B 至今 6/6 全过**，包括跨文件新功能（3 个函数 + LCG 统计性质 + 存根）。

**成本拆解与保本点**：

| 题 | B 端到端 | D 规划 | D 执行 | D/B | 保本所需任务数 |
|---|---|---|---|---|---|
| t04 | $0.0065 | $0.0315 | $0.0052 | 5.6× | **25** |

保本任务数 = 规划成本 ÷（B 成本 − D 执行成本）。含义：**一个计划要覆盖这么多任务，
D 才不比 B 贵。**

**结论（本次实验最重要的三条）**：

1. **编排的执行侧确实更省**：同样三个任务，D 的 worker 比 B 端到端便宜 20% / 6% / 33%。
   "把任务收窄" 这个机制是有效的。
2. **但规划一次要 $0.03–0.08**，等于 3–25 倍的执行成本。**一次规划 ≈ 十次执行。**
3. **所以保本需要 12–25 个任务共享一份计划**（t05 那种 B 极便宜的情形要 480）。
   我们现在的"一次需求拆 3–6 个任务"远不够。

**前提也被推翻了一半**：原假设是"任务超出 L 能力、但可拆给 L"。
实测 deepseek-flash 单独就能做跨文件新功能（6/6），**没有可拆的缺口**。

**如果要让这个架构有意义，只有三条路**：
① 计划覆盖 12+ 任务（改实验单位）；
② 规划改用便宜档或复用（降 plan 成本）；
③ 换更弱的 L（让"拆"真的有价值）—— 但这会变成另一个实验问题。

### E14　阶段性结论（2026-11-10 21:40）

#### 结论一：大部分场景下，Codex + 编排相对"单 DS 单干"没有优势

**证据**（累计 6 道题、每格 1 次）：

| 观察 | 数字 |
|---|---|
| B（DS 端到端）通过率 | **6/6**，含跨文件新功能（t06：3 函数 + 存根 + LCG 统计性质） |
| D 的成本构成 | 几乎全在规划：t04 86%、t05 95%、t06 84% |
| 保本任务数（一份计划需覆盖多少任务） | t04 **25**、t05 **480**、t06 **12** |
| D 执行侧 vs B 端到端 | 便宜 20% / 6% / 33%（机制有效，但被规划费吃掉） |

**所以这个项目的价值不在"比不用编排更省"，而在于：**

> **维持 Codex 单应用开发的体验性与便利性**——不换工具、不离开客户端、不手工拆任务；
> 把执行从 Codex 的额度里挪出去（实测压到 **5–15%**），质量与 Codex 单干持平。

**仍然有价值的场景**（这是"大部分场景无优势"的例外，也是后续该做的方向）：

1. **批量同构修改**：一份计划覆盖 N 个同构单元（N 越多，规划费摊得越薄；
   实测 N=3 时 D/A 降到 0.06–0.27×）。
2. **文字任务处理**：输出密集型。H 输出 $10/M vs L 输出 $0.6/M，差约 17 倍；
   而文档类任务的成本主要在输出上，这与代码任务（成本主要在读仓库的输入）方向相反。

#### 结论二：本地模型工具调用困难，端云协同存在现实困难，继续用云端模型

**依据**：

| 项 | 实测 |
|---|---|
| 本机 ollama | 未安装、无服务；安装包 1.86 GB + 模型 2.3 GB |
| `ollama run` 能力 | 只能生成文本，**不能改文件**；当 agent 需绕 OpenAI 兼容端点 + 多轮工具循环 |
| 4B 级模型在该循环里的典型失败 | 不是"不会写代码"，而是**不会按格式调用工具**；测出来的是工具遵从性，不是编程能力 |
| 更致命的一点 | D 的 worker 与 B 是**同一个 L**。L 太弱时两臂同时失败，**结构上比不出差异** |

**决定**：L 固定用云端模型（`deepseek-flash`，或 `glm-5.3-flash`）。端云协同不作为本轮路线。

#### 顺带确认的可复现事实（供报告引用）

- codex **0.167 起移除 `wire_api = "chat"`**，自定义 provider 只能用 `responses`。
- 智谱的 Responses 端点是 `https://open.bigmodel.cn/api/v1`（不是 `/paas/v4`）；key 需 `id.secret`。
- `glm-4.7-flash`（早前宣称免费）在本账号**不在模型目录**且持续 429（code 1305），免费档撑不起批量实验；可用的是 `glm-5.3-flash`。

#### 文档

`orch项目说明与进展` 升版为 **v4 · 2026-11-10**，新增「四臂实测」一节，并按上面两条结论改写边界与下一步。

### E16　停批：先把尺子钉死（22:50–23:05）

**触发**：用户指出"我们似乎一直在改尺子"。这个判断成立，先把账摊开。

| # | 改了什么 | 为什么 | 失效范围 |
|---|---|---|---|
| 1 | 参考解的空串判定 `== ""` → `strip() == ""` | 判据把全空白也算空串 | b1 自检作废 |
| 2 | 验收脚本补 `sys.path.insert(0, ".")` | b2 的 `import scripts.*` 找不到仓库根 | b2 自检作废 |
| 3 | seed 加 `.gitignore` | **跑出来之后才发现**：worker 跑验收生成 `__pycache__`，被判"越界写入"，8 任务废 4 个 | 用户跑的那次 b3/D（4/8、FAIL）作废 |

第 3 条尤其说明问题：`task.out_of_scope` 的文件是 `src/__pycache__/*.pyc`，
**这是环境产物，不是模型越界**。它能潜伏到跑批阶段，是因为前三轮自检只验"seed 必败 / 参考解必过"，
没验"worker 正常执行时会不会产生额外文件"。

**决策一：把"冻结"做成机制，不靠记性**

- `scripts/freeze_taskset.py freeze` → 给题库每个文件算 sha256，汇总成一把总哈希，写 `tasks/FREEZE.json`
- `scripts/freeze_taskset.py check` → 核对当前题库是否仍是那一把
- `scripts/sim.py collect` → 写结果之前先对表，**不一致直接拒绝写入**（退出码 3）

冻结记录：`taskset-v1` · 总哈希 `bb77d705…` · b1 42 文件/b2 52/b3 34 ·
codex `0.167.0-alpha.3.2` · orch `v1.9.4-13`

**决策二：验收做实——三种撞法都要挡住**

| 撞法 | 期望 | 实测 |
|---|---|---|
| 空补丁 | 0 通过 | ✓ 0/10、0/12、0/8 |
| 参考解 | 全通过 | ✓ 10/10、12/12、8/8 |
| 把仓库里 checks 改成永真 | 仍判不通过 | ✓ 三批全 `resolved=False` |

第三关证明"被验收者改不了标准"——评分用的是题库副本，覆盖仓库同名文件。

**决策三：驱动方式定为仿真模式**

用户要求"输入和验收放在 Codex，脚本只做检测与采集"。据此新增 `scripts/sim.py`：

| 子命令 | 作用 |
|---|---|
| `prep` | 从 seed 铺一格仓库 + 初始提交 + 记基线 sha + 落 `GOAL.txt` |
| `goal` | 打印交给 Codex 的原话（需求 + "自己跑验收并贴结论、不得改 checks"） |
| `collect` | 解析会话 token → 取补丁 → **独立复核** → 追加一行（含自报结论 vs 复核结果） |

记录里新增 `claimed`（Codex 自报）与 `units_ok`（复核）：两者不一致时只提示、不改判——
"它说做完了"和"实际做完了"是两件事，这正是要量的东西。

**新增文档**：`docs/冻结规则与仿真模式.md`（冻结规则、变更规则、每格三步、开跑清单）、
`runs/exp/README-INVALID.md`（哪些格不能用、为什么）。

**规则（写死）**：冻结后任何改动都算 `taskset-v2`，v1 的数据不得与 v2 合并；
一次跑批内不许改题、改验收、改 workers、升 codex；发现题错就停批重跑整批，不许"只补跑受影响的那几格"。

### E22 补记　为什么"驱动方式不影响结论"（09:05）

用户要求把这条写清楚，分原理与实验。原理补在这里，实验数据见 E22 正文。

**原理：同一二进制、同一配置，差异只有三处，两处可消、一处必须控制。**

| 差异 | 影响什么 | 处理 |
|---|---|---|
| 系统提示 / 脚手架长度 | 每轮输入的**固定前缀**，与解题无关 | 两臂用同一驱动即抵消（比值不受影响） |
| 工作目录 | 文件定位 | 两边固定到格子；错目录会被"补丁几乎为空"检出 |
| **工具可见性**（`orch` 在不在 PATH） | **会不会去编排** | 必须机制化隐藏，靠人记得不可靠 |

第一条是关键：这 12% 加在每轮输入上，是**常数偏移**，不是"模型做了不同的事"。
实验的因变量是成本比与质量，不是 token 绝对值，所以它不进结论——
**前提是一次跑批内两臂同驱动**。混着用（A 手工、D 机器）才会把 12% 变成系统偏差。

**证据强度排序**（从硬到软）：

1. **补丁逐字节相同**（4,672 = 4,672）——最硬。判据就是"补丁能否过验收"，补丁一样，结论必然一样。
2. **输出 token 差 0.2%**——模型"想多少"没变。
3. 输入 token 差 12.2%——差在前缀长度；折钱只差 5.1%（缓存命中占 91%）。
4. 墙钟差 8.1%——在此量级上与噪声不可分。

**因此定的规则**：一次跑批内两臂同驱动；A 臂由 `exp_lib.orch_hidden()` 隐藏 `orch`，
不依赖"记得停用技能"。这条已写进 `docs/实验六_强制编排_规模阶梯.md` 第 0 节。

#### 四、机制：规模经济属于单会话，编排把它拆掉了

| N | B 每单元输入 | D 每个 worker 输入 | 倍数 |
|---|---|---|---|
| 1 | 524,733 | 512,457 | 1.0× |

B 的每单元输入随 N **下降 16 倍**（52 万 → 3.2 万）：一个会话看到第一个文件时要读一遍仓库，

D 的每个 worker 是**独立新会话**，固定成本约 46 万，N 再大也不摊薄。

**所以在这个任务族上，"编排 + 并行"恰好摧毁了单会话唯一的规模经济。**

> 对**同构批量**（同样的活重复 N 次）这类任务：编排没有规模经济。
> 它的成本是"N × 单会话固定开销"，而单干的成本是"1 份固定开销 + N 份边际"。
> N 越大，编排越吃亏——实测从 2.4 倍拉到 9.5 倍。

这条**不能**外推到跨文件推理、需要先读文档、或单元之间耦合的任务——那类任务里

1. **质量没有区分度**：45 格全部 N/N 通过。三个臂都能做对，这类题对谁都不难。
2. **B（便宜模型单干）在所有规模上都最便宜**，D/B 从 1.9× 一路涨到 15×。
3. **A 与 D 的关系随规模翻转**：N=1–2 时 D 有时更便宜；到 N=16，A 明确更便宜
   （A 单次 0.0022–0.0076/单元，D 稳定 0.0091–0.0106）。也就是说，
   **批量越大，Codex 单干越划算，编排越没有位置**。

**A 的方差是这批数据最大的问题**：每单元从 0.0022 到 0.0972，跨度 44 倍；
同一个 N=8，三次总成本是 $0.3674 / $0.0777 / $0.1059（4.7 倍）。
所以任何「均值曲线」都会被单次极端值带偏——这也是为什么要保留逐次数据。

**与前几篇的关系**
- E23/E24 的 A 数据（sc02–sc16）作废，替换为本条。
- E26 里「D/B 从 2.4× 升到 9.5×」用区间表示为 1.9–15×，方向不变、幅度更宽。
- E24 的「A 在 N=2 特别贵」不再成立：那是 orch 的成本，不是 Codex 单干。

### E28　两条结论：在「不换客户端」前提下编排有价值，且显著降低成本方差（17:15）

由宇嘉提出，用 E27 的 45 格原始数据核验。两条都成立，但都有明确边界。

#### 结论一：以 A（继续用 Codex）为基线，中小批量上编排更便宜

| N | A 中位（每单元） | D 中位 | D/A | D 用的 Codex 额度 ÷ A | 质量 |
|---|---|---|---|---|---|
| 1 | 0.03432 | 0.02005 | **0.58×** | 18% | 全过 |
| 2 | 0.03510 | 0.01494 | **0.43×** | 16% | 全过 |
| 4 | 0.05322 | 0.01261 | **0.24×** | 2% | 全过 |
| 8 | 0.01324 | 0.01028 | **0.78×** | 6% | 全过 |
| 16 | 0.00308 | 0.01042 | **3.38×** | 15% | 全过 |

**读法**：N=1–8 时 D/A 的中位比是 0.24–0.78，即便宜 22%–76%；
同时 Codex 侧额度只用到 A 的 2%–18%。**N=16 是反例**（D/A=3.38），不能外推。
所以准确说法是：「**在中小批量（本次实测 N≤8）的同构任务上，编排在保持客户端不变的前提下降低成本**」，
而不是「批量越大越该编排」。

#### 结论二：编排把成本的不可预测性压掉一大截

| N | A 的 CV | D 的 CV | A 极差倍数（max/min） | D 极差倍数 |
|---|---|---|---|---|
| 1 | 47% | **9%** | 2.60× | **1.19×** |
| 2 | 74% | **26%** | 3.82× | **1.54×** |
| 4 | 65% | **21%** | 5.55× | **1.49×** |
| 8 | 87% | **11%** | 4.73× | **1.26×** |
| 16 | 67% | **8%** | 3.44× | **1.16×** |

A 的三次之间能差 2.6–5.6 倍；D 只差 1.16–1.54 倍。CV 上 D 是 A 的 1/3 到 1/8。

**机理**：两边的不确定性来源不同。
- A 的成本取决于它这次探索多少步——读到什么、要不要回头、几轮才收敛，全是变数；
  同一个 N=8，三次总成本 0.3674 / 0.0777 / 0.1059。
- D 的成本是结构性可算的：`计划（近固定）+ N × 单个 worker 固定开销`。
  worker 的开销由外壳上下文决定，与任务难易基本无关，所以总额稳定。

**这一点对实际使用比「便宜多少」更重要**：可预测才能做预算。
按 A 跑批，你要按最坏情况备额度（约中位的 2–3 倍）；按 D 跑，中位加两成就够。

#### 边界（必须一起写）

1. **规模窗口**：N≤8 实测成立，N=16 反例。窗口上界取决于「A 什么时候学会批量做」，
   本次是 N=8 时 A 已开始摊薄（D/A 从 0.24 回升到 0.78）。
2. **任务形态**：只对同构批量成立。跨文件推理、需要先读文档的任务未测。
3. **样本量**：每格 3 次，CV 本身也不稳（3 次估 CV 误差很大）；方向可信，具体数值别当参数用。
4. **D 仍有残余波动**（N=2/4 时 CV 21–26%）：计划大小与 worker 轮次仍会变，尚未查清来源。

#### 对项目定位的意义

之前把结论写成「编排相对便宜模型单干没有优势」，这句话是对的，但它回答的是

「要不要放弃 Codex」——不是这个项目要回答的问题。
在**继续用 Codex** 这个真实前提下，实测结论是：

> 中小批量的同构任务上，编排把成本降到 Codex 单干的 1/4–3/4，
> Codex 额度只用 2%–18%，质量不变，而且成本波动从 3–5 倍压到 1.2–1.5 倍。

这四条合起来，才是这个项目成立的理由。

### E29　h1（跨文件·需先读约定）九格：假设被否，且暴露一条更一般的规律（18:05）

h1：31 个源文件 / 601 行，5 个领域各 4 层，必须先读 `docs/CONVENTIONS.md`。
三臂各跑 3 次，共 9 格。

| 臂 | r1 | r2 | r3 | 均值 | CV | 通过 |
|---|---|---|---|---|---|---|
| A | $0.1750 | $0.1503 | $0.1768 | **$0.1673** | 9% | 5/5 5/5 5/5 |
| B | $0.0522 | $0.0426 | $0.0335 | **$0.0428** | 22% | 5/5 5/5 5/5 |
| D | $0.2294 | $0.2010 | $0.2190 | **$0.2165** | 7% | 5/5 5/5 5/5 |

**质量：9 格全是 5/5。** 三臂都能做完，h1 没有制造出「B 失败、D 成功」的分歧。

**成本排序：B（$0.0428）< A（$0.1673）< D（$0.2165）。**
D/A = 1.29×，D/B = 5.06×，A/B = 3.91×。**编排在这道题上最贵。**

#### 一、我原先的假设错了

此前的判断是：「跨文件、要先读文档的任务，单会话的『学会一次』不成立，可能轮到编排」。
实测正好相反——**这类任务恰恰是编排最吃亏的形态**。原因在 D 的 token 膨胀：

| | 输入 token |
|---|---|
| A 一次做完 5 个领域 | 486k / 504k / 700k |
| D 的 5 个 worker，每个 | 1164k / 1209k / 1706k / 1316k / 808k（均值 ≈1.24M）|
| D 合计 | 5.8–6.2M，是 A 的 **约 12 倍** |

每个 worker 都要**重新读一遍整个框架与约定**——31 个文件、共享层、CONVENTIONS。
而 A 只读一次，然后在同一个上下文里把 5 个领域都写完。

L 的单价优势是 13 倍，token 膨胀是 12 倍——**两者几乎正好抵消**，
再叠加计划成本，D 就变成了最贵的那个。

#### 二、真正的变量不是规模 N，是「每个单元要读多少共享上下文」

| 任务族 | 每单元要读的共享上下文 | token 膨胀 | 结果 |
|---|---|---|---|
| sc 阶梯（同构小文件） | 几乎为零（只读自己那个文件） | 4.5× | D 比 A 便宜 |
| h1（跨层、需读约定） | 全部（框架 + 共享层 + 文档） | 12× | D 比 A 贵 1.29× |

所以判据不是「N 多大」，而是：

> **单元之间能共享的知识，单会话能一次装下并复用；跨越这道边界去做并行，
> 每个 worker 都要重建一次全局理解，膨胀倍数随「共享上下文 ÷ 单元自身工作量」上升。**

这也解释了为什么之前在同构题上 D 能赢：那些单元彼此不需要知道对方的存在。

#### 三、附带修正：E28 的结论二有边界

E28 说「编排显著降低成本方差」。在 h1 上这条**不成立**：

| 臂 | sc 阶梯的 CV | h1 的 CV |
|---|---|---|
| A | 47%–87% | **9%** |
| D | 8%–26% | 7% |

A 在 h1 上反而很稳（9%）。原因是 h1 的任务边界清楚、收敛点明确，
A 不会在「做到哪算够」上反复试探；而 sc 阶梯的单元小、判据简单，
它有时一次做完、有时反复跑验收，成本就散开了。

**修正后的说法**：编排降低方差，只在「A 自己拿不准做到什么程度」的任务上成立；
任务描述越明确，这个优势越小。

#### 四、还剩下唯一一个可能翻盘的形态

上面所有失败都指向同一件事：**A 的瓶颈不在钱，在上下文容量**。
只要仓库能塞进一个上下文，A 就比「拆开再合并」便宜；
所以编排真正的位置只可能在：**单个上下文装不下**的情形——
仓库规模远超窗口、或任务本身要求在大量互不相关的区域并行探索。

这不是 N 的问题，也不是题型的问题，是容量的问题。要用实验证明它，
得先有一个「装不下」的任务，而我们目前所有题目（601 行～16 个文件）都远未触及。

#### 五、本轮结论（可直接引用）

1. h1 上三臂全过，编排最贵（D/A=1.29，D/B=5.06）。
2. 「跨文件 = 编排的机会」是错的；跨文件恰恰让每个 worker 重复付费。
3. 决定编排成败的是「每单元需读的共享上下文」，不是单元数。
4. 编排降低方差这条，随任务描述清晰度上升而失效（h1 上 A 的 CV 只有 9%）。

### E32　"额度"这个数是怎么来的，准到什么程度（18:25）

用户追问口径可核性，逐层拆开。

#### 一、数据链路（算术上可 100% 复核）

```
codex exec --json  →  turn.completed.usage（provider 上报的 token 计数）
                   →  orch/planner.py parse_json_events() 累加
                   →  trace.jsonl 的 task.usage（逐 worker 一条）/ run.usage（合计）
                   →  exp_runner.orch_usage() 读 trace
                   →  runs/exp/*.jsonl 的 usage / plan_usage
                   → report 与本文的表
```

现场复核（sc08 D r1，trace 75 条事件）：
8 条 `task.usage` 逐条相加 = 3,565,353 输入，与 `run.usage.tokens_in` 完全相同，
与 jsonl 记录的 `usage.input_tokens` 也相同。**没有估算、没有抽样、没有按字符折算**，
每个 worker 的 token 都来自它自己那次 exec 的返回。

#### 二、但口径不对称——这是真问题

| | A 臂的 usage 覆盖 | D 臂的 plan_usage 覆盖 |
|---|---|---|
| 读需求 | ✓ | ✓ |
| 读文件 / 读仓库 | ✓（读到多少算多少） | **✗ 通常一次都不读** |
| 写方案 / 改代码 | ✓ | 只写计划 |
| 跑验收、看到失败再改 | ✓（多轮） | ✗（worker 的活，不占 H） |
| 看报告、复核 diff、`apply` | — | **✗ 实验里由 harness 代做** |
| 与用户多轮对话 | — | **✗ 没有** |

所以 8.5× 是「**D 的规划步**」对「**A 的完整会话**」的比值，**对 D 有利**。
真实用起来 D 的 H 还会涨：看报告、处理 apply 冲突、用户追问、返工。
方向可信，倍数不可当承诺——它是上限，实际会往下走。

b3 那次 1.4M 就是这个偏差的现实版：Codex 一旦"接活"（自己读仓库），
口径立刻从"规划步"变成"完整会话"，优势反转。所以 E31 那条优势成立与否，
不取决于任务，取决于**规划阶段读没读仓库**。

#### 三、token ≠ 额度

订阅额度不是线性 token 计价，是限额窗口里的消耗速度。所以严格说法是
「H 侧 token 消耗」，它是额度的**代理指标**，不是额度本身。
跨模型比 token 也无效（E21 已作废过一版结论），所以只做同侧比较（H 对 H）。

#### 四、可接受的表述

### E33　"不读仓库"到底丢了多少体验，代价多少（18:30，探针实测）

用户追问：这条硬约束体验上丢了什么、要保持代价多大。先做探针再答。

**设计**（`scripts/probe_plan_ctx.py`）：同题面、同模型、同仓库副本，只改规划时的输入

| 变体 | 给 Codex 什么 |
|---|---|
| P0 | 题面 + 文件路径清单（现行硬约束） |
| P1 | 题面 + 清单 + **全仓文件正文拼进 prompt** |
| P2 | 题面 + 清单 + **允许自己 ls/cat/grep 探索** |

结果（各跑 1 次，只规划不执行）：

| 题 | P0 清单 | P1 通读 | P2 自由探索 | P1/P0 | P2/P0 |
|---|---|---|---|---|---|
| h1（31 文件 / 601 行） | 17,976 | 29,204 | 106,528 | 1.62× | 5.93× |
| b3（8 个 loader） | 17,754 | 22,569 | 17,785 | 1.27× | 1.00× |

**关键：三个变体产出的计划完全相同** —— 同任务数、同 writes 集合
（h1 都是 5 个任务 / 20 个文件，b3 都是 8/8 且覆盖参考解全部 8 个文件）。

所以"不读仓库"丢的**不是计划能力**，是别的东西（下面第三节）。

#### 一、1.4M 那次不是"读了一遍"，是"试了 27 次"

拆 `sess-D-b3-r2.jsonl`：**1 个 turn，27 次 PowerShell 命令**，累计输入 1,415,264。
机制很清楚：**每次工具调用都把整个上下文重发一遍**，所以成本 ≈ 命令数 × 上下文大小。

| 行为 | 额外 H 输入 |
|---|---|
| 把全仓正文拼进 prompt（1 次） | +5k ~ +11k |
| 自由探索到出计划（h1，约 6–8 条命令） | +89k |
| 边读边试边改（b3 那次，27 条命令） | +1.40M（80×） |

**结论：代价不是"读不读"的二值开关，是"探索几轮"。** 一次通读几乎免费，反复探索才是灾难。

#### 二、体验上具体丢的五件事

| 丢的东西 | 具体表现 | 有没有实验证据 |
|---|---|---|
| 仓库现状认知 | 只能说"这些文件在"，说不出"这个函数还是占位实现" | 计划未受影响（本题题面写死验收） |
| 失败归因 | 验收挂了，分不清是计划错、判据错还是 worker 错，只能转述报告 | b3 D r1 挂了 4 个单元，报告说不清原因 |
| 多轮指代 | "把这个函数改成异步"——"这个"没有落点，要么用户贴码，要么它去读 | 未测 |
| 可抽查 | 报告"8/8 通过"无法二次确认，用户只能信 | — |
| 责任位置 | Codex 退化成"需求翻译 + 命令搬运"，验收回到用户手上 | — |

最后一条最要紧：**它不是省了额度还保持体验，是换了一种分工。**

#### 三、要保持，四条路线的价格

以 h1 为基准（A 单干 486k–700k，P0 18k）：

| 路线 | 做法 | H 输入 | 相对 A 省 | 体验恢复度 |
|---|---|---|---|---|
| A 通读一次 | 全仓正文拼进 prompt | 29k | 17–24× | 中：知道现状，但不能追问 |
| B 摘要 | 便宜模型先产结构摘要，planner 只读摘要 | ~22k | 22–32× | 低：摘要会失真 |
| C 事后抽查 | 执行完只读 diff | 18k + 3–8k | 15–20× | 中高：能确认改对没 |
| D 自由探索 | 允许它自己 ls/cat/grep | 107k | 4.6–6.5× | 高：接近客户端 |
| E 失败才读 | 正常不读，验收挂了才读相关文件 | 18k / 28k | 17× / 11× | 中：只救异常路径 |
| F 接整件活 | 读+试+改+自测（b3 那次） | 1.4M | 0.5×（更贵） | 完整 |

**A + C 组合（通读一次 + 事后果断抽查 diff）约 32–37k，仍省 15 倍左右，体验接近完整。**
这是目前性价比最高的一条，比现行"一律不读"只贵 1.8 倍，却把前三项体验都补回来了。

#### 四、要改的规则

现行 skill 写的是"禁止读文件内容"，按本探针**过严**：通读一次只 +62%，计划却完全相同。
应改为：**允许一次通读（把正文给全），禁止多轮探索（反复 ls/cat/grep 或边读边试）。**
判据一句话：*如果它需要问第二个问题才能写计划，就该把资料一次给全，而不是放它去翻。*

### E38　决定：放弃饱和实验（20:36）

**决定**：sat 饱和级任务库**停止建设**，不做 sat01–sat06，也不做 81 格矩阵。
设计文档 `docs/饱和级任务库_设计.md` 保留作存档，顶部已标"已取消"。

#### 原因（三条，按权重排）

**一、成本过高。**

不是模型费贵，是**额度窗口撑不住**：

| 事实 | 数字 |
|---|---|
| 探针 4 档（10k / 265k / 492k / 619k）合计输入 | ≈ 1.4M token |
| 结果 | **当日订阅额度打满**，900k 那档直接报 `You've hit your usage limit` |
| 设计估算（81 格） | 模型侧 $25–35，但真实瓶颈是窗口：一次 900k 即打满 |
| 要跑到有统计力（A 的 CV 47–87%，n 需 ≥15） | 单档就要 45 格以上，跨天分批也跑不完 |

一句：**这套设计在订阅制 + 单人操作下，物理上跑不完**，不是预算问题。

**二、条件受限。**

- Codex 的 500k 是**客户端配置**，`max_context_window` 872k，模型对外宣称 1.05M；
- 而实测 619,498 已被完整吃下并正确召回，说明 500k 不是墙；
- 真正的墙（如果存在）在 872k–1.05M 之间，**而 900k 那档先撞到额度**，再往上测不了；
- 探针本身还有缺陷：针在 25%/75%，即使被截到 500k 也仍在窗内，需放到 98% 才判决性——这一轮也没跑成。

**测不到墙，就设计不出"必须超墙"的题**：sat03–sat06 的档位全靠推断，等于把结论建在未验证的前提上。

**三、无力开展。**

| 项 | 规模 |
|---|---|
| 单题生成 | sat06 需 1,280 个文件 / 102,400 行 |
| 矩阵 | 81 格，高档位单格 10–20 分钟 |
| 约束 | 每小时只能跑几格，且受额度窗口截断；每题还要冻结校验、双向自检、分段解自检 |

在"一个人 + 订阅制 + 一台机器"的条件下，这不是一个能收口的实验。

#### 保留什么

1. `docs/饱和级任务库_设计.md` 全文（含六档规模表、四关验收、预注册判据）；
2. E37 的探针数据与"500k 不是墙、额度才是"的结论；
3. 结论边界里那句必须保留的话：**容量假设既未被证实，也未被证伪**——现有最大题 h1 仅 1.2 万 token，离墙差 20–80 倍。

#### 如果将来要恢复，先满足两个前置

| 前置 | 说明 |
|---|---|
| 计费方式 | A 臂改用按量 API key，不受订阅窗口限制；否则加量无从谈起 |
| 窗口定位 | 98% 尾部针 + 872k/1.05M 两档，先把墙定出来，再定题目规模 |

#### 备选（更便宜的替代路径，未采纳、未验证）

不必靠"绝对规模"制造饱和，可以靠**任务结构**：全局唯一序号 + 跨域汇总 + 干扰项，
把必需读取量压到 **60–120k**，用"局部看不到全局就算错"制造难度，而不是用十万行。

### E40　定位：文档题 D 失败不是能力问题，是 E007 + 计划形态（21:40）

**结论先行：E39 的"D 在文档题上更差"作废，是题目/校验器接口造成的假象。**

#### 一、失败链条（三层，逐层有证据）

1. **直接原因**：`plan_diag` 里 6 个任务全是 `E007 goal 含并列标记 '；'`。
   原因在 `orch/contract.py:328`：E007 是**纯字符串包含检查**，goal 里出现 `；` 就判"复合任务"。
   文档题天然要在 goal 里罗列 5 条格式要求，planner 连续两轮都写成
   「…；所有条款使用专属 CODE…」，两次 validate 都失败 → `plan_for` 返回 None → 该格 `resolved=None`。
2. **次级原因**（每次规划多花一轮）：即使 E007 过了，第一版判据会写成
   「文件断言：…条款编号依次为 R-API-01、R-API-02、R-API-03。」——
   E014 要求断言里含可判定谓词（返回/含/等于/退出码），这版没有，必被拒，第二轮才改对。
   代价：规划从 1 轮变 2 轮，H 侧 17.9k → 81.6k（4.6×）。
3. **结构原因**：计划形态决定成本。修复后三次 `turns` 全是 1——
   planner 只拆 1 个任务、一个 worker 改完 6 份文档；而修复前成功的两次 `turns=6`，
   6 个 worker 各付一次底座，worker 侧 3.7M–4.1M。**同一道题，D 的成本在两个形态间差 5 倍。**

#### 二、修复动作

`scripts/exp_runner.py` 的 `PLAN_PROMPT` 增加一条：

> goal 必须是一句话、一个动词：不许出现「；」「然后」「同时」「以及」这类并列标记。

注意：该 prompt 同时用于代码题，**改变后续实验的计划风格**；已完成的数据不受影响。

#### 三、修复后重跑（`runs/exp/docs_fix.jsonl`）

| 次 | 通过 | 成本 | 计划输入 | worker 轮数 | worker 输入 |
|---|---|---|---|---|---|
| r1 | 是 | $0.0736 | 81,629（2 轮，E014 返工一次） | 1 | 638,256 |
| r2 | 是 | $0.0255 | 17,871（1 轮） | 1 | 493,053 |
| r3 | 是 | $0.0320 | 18,420（1 轮） | 1 | 834,172 |
| 均值 | **3/3** | **$0.0437** | 39,307 | — | 655,160 |

**D/A = 0.68×（编排更便宜），D/B = 4.60×（仍输）。**
与修复前的 1.72× / 11.58× 完全翻转——差别全部来自"计划能不能一次写对"和"拆不拆"。

#### 四、可以留下的三条

1. **E007 是代理指标，对文档类误伤**：`；` 不等于复合任务。修 prompt 比修校验器便宜，
   但如果以后接文档类需求常态化，应考虑把 E007 从"纯字符串"改成"分号且动词数 >1"。
2. **E014 的失败是可预测的**：planner 第一版总把格式检查写成没有谓词的"文件断言"。
   在 prompt 里给一个正确示例（`文件断言：docs/x.md 含 \`R-API-01\``）能省掉这一轮返工，
   价值约 60k H token/次。本轮没做，留作下一项。
3. **D 的成本下界 ≈ B + 计划费**：当 planner 不拆时，D 的执行 ≈ B，多出来的就是计划费。
   文档题上计划费（17.9k ≈ $0.014）已接近 B 的任务成本（$0.0095），所以 D/B 下不去。
   **这是结构性的，不是调优能解决的。**

### E43　让 Codex 能"负责"：retry + 授权边界 + 责任声明（23:30）

用户要求："我需要 codex 能对这个项目负责"。拆开是三层能力：定判据（有）、验结果（E42 补证据）、
发现不对能改（**原来完全没有**——orch 只有 apply/undo/cleanup/cancel/answer，没有局部返工）。

#### 一、新增 `orch retry`

```bash
orch retry <run_dir> --tasks t03
orch retry <run_dir> --tasks t03 --plan fix.json   # 改判据时传一份只含该任务的计划
```

设计取舍：**不做"原地重跑"，而是新起一次小运行**。原因：orch 只在整层通过后合并，
失败层的改动不在用户仓库里，原地打补丁会基于错误基线。新 run 保留旧 trace/diff，可直接对比。
每次 retry 落一份 `retry-<ts>.json`，记录重跑了哪些任务、判据改前改后。

#### 二、授权边界（已写进 skill，两处同步）

| 项 | 授权 | 理由 |
|---|---|---|
| A 自行返工 | **1 次** | 一次能救回机械失败，成本 +$0.02–0.08；两次以上就该人判断 |
| B 改判据 | **可改，必须报备** | 判据=验收标准，偷偷放宽等于作弊；E014 类失败本来就是判据写错 |
| C 自己下场改代码 | **不许** | 一开就退化成 A 臂，"省额度"的前提消失 |

#### 三、汇报必须说清验证边界

固定三行：`我验证了 / 我没验证 / 剩余风险`。只报"8/8 通过"是不够的——
判据没覆盖的地方，Codex 并没有验证。

#### 四、端到端实测（顺带证明证据行有用）

对第一批失败 run 执行 retry（`20261111-205217-3092` → 新 run `20261111-231612-a0ac`）：

- 命令正常识别出未完成的 t01，新起 run、旧证据未动；
- 结果仍失败（exit=4），但**证据行直接给出真因**：

```
  FAIL  t01  114.2s  6 文件 · +96 −84 · 未过 7 条
        验收 0/7 通过
        ✗ python checks/check_api.py 退出码 0  [rc=2]
          …python.exe: can't open file '…\checks\check_api.py'
```

`rc=2` + "can't open file" 说明**仓库里没有 checks/**（第一批题库的缺陷），不是 worker 做错。
没有这两行，报告只会说"未过 7 条"，人和模型都会误判。

#### 五、对实验数据的影响

`retry` 是**新运行**，不改既有 run 的任何数值；但它是新的行为变量——
一旦 Codex 在真实使用里自行返工，D 的成本就会高于现有实验值。
所以：**现有 D 数据不含 retry**，引用时要注明"单次执行、不返工"。
若要测"会返工的 D"，应作为 D2 形态单独跑，不与现有数据混算。

### E44　D2 首组：返工一次的代价（23:40）

**D2 定义**：D + 一次返工。做法是在第一轮计划里**注入一条写错的判据**
（`check_api.py` → `check_api_typo.py`，必然 `rc=2`），复现"判据写错"这种最常见的失败；
第一轮失败后用**原计划**（正确判据）再 dispatch 一次，取第二轮的产物评分。
成本 = 两轮之和，计划只算一次。

| 次 | 第一轮过 | 返工触发 | 返工后过 | 成本 | 墙钟 | 总输入 token |
|---|---|---|---|---|---|---|
| r1 | 否 | 是 | **否** | $0.0826 | 202s | 4.20M |
| r2 | 否 | 是 | 是 | $0.1216 | 381s | 7.85M |
| r3 | 否 | 是 | 是 | $0.1357 | 405s | 7.89M |
| 均值 | 0/3 | 3/3 | **2/3** | **$0.1133** | **329s** | 6.65M |

#### 与 D、A、B 并列

| 形态 | 通过 | 成本 | 墙钟 | D/A 钱 | D/A 时间 | D/B 钱 |
|---|---|---|---|---|---|---|
| A（Codex 单干） | 3/3 | $0.0642 | 64s | — | — | — |
| B（ds 单干） | 3/3 | $0.0095 | 95s | — | — | — |
| D（单次执行） | 3/3 | $0.0782 | 177s | 1.22× | 2.74× | 8.21× |
| **D2（含一次返工）** | **2/3** | **$0.1133** | **329s** | **1.76×** | **5.14×** | **11.93×** |

#### 三条结论

1. **"负责"是有价格的**：一次返工让 D 从"贵 22%"变成"贵 76%"，时间从 2.7 倍变 5.1 倍。
   这是复核/返工成本第一次被量化——约 **+45% 金额、+86% 时间**。
2. **返工不等于救回**：3 次里只救回 2 次。最坏那次（r1）花了 $0.0826、没过，
   比 D 单次（$0.0782）还贵且更差——**返工是有风险的支出，不是保险**。
3. **对 B 的劣势进一步扩大**：D2/B = 11.93×。说明"用便宜模型单干"这条基线，
   编排再怎么补也追不上；返工只会把差距拉大。

### E45　返工机制的整体效益 + 路由判据与预实验设计（23:50）

#### 一、先补一条结论：返工机制在"整体效益"上成立

不是"单次有比没有强"，而是**机制按需触发，所以与失败概率无关**：

- 不触发时成本 = D（零额外开销）；
- 触发时期望挽回 = `救回率 × 失败损失 − 返工成本`。

代入本轮数据（r = 2/3、c_r = $0.035）：

| 场景 | 失败损失 L | 每次失败净收益 |
|---|---|---|
| 文档题（重跑一次 $0.064） | $0.064 | **+$0.008**（几近持平） |
| 中型代码任务 | ≈ $0.2 | +$0.10 |
| 大任务 / 对外交付 | ≥ $1 | **+$0.6** |

结论：**机制本身成立；净收益随任务价值上升**。若把"人来接手"（5–15 分钟）折算进去，
L 远高于阈值 $0.053，机制在任何任务上都是净收益。

三个前提：按需触发（不是每轮都跑两遍）、最多 1 次、失败必须上报。
缺一个，结论翻转。

#### 二、是否需要编排：判据（派发前可估）

| 编号 | 判据 | 阈值 | 依据 |
|---|---|---|---|
| C1 | 可拆出的独立交付单元数 k | **2 ≤ k ≤ 8** | k=1 计划费吃掉收益（D/A 时间 1.36–1.40×）；k≥9 底座 ×N 反噬（sc16 2.34× / 4.34×） |
| C2 | 每个单元的预期读取量 R | **R ≥ 46k token**（≈1.6 万汉字 / 500 行代码） | worker 固定底座约 46k；R 低于它时确定性地亏（docset1 每单元 24k → D/A 1.22×） |
| C3 | 单元之间是否共享全局上下文 | **不共享** | h1 每个 worker 重读 31 文件约定 → D/A 1.29×，token 膨胀 12× |
| C4 | 判据能否机器判定 | **命令 / 文件断言** | 判据不可判定 → E014 返工，计划费 17.9k→81.6k |
| C5 | 失败损失 L 是否 > 返工成本 | **L > $0.053** | 否则返工不划算（E44） |
| C6 | 用户是否受额度约束 | **订阅制 → 额度优先** | 额度省 5–37×，即使金额贵 22% 也可能值 |

C1–C4 全部满足、且（C5 或 C6 至少一条）成立 → **走编排**。
任一条不满足 → **自己单干**（并把这次判断记进 bypass）。

#### 三、为什么"路由"值得做：一条能算的结论

设任务集中需要编排的比例为 q，路由准确率 a，`c_D > c_A`（不该编排的任务上编排更贵）：

- 硬性编排成本 ≈ `c_D`
- 路由成本 ≈ `a·(q·c_D + (1−q)·c_A) + (1−a)·(q·c_A + (1−q)·c_D)`

**路由优于硬编 ⟺ a > 0.5。** 只要判据准确率过半，路由就赢——与 q 无关。
这是路由实验唯一需要证明的事：**判据的判对率能不能过 50%**，而不是"路由能比最优更好"。

上限也要说清：oracle（每题选最优）是下界，路由永远不可能优于它。

#### 四、分散任务集设计（`tasks/router1`，待建）

| 组 | 任务形态 | k | 每单元读取 | 应该编排？ | 用途 |
|---|---|---|---|---|---|
| R-yes | 4 个独立模块各 400 行，互不引用 | 4 | ≈60k | **是** | 路由该说"走" |
| R-no-short | 6 篇短文档，每篇 40 行 | 6 | ≈8k | **否** | C2 不满足（底座 > 工作量） |
| R-no-one | 单文件 30 行改动 | 1 | ≈8k | **否** | C1 不满足 |
| R-no-shared | 4 个模块共享一份 CONVENTIONS | 4 | ≈80k | **否** | C3 不满足 |

每组三臂（A/B/D）× 3 次；第四臂 R（模型自选是否编排）留到判据验证后再上。

采集字段（每条记录）：`arm / task / rep / 是否编排（orch_called）/ wall / usage_h / usage_worker / cost / resolved / 路由决策与理由`。

#### 五、预实验（先做两个，验证判据方向）

| 任务 | 设计 | 预期 |
|---|---|---|
| P1（该编排） | R-yes 缩到 k=4、每单元 400 行 | D/A 0.3–0.6，额度 5–30× |
| P2（不该编排） | 单文件 30 行改动 | D/A 1.5–3，时间 1.3–2×，额度仍省但无意义 |

判据验证方式：**若 P1 落在 D/A < 1 且 P2 落在 D/A > 1，则 C1–C3 的方向被支持**；
若 P1 也 > 1，说明阈值定错了（R 或 k），应先改判据再测路由。

预实验成本：2 组 × 3 臂 × 3 次 ≈ 18 格，约 $1.5–2、1 小时。

#### 三、结论一：预注册的预测只对了一半

预期 P1(该编排) D/A<1、P2(不该编排) D/A>1。实测 **P1 0.14×（强成立）、P2 0.43×（也 <1）**。

A 的固定成本太高——51 行文件的单文件小改，A 仍花了 95k 输入 token / $0.0355，
而 D 只花 18k 计划 + 一个缓存命中率极高的 worker。

#### 四、结论二：k=1 时 D 的成本恒等式成立（这是本轮最有用的一条）

| 题 | B 均值 | + 计划费 | 预测 | D 实测 | 误差 |
|---|---|---|---|---|---|
| r1no1 | $0.0047 | $0.0113 | **$0.0160** | **$0.0154** | −4% |

**k=1 时 D ≈ B + 计划费**，与 E41 的推断一致，现在有实测支撑。
k=4 时多出 (k−1) 个 worker 的边际开销：$0.0253 → $0.0427，每个 worker ≈ $0.005。

推论：小任务上**真正的分界线不在 A 与 D 之间，而在 D 与 B 之间**。
D 比 A 便宜是常态，但它比 B 贵 3.3 倍——而 B 的产物质量在本题上与 A、D 相同（3/3 全过）。

#### 五、结论三：额度优势随单元数放大，且很陡

r1yes 的 A 读 248k–2.44M，D 计划恒定 17,979 → **80.9 倍**（历史最高，之前中位 8.5×）。
r1no1 只有 5.5 倍。差别来自 A 在 1,488 行仓库上反复读，而 D 的计划长度与仓库大小无关。

#### 六、一个必须更正的旧笔误：worker 底座不是 46k

E39/E41/E45 里写的"worker 固定底座 ≈46k"是**单位写错了**（万 → k）。
实测 192 个 worker 的累计输入：min 171,463 / 中位 **542,061** / max 1,706,454。

但它对成本的影响没有旧文说的那么大，因为 **90%+ 是缓存命中**（$0.003/M）：
每个 worker 的**边际成本 ≈ $0.005**，而不是 0.5M × $0.15 = $0.075。

所以正确的说法是：
- worker 读得很多（中位 54 万 token），但绝大多数是重复读的上文，按缓存价计费；
- 决定 D 成本的是 **计划费 + 0.005 × N**，不是"单元要读多少"。

#### 七、对路由判据的修正

| 旧判据 | 判定 | 修正 |
|---|---|---|
| C1 k=1 不该编排 | **证伪（金额口径）** | k=1 时 D 仍比 A 便宜 57%，只是不省时间（1.02×） |
| C2 R≥46k | **口径错误** | 改为"单元数 k 与单元规模共同决定幅度"，不决定符号 |
| C3 共享全局上下文 | 保留 | h1 仍然输（1.29×） |
| C4 判据可机器判定 | 保留 | docset1 首批两轮全挂就是它 |
| C6 额度约束 | 保留 | r1yes 80.9×、r1no1 5.5× |

**新的判断顺序**（不是"能不能省钱"，而是这三问）：

1. **会不会更慢？** k=1 或单元极短时 D 不快（1.02–1.36×），文档题甚至 2.74×。时间敏感就别编排。
2. **愿不愿意接受 B？** 若 B 的质量可接受，D 恒比 B 贵 3.3–3.6 倍，直接单干。
3. **单元是否共享全局、是否超过 8 个？** 是则编排翻负（h1 1.29×、sc16 2.34×）。

- **金额**按 `config/prices.json` 折算。gpt-6.1-sol 无峰谷差；deepseek-flash 高峰（UTC 周一–五 01–04、06–10）翻倍，
  所以 D 的 worker 侧和 B 臂在高峰贵一倍，**A 不受影响**——这会让 D/A 的比值随时段摆动 1.3–1.7 倍。

#### 两条必须一起说的读法

1. **金额会随时段翻符号。** h1 在高峰 1.29（D 贵 29%），在空闲 **0.84（D 便宜 16%）**；
   sc16 高峰 2.34、空闲 1.37。**"h1 全输"是高峰价下的结论，空闲价下不成立。**
   之前 E29/E31 里写的"h1 输 1.29×"应标注为"高峰档口径"。
2. **额度不受峰谷影响**，只取决于 A 读了多少：从 0.253（docset1）到 0.012（r1yes），跨 20 倍。
   它和金额不是同一个方向——docset1 金额最差（1.81）、额度也最差（0.253），
   而 sc16 金额最差（2.34）、额度却只要 0.092。**两个口径要分开记，不能互相替代。**

### E50　成本核算进报告：额度 + 金额，试验模式真跑对照组 A（10:15）

#### 一、做了什么

| 文件 | 作用 |
|---|---|
| `orch/costing.py` | 价格/峰谷、形态查表、核算与渲染（额度用 D/A，金额带正负号） |
| `orch/control_arm.py` | 对照组 A：clone 仓库、隔离 orch skill、跑一次 `codex exec`、返回实测用量 |
| `scripts/make_baseline.py` | 从历史 jsonl 生成 `config/baseline.json`（11 个形态签名） |
| `orch/dispatch.py` | 执行前跑对照组；`_render_done` 末尾追加「成本核算」块 |
| `orch/cli.py` | `orch control-arm on|off|status` |
| `skill/SKILL.md` | 要求转述成本块；出现「试验模式」必须原样提醒并可关闭 |

报告块长这样（真实运行输出）：

```
## 成本核算
  A 对照（实测）   78,082 token · $0.0368
  对照耗时         38s
  本次 D           17,972 token（H 估计） + 539,358 token（执行） · $0.0207
  估计节省         额度 77.0%（D/A 0.230）· 金额 +$0.0162（省 44%）

  ⚠ 当前为试验模式：每次多跑一次对照组 A（本次 +$0.0368、+38s）。真实运行时请让我关闭对照组（`orch control-arm off`）。
```

关掉对照组后自动走题库基线：

```
  A 基线（高，n=3） 95,341 token · $0.0298
  ...
  对照已关闭：A 的数字来自题库基线，不是本轮实测。
```

#### 二、试运行实测（`r1no1`，D 臂各 1 次）

| 模式 | 墙钟 | D 成本 | A 的取值 | 节省（额度/金额） |
|---|---|---|---|---|
| 对照组开 | **115.5s** | $0.0207 | 实测 78,082 token / $0.0368 | 77.0% / **+$0.0162（省 44%）** |
| 对照组关 | **46.9s** | $0.0162 | 基线中位 95,341 token / $0.0298 | 81.1% / +$0.0136（省 46%） |

- **对照组的价格：+68.6s、+$0.0368**（本题 A 比 D 还贵，所以开一次对照就多花一份 A 的钱）；
- 两条路径给出的方向一致（都是省 44%–46%），说明基线表可用；
- 与历史实验对照：实验口径 r1no1 D/A 金额 0.43、额度 0.181；本次实测 0.55、0.230 —— 同量级。

#### 三、修掉的一个算法错误

第一版把 H 侧 17,973 token 按全价（$2/M）算，得出「D 比 A 贵 52%」——**方向反了**。
实际计划输入里 76% 是缓存命中（历史 13,696/17,969），折价后 H 只花 $0.010 而不是 $0.036。
修正后结论回到「省 44%」，与实验一致。**这条必须记：H 侧不打缓存折扣会系统性冤枉编排。**

#### 四、影响评估（实测值，不是估计）

| 对象 | 影响 |
|---|---|
| 已有实验数据 | **零**——`exp_runner` 里显式 `ORCH_CONTROL_ARM=off`，实验永远不跑对照组 |
| 真实使用（默认开） | 每次 **+1 次 A 的运行**：小题 +$0.03/+40s，大题可能 +$0.3/+6min |
| H 额度 | 报告多 6 行，约 +150~250 token（占 18k 计划的 1–2%） |
| 工作区 | 无污染：A 在临时 clone 里跑，skill 临时挪走再还原（已核对无残留） |

#### 五、三条已知限制（报告里也标着）

1. **H 侧是估计**：orch 是子进程，看不到 Codex 会话的真实用量；17,800 是历史中位底座 + 计划文件长度。
2. **对照组只跑一次**：A 的 CV 是 40%–63%，一次对照给出的是「这次 A 会花多少」，不是分布。
   所以试验模式下的节省**不能当统计结论**，只能当这次运行的对照。
3. **基线只认三种形态**：k / 单元行数档 / 是否共享。形态不匹配时按同 k 外推并降信心，k 超范围直接不报。

### E52　改判：共享上下文不再一票否决（11-12 20:20，用户决定）

#### 一、改了什么

原判据 C3 是「单元之间共享全局上下文 → 不该编排」。今天改成：

> **共享仍然编排。** 共享影响的是时间，不是金额。

依据是同批消融里那两格：

| 形态 | 金额 D/A | 时间 D/A | 额度 D/A |
|---|---|---|---|
| r2shared（4×382 行 + 共享 `CONVENTIONS.md`） | **0.30×**（省 70%） | 1.03×（打平） | 0.047 |
| h1（5 领域 × 4 层，共享 31 文件约定） | **0.77×**（省 23%） | 1.65×（慢 65%） | 0.116 |

两格的共同点：**金额一直是省的，翻的只有时间**。原来的判据把"时间优势消失"写成了
"不该编排"，等于因为不快而放弃省钱——在真实项目里几乎每个需求都带一点共享约定，
这条判据会把大部分本该省的任务挡在门外。

#### 二、为什么当时会判错

E48 的结论里写的是「C3 在单变量下成立」——这句本身没错（共享确实把 D/A 从 0.14 抬到 0.30）。
错在把它**升格成一票否决**：成立的是"优势缩小"，不是"优势消失"。
这是把一个连续量当成布尔量用了。

#### 三、判据的最终形态

| 问题 | 否定条件 | 说明 |
|---|---|---|
| 规模 | N=1 或 N≥9 | N=1 省但必慢；N≥9 贵 |
| 判据 | 写不成命令/文件断言 | 会返工，计划费 17.9k→81.6k |
| 是否接受单模型 | 接受 → 不编排 | D 恒比 B 贵 2.7–11.1× |
| 时间卡不卡 | 卡且单元短 → 不编排 | 41 行 × 4 那种：省 63% 但慢一倍 |
| **共享上下文** | **不构成否定** | 只影响时间（1.0–1.7×） |

#### 四、影响面

- `skill/SKILL.md`：description 与"什么时候用"两处（这是真正决定 Codex 行不行动的地方）
- `README.md`：第三节判据表、第七节边界表
- 实验数据不变，本条目只是**解释口径**的变更

#### 五、要补充说明的

h1 那格（0.77× / 1.65×）现在在 README 里归入"仍该编排但有代价"，不再是"反例"。
如果以后出现"共享且时间敏感"的任务，应走第四问（时间卡不卡），而不是回到"共享就不编"。
