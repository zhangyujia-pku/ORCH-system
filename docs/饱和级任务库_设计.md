# 饱和级任务库（sat v1）设计

> **状态：已取消（2026-11-11 20:36）。** 设计保留作存档，不再建题库。
> 取消原因见 `docs/实验日志.md` E38：成本过高、条件受限、无力开展。
> 若将来恢复，先解决计费方式与窗口定位两个前置条件。

> 目的：检验"编排的价值出现在**单个上下文装不下**的场景"这条唯一未被证伪的假设。

## 一、事实基础

### 1.1 窗口（可核）

| 项 | 值 | 出处 |
|---|---|---|
| Codex 客户端 `gpt-6.1-sol` | `context_window 500000`，`max_context_window 872000` | 本机 `~/.codex/models_cache.json`（模型元数据，可 `grep context_window` 复核） |
| `gpt-6.1-sol` 对外宣称 | 1.05M | 第三方模型库（AIVerso / LLMPodium） |
| `deepseek-flash`（= V4.1-Flash） | 1,048,576 输入 / 393,216 输出 | 本机 `workers.json` 已记录；DeepSeek V4 Flash 指南（0731 契约，架构未变） |

**第一条推论：Codex 的 500k 是客户端配置，不是模型上限。**
所以"A 超窗"这件事可以被 `-c model_context_window=...` 改掉。实验必须固定该值并写进每条记录，
否则 A 的失败无法区分是能力墙还是配置墙。

> **实测更正（19:39，探针已跑）**：`codex exec` 单轮在 **619,498 输入 token** 下正常完成、
> 答案正确，且事件流里**没有任何 compact 事件**。也就是说 `context_window 500000` 在 exec 路径上
> **不是硬截断线**。真正的位置要往 872k（max_context_window）/1.05M（模型宣称）去找。
> 详见 `docs/实验日志.md` E37。

### 1.2 为什么不能按"窗口"设档：有效上下文远小于窗口

| 研究 | 结论 | 出处 |
|---|---|---|
| RULER（NVIDIA, COLM 2024） | 有效上下文 ≈ 宣称值的 **50%–65%**；多跳推理与代码更低 | arXiv 2404.06654 |
| Chroma "context rot"（18 个模型） | **每增加一段长度都在掉**，不是只在接近上限时掉；1M 模型 ~50k 即可测出衰减；安全有效区常为宣称值的 1/4–1/10 | research.trychroma.com/context-rot |
| BABILong（NeurIPS 2024） | 模型实际只用到上下文的 **10%–20%** | arXiv 2406.10149 |
| NoLiMa（ICML 2025） | 13 个宣称 ≥128K 的模型里，11 个在 **32k** 就掉到短上下文基线一半以下 | arXiv 2502.05167 |
| Du et al.（EMNLP Findings 2025） | **即使检索完美**，仅长度增加就让准确率掉 13.9%–85% | 论文（编号未核，经 S18 综述转引） |
| 生产实践建议 | 可靠工作上限取宣称值的 **25%–30%** | 多篇 2026 综述一致口径 |

按此折算，本实验两臂的**真实可用区间大致是 Codex 125k–325k、ds 250k–650k**。
这个区间本身是**待测量**，不能拿来当设题依据——否则就是预设结论。

### 1.3 两家已知的长上下文短板（会污染实验的部分）

| 现象 | 数字 | 出处 |
|---|---|---|
| DeepSeek 分块 KV 压缩导致**固定相位盲区** | 位置间准确率落差：原版 Flash **40.2%** → 0731 **19.1%** → Pro-0813 **14.8%** → **V4.1-Flash 6.1%** | 第三方复现（字节），中文技术媒体转述 |
| DeepSeek 各 build 的 MRCR 1M 差异极大 | 原版 Flash **37.5%**、Flash-0731 **78.7%**、Pro-0813 **83.5%** | BenchLM 汇总（厂商自测数据） |
| V4-Flash-0731 在召回密集任务上很差 | MLCR **13.3%**，AA-Omniscience −14.3（不幻觉率 8.3%） | ARMES 模型页（第三方评） |
| Sol 线在 512K–1M 明显掉队 | GPT-5.6 Sol MRCR v2：256–512K **91.5%**、512K–1M **73.8%**；Astra 才是 100% / 96.3% | OpenAI 自测（多家转述一致） |
| `gpt-6.1-sol` 自身分档成绩未公开 | 只有综合值：MRCR v2 ≈94、AA-LCR 83.0、MLCR 38.3% | 第三方榜单（LLMPodium / OrcaRouter / BenchLeader） |

**第二条推论：不能引用 Astra 的长上下文能力来设计题目**——我们用的是 Sol 线，
而 Sol 线在 512K 以上已经掉到 74%。断点必须自己测。

**第三条推论：DS 的位置盲区必须被控制**，否则"B 在某档挂了"可能只是关键信息落在了盲区相位上。

## 二、设计原则

| 编号 | 原则 | 理由 |
|---|---|---|
| P1 | **不预设断点，用几何阶梯扫描** | 有效上下文是待测量（1.2 节）；按 500k/1M 设档等于把厂商数字当结论 |
| P2 | **饱和 = 必须同时持有，不是"读得多"** | 仓库再大也能 grep、能分次 cat；只有"局部看不到全局就算错"才是硬墙 |
| P3 | **断点必须可归因**：长度 vs 题型 | 需要同规模的检索型对照，否则无法区分"长度导致"和"任务要求同时持有导致" |

## 三、题库结构

### 3.1 生成器

```
scripts/make_sat.py --kind agg|ret --domains 1|2|4|8|16|32 --files-per-domain 40 --seed N --render py|md
```

一个领域 = 40 个文件 × 80 行（≈ 3,200 行 ≈ 27k token）。
**档位只改 `--domains`**，因此六档同构：

| 档 | 领域数 | 文件数 | 行数 | ≈token | 记录数（data 版） |
|---|---|---|---|---|---|
| sat01 | 1 | 40 | 3,200 | 27k | 550 |
| sat02 | 2 | 80 | 6,400 | 54k | 1,100 |
| sat03 | 4 | 160 | 12,800 | 109k | 2,200 |
| sat04 | 8 | 320 | 25,600 | 218k | 4,400 |
| sat05 | 16 | 640 | 51,200 | 435k | 8,800 |
| sat06 | 32 | 1,280 | 102,400 | 870k | 17,600 |

token 换算基准：**≈8.5 token/行**（h1 实测 9.3、b3 实测 7.5，取中）。

### 3.2 两种渲染，覆盖非代码场景

同一份逻辑，`--render py` 出 Python 模块，`--render md` 出规格文档 / 表格行
（每条记录 5 行、字段固定）。**两版共用同一答案指纹生成器**，用来回答
"结论是不是只在代码上成立"。

### 3.3 两种题型

| 题型 | 任务 | 为什么能强制全读 | 输出规模 |
|---|---|---|---|
| **agg**（主型） | 每个文件/记录带一个局部键，要求按全局规则算出**全局唯一序号**并写回各自位置；同时给出一份跨领域汇总校验值 | 任何局部都看不到别人的键，序号依赖全序；漏读一个文件全序就错 | 输出极小（一个校验值 + 写回文件） |
| **ret**（对照型） | 在同样长度里定位 N 处指定条件的位置，输出坐标列表 | 只考察检索，不要求同时持有 | 小 |

agg 的验收设计成**全序 + 汇总双判据**：既查"序号是否全序正确"，也查"汇总值是否对"。
这样"只读一半"必然两项都错，不会侥幸通过。

### 3.4 位置盲区控制（针对 1.3 节的 DS 缺陷）

- 每个关键事实在 **≥3 个相位**冗余出现（同一键值在多处可交叉验证）；
- 冗余位置由 seed 决定，跨 3 次重复用不同 seed；
- 记录 `seed` 与"关键键落在哪些偏移"，事后可判断失败是否集中在盲区相位。

不做这一条，sat05/sat06 上 B 的失败无法与容量墙区分。

## 四、验收（四关，沿用三关加一关）

| 关 | 内容 | 排除什么 |
|---|---|---|
| 1 | 空补丁 → 0 通过 | 判据太松 |
| 2 | 参考解 `ref/` → 全过 | 题坏了 |
| 3 | 篡改仓库内 checks → 仍判不过 | 自证式验收 |
| 4 | **分段解必败**：写一个"只读前一半文件就作答"的假解 → 必须判不过 | **证明"必须全读"，这是 sat 库的立库之本** |

第 4 关是新增的关键：如果分段解也能过，说明题目没有强制同时持有，整库作废。

## 五、实验矩阵

| 组 | 设计 | 格数 | 作用 |
|---|---|---|---|
| 主组 agg | 6 档 × 3 臂（A/B/D）× 3 次 | 54 | 找断点、比谁先断 |
| 对照组 ret | 2 档（sat01、sat05）× 3 臂 × 3 次 | 18 | 证明断点来自"必须同时持有"而非长度 |
| 场景组 agg-md | 1 档（sat04）× 3 臂 × 3 次 | 9 | 证明结论不只适用于代码 |

合计 81 格。三臂定义不变（A=Codex 端到端、B=ds 端到端、D=Codex 规划+ds 执行，强制编排）。

### 控制变量（全部写进记录）

- `model_context_window = 500000`（固定，不随档位改）；
- reasoning effort `high`；温度与超时不变；
- A/B 臂 `orch_hidden`（含技能目录，`which` 校验）；
- 同一 `seed`、同一 `checks`、冻结哈希校验后才写入结果；
- 记录：档位、domain 数、seed、必需读取量、patch 字节、四项 usage（H/worker/total/turns）、墙钟、通过明细。

## 六、预注册判据（先写死，防事后解释）

1. **容量假设成立**：存在档位 L，使 A 通过率 < 3/3，且 D = 3/3，且 B ≤ A。
2. **容量墙对全体成立**：A 与 D 同档同降 → 编排无独特价值，是"所有单会话模型的墙"。
3. **断点归因**：若 ret 型在各档不降、agg 型在 240k–480k 段崩 → 断点由"必须同时持有"决定，不由长度单独决定。
4. **成本口径**：同时记 H 侧 token 与折算金额；N 越大 D 的 worker 固定底座（≈46k/单元）会放大，需单独列出。
5. **失败形态记录**：Codex 超窗时是硬报错、自动 compact、还是静默截断——逐格记录，不合并成"失败"。

## 七、前置探针：已跑，结论见下

**目的**：Codex 超窗是硬报错 / 自动 compact / 静默截断。脚本 `scripts/probe_ctx_limit.py`，
针埋在 25% 与 75% 位置，要求模型原样输出。

| 目标档 | 实测输入 | 结果 | 墙钟 |
|---|---|---|---|
| 10k（校准） | 37,910 | 答对 | 15s |
| 300k | 265,503 | 答对 | 11s |
| 492k | 492,252 | 答对 | 16s |
| **620k** | **619,498** | **答对** | 26s |
| 900k | — | **撞额度上限**（非上下文错误） | 9s |

**结论三条**：

1. **500k 不是硬墙**。619k 被完整处理（usage 报 619,498，模型答对），事件流无 compact。
   所以 sat 阶梯的"断点"要往 872k–1.05M 找，不能停在 500k。
2. **单轮 exec 不做压缩**。没有 `compact` 事件，超窗若发生只能是硬拒或静默截断。
3. **额度是比窗口更早撞到的墙**。900k 那档报的是
   `You've hit your usage limit ... try again at 8:22 PM`——订阅额度打满，与被测能力无关。

**探针自身的两个缺陷（下一轮修）**：

- 针放在 25%/75%，在 619k 下分别落在 155k/464k，**即使客户端截到 500k 也仍在窗内**，
  无法排除"截断但答对"。下一轮把针放到 **98%**；
- 未测 872k（`max_context_window`）与 1.05M（模型宣称），因为额度先耗尽。

**对设计的影响**：sat05（435k）与 sat06（870k）的定位要改——
435k 大概率只是"更贵"，不是"做不到"；870k 目前**跑不动**（额度），
要么改用按量计费的 API key，要么把最高档降到 620k 并分窗口跑。

## 八、预算与时长

| 档 | A/格 | B/格 | D/格 |
|---|---|---|---|
| sat01–sat02 | $0.05–0.1 | $0.01 | $0.03 |
| sat03–sat04 | $0.3–0.6 | $0.03 | $0.08 |
| sat05 | $1.2（分次读 2–3×） | $0.08 | $0.20 |
| sat06 | $2.5–6 | $0.15 | $0.35 |

81 格合计约 **$25–35**；墙钟 8–12 小时（sat05/06 单格 10–20 分钟）。

**但真正的约束不是钱，是订阅额度窗口**（探针实测）：一次 900k 调用即打满当日额度，
报 `You've hit your usage limit`，与能力无关。所以：

| 方案 | 说明 |
|---|---|
| A 用按量 API key 跑 | 不受订阅窗口限制，但需要 key 与计费；金额口径反而更干净 |
| 分窗口跑 | 额度恢复后继续，sat05/06 每天只能跑几格，周期拉长到数天 |
| 最高档降到 620k | 已验证可行，但会失去"明显超窗"这一格，容量假设可能又测不出 |

## 九、风险与降级

| 风险 | 处理 |
|---|---|
| 生成 1,280 个文件 / 10 万行，git 与 checks 变慢 | 单题生成 < 30s；checks 用"每域一条 + 全局一条"，不逐文件跑 |
| 输出上限（Codex 65k / ds 393k） | agg 只输出校验值 + 写回，不做全量打印 |
| DS 位置盲区污染 | 三相位冗余 + seed 随机化 + 记录键偏移 |
| Codex 自动 compact 掩盖容量墙 | 探针已排除：单轮 exec 无 compact 事件，只有硬拒或静默截断 |
| **订阅额度先于窗口耗尽** | 900k 一档即打满；高档位需改 API 计费或分窗口跑（见第八节） |
| 题目可被 grep 走捷径 | agg 的全序依赖"跨领域相对大小"，局部搜索无法推出 |
| 生成器本身写错，误判为模型失败 | 双向自检（seed 必败 / ref 必过）+ 第 4 关分段解必败 |
