总路线：[实施路线图](实施路线图.md)。本步只处理分层成果传递、真实任务起点及相关修改范围检查，不实施第三步的整体验证或第四步的自动返工。

## 1. 原来的问题

原 `runner.py` 虽然按依赖分层启动任务，但传给每次 `_run_one()` 的总是 intake 时记录的原始 `base`，所有工作目录都从原始代码开始；分支统一等到所有任务结束后才合并。

因此 A 创建接口，B 虽然等 A 完成，却仍从没有接口的版本启动。原先的测试只检查依赖失败会阻断后续，没有检查依赖成功后成果是否真实可读。

另一个相关问题：`git status` 只看当前未提交状态。worker 自行提交后，工作目录可能干净；旧检查会漏掉修改，验收 diff 也可能为空。引入前置成果后，比较起点还必须是本任务起点，不能拿原始总基线计算本任务修改，否则会把继承来的文件误认成越界写入。

## 2. 选择的传递策略

采用路线图已选定的分层整合方案：

```text
原始基线 V0
  ├─ A 从 V0 开始 ─ 验收通过 ─┐
  └─ B 从 V0 开始 ─ 验收通过 ─┴─ 按计划任务顺序整合，形成 V1
                                      ├─ C 从 V1 开始
                                      └─ D 从 V1 开始
                                           ↓ 本层验收与整合
                                          V2
```

四个明确约定：

1. 同层任务从同一个版本开始，继续并行；任务结束后才越过本层屏障。
2. 通过任务验收的成果按本层计划顺序整合，不按任务完成快慢决定顺序。
3. 下一层看到此前各层已经整合的全部成果，不是仅看显式依赖的那些文件。事件标记 `visibility=all_prior_integrated_layers`，未来实验需固定这个条件。
4. 原始总基线不改写。原始起点回答“这次 run 从哪里开始”；任务起点回答“这个 worker 实际拿到哪个版本”。

这是一种实现简单、可追踪的协同策略。它不提供任务级精确上下文隔离，也不自动发现语义依赖。

| `tests/test_dependencies.py` | 新增真实临时 Git 仓库中的传递、并发、整合失败与范围测试 | 通过文件、命令与版本关系证明成果已传递 |

## 4. 失败怎样处理

### 任务实现或验收失败

该任务不进入整合版本，依赖它的后续任务被阻断。独立成功任务仍可以整合，它们自己的依赖链可以继续。整体 run 如实报告失败或部分完成。

### 成果整合失败

当前失败分支不能报告为 done；同层尚未整合的成果标为 blocked；后续所有层停止发车，避免继续使用不确定的层版本。已整合成功的分支和证据保留，不回滚或抹除历史，不自动解决冲突。

### 无改动与自行提交

- 没有内容变化、没有 worker 新提交：记录 `task.no_commit`，仍按判据验收。
- worker 已自行提交、引擎没有额外提交：记录 `task.existing_commit`；累计 diff 与范围照常检查。
- worker 已提交后又修改文件：验收 diff 覆盖两部分，必要时由引擎创建额外提交。
- worker 修改范围外文件后提交再恢复：提交历史仍能查到，判定越界。

## 5. 涉及概念

### 依赖图与分层

任务是点，“B 需要 A”是一条依赖边。没有依赖环时，可把任务按先后分层。同层任务具备并发执行条件；新一层要等前层处理完。

### 屏障

屏障就是整层的等候点。A 做得快也不会让下一层提前启动；要等同层其他任务结束，并完成本层整合。这样下一层有一个确定的共同起点。

### 工作目录隔离与成果共享

隔离目录像各自的草稿副本：能避免同时覆盖文件，却不会自动把别人的新内容复制过来。共享通过 Git 提交与整合版本完成。两个机制解决不同问题。

### 提交和版本标识

提交记录代码快照及历史关系。完整版本标识用于准确定位代码。`base_sha` 是开始时的版本，`head_sha` 是该任务保存后的版本，整合版本还可能有自己的合并提交标识。

### 祖先关系

如果 B 的起点包含 A 的成果，B 完成后的历史必须仍继承这个起点。检查祖先关系能发现把历史重置到更旧位置的情况，但不能证明 worker 没有在后续提交里破坏功能；行为正确仍需要验收。

### 修改范围与 diff

修改范围检查回答“触碰了哪些文件”；diff 回答“内容怎样变化”。两者都以本任务起点为参照。继承来的接口不应算 B 新写的文件，但 B 若自行修改接口，就需要在自己的 writes 中获得许可。

### 局部验收与成果接纳

任务验收通过，只说明它在自己的工作目录里满足当前判据。整合成功后才成为下一层可使用的成果。所有任务验收与整合成功，仍不等于做过第三步计划中的合并后整体验证。

## 6. 验收设计

| 场景 | 具体检查 |
|---|---|
| A 创建接口、B 调用、C 检查 | B、C 实际读到前置文件；三个任务使用真实 Python 命令验收，不使用模型打分 |
| 同层并发 | 两个 worker 在同步屏障碰面；串行执行无法通过该测试；起点版本相同，目录互不包含同层新文件 |
| 下一层可见范围 | 只显式依赖 A 的任务，也能看到此前同层成功整合的 B，符合约定策略 |
| 前置失败 | 后续不启动，失败成果不出现；独立成功任务及其依赖链仍可继续 |
| 固定整合顺序 | 强制 t10 比 t1 先完成，仍按 t1、t10 的计划顺序整合 |
| 重复运行 | 每次首层仍从 intake 的固定起点开始，不继承上一轮成果 |
| 整合失败 | 注入失败，后续层零调用，未接纳成果不报成功 |
| 部分整合成功 | 真实整合第一个分支，再注入第二个失败；保留首个成果，阻断后续层 |
| worker 自行提交 | diff 非空、路径被核验、没有重复声称引擎创建了提交 |
| 已提交越界与恢复 | 违规路径被发现；不因当前工作目录干净或文件已删除而漏判 |
| 重命名、中文和空格 | 重命名源和目标都被核验；中文空格路径保持原样 |
| 重置旧历史 | worker 不能丢弃继承版本后被接纳 |
| 已有单写者限制 | 即使两个同文件任务有依赖，当前 E013 仍阻断；没有放宽契约 |

## 7. 本步保留的边界

- 当前契约仍是一个文件只由一个任务写；串行同文件多任务也仍被 E013 拒绝。文档里曾建议“加依赖串行”与实现存在差距，本步不通过改契约放开此能力。
- 下一层继承此前所有已整合成果，不是严格依赖子集；这可能影响未来研究的上下文条件，必须明确记录。
- 整合沿用现有目标仓库运行分支；独立整合目录与合并后整体验证仍属第三步。
- 不实现冲突自动修复、worker 自动重试、预算控制或动态重新规划。
- Git 可见路径检查覆盖版本化文件、普通未跟踪文件和任务新增提交；这不是操作系统级文件访问隔离，也不能发现所有语义破坏。
