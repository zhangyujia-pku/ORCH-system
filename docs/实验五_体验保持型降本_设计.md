# 实验五 · 体验保持型降本（重新定位）

> 一句话：**用户仍然只跟 Codex 说话、不离开客户端、不手工拆任务；把"执行"外包给便宜模型，从而把 Codex 的额度消耗压到原来的 5–15%，质量不下降。**

## 一、为什么基线必须是 A，不是 B

之前几轮把 B（便宜模型单干、完全不用 Codex）当对照，得出"编排不划算"。那个对照回答的是另一个问题——**要不要用 Codex**。

而项目的真实形态是：**用户已经在用 Codex，且不想换**。于是唯一有意义的对照是：

| 臂 | 含义 | 用户视角 |
|---|---|---|
| **A** | Codex 端到端（当前体验） | 基线 |
| **C** | Codex 规划 + Codex 执行 | 体验不变，只是先写计划 |
| **D** | Codex 规划 + 便宜模型执行 | 体验不变，执行换人 |
| B | 便宜模型端到端 | **不适用**：用户不会为此放弃 Codex |

换成 A 作基线后，"省了多少"才有意义——因为它省的是**你正在付的那笔账**。

## 三、三条结论

**① D 把 Codex 额度压到 5–15%，质量与 A 持平。**
三题里两题全过、一题与 A 同样失败。没有出现"D 比 A 差"。

**② C 是稳妥档，不是省钱档。**
C 用同一个模型，只把"探索"换成"计划"。它在 t01/t02 便宜（0.28×/0.76×），
但 t03 反而贵 37%——因为 H 既要规划又要执行，两次都把大上下文读了一遍。
好处是质量最稳（t03 唯一通过的就是 C）。

**③ 规划费可摊薄，D 还有下降空间。**
同一仓库连续 N 个需求共享一份计划时：

| 题 | N=1 | N=3 | N=5 |
|---|---|---|---|
| t01 | 0.14× | 0.06× | 0.05× |
| t02 | 0.29× | 0.14× | 0.11× |
| t03 | 0.40× | 0.27× | 0.24× |

## 四、代价与风险（必须先说）

| 项 | 实测 | 影响 |
|---|---|---|
| 墙钟 | D 在 t01 快 60%，t02/t03 慢 40–63% | 规划有固定延迟；用户会感知 |
| 质量依赖 L | t03 的 D 失败与 A 同因 | L 换弱档就可能把质量拉下来 |
| 金额口径 | 订阅无逐次账单 | 金额是影子价；额度（token）才是硬指标 |
| 样本 | 3 题 × 1 次 | 只能提方向，不能下判定 |

## 五、正式实验怎么设计

- **对照**：A / C / D 三臂，同一题配对
- **主指标**：
  1. `H 输入 token ÷ A 的 H 输入 token`（额度节省，硬指标）
  2. `Δ resolved`（质量非劣，配对）
  3. 影子金额比（辅助）
- **次指标**：墙钟、规划被拒次数、patch 应用失败率
- **样本**：30 题（S/M/L 各 10）× 3 臂 × 1 次 = 90 次
- **判定**：
  - 支持定位：`resolved` 差异的 95% 区间下界 > −10pp，且 H 额度比 < 0.5
  - 否定定位：出现 D 显著差于 A，或 H 额度比 > 0.8
- **不做**：把 B 当主对照（那是另一个问题）

## 六、什么会推翻这个定位

1. 扩到 30 题后，D 的 resolved 明显低于 A（说明省的是质量，不是浪费）
2. H 额度比在真实仓库上明显高于 15%（说明 t01 的 5% 是小仓库特例）
3. 墙钟变慢到影响使用（例如普遍 +100%）
4. L 的档位一换（更便宜/更弱），质量就崩
