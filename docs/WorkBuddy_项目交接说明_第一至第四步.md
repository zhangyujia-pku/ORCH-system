# 项目交接说明：第一至第四步改动及原因

交接日期：2026-11-08。

项目根目录：`<orch 仓库目录>`。

项目目标是完整的多 Agent 协同框架，涵盖需求存档、规划、能力路由、并行执行、依赖成果传递、验收、整合、有限返工和恢复。语言学研究仍等待工程验收完成、版本冻结后开始；开发期间仅保留案例和设计记录。

本文整理此前交付记录。本次保存仅新增交接文档，没有修改代码或重新运行测试；下述验收结果对应各步交付时的记录。接手后应先核对当前工作区，再验证当前版本。

## 第一步：让状态、实际动作和报告一致

主要涉及模块：`orch.planner`、`orch.runner`、`orch.workers`、`orch.providers`、`orch.intake`、`orch.worktree`、`orch.trace`、`orch.status`、`orch.cli`、`orch.dispatch`。

具体改动：

- 规划失败明确报告“尚未执行”，记录实际尝试数；旧 `fallback` 标识保留兼容，但不再被解释为已经启动单 Agent。
- 重新规划前归档旧计划，防止旧成功计划冒充当前结果。
- 执行前检查计划、仓库基线、能力要求和完整分派；不满足条件时阻断。
- 基线缺失或不可用时停止，不自动换成当前 HEAD。
- 区分创建新提交、已有提交、无改动和提交失败。提交失败的成果不能进入验收、整合。
- 使用 `operation_id` 关联当前调用的事件，避免历史成功污染当前状态。
- 区分计划就绪、执行结果和通知结果，通知失败单独记录。

原因：原先存在“报告说做了，实际没做”和“读取到旧结果便误报成功”的风险。后续协作、恢复和研究都需要可信的运行事实。

当时验收：151 项测试通过。

详细记录：[第一步实施验收](第一步_实施验收.md)。

## 第二步：让后续任务真正拿到前置成果

主要涉及模块：`orch.runner`、`orch.worktree`、`orch.worker`；新增测试模块 `tests.test_dependencies`。

具体改动：

- 引入随层推进的整合版本：同层任务从共同起点并行执行，验收后按计划顺序整合，下一层从新版本启动。
- 下一层可见此前各层已整合的全部成果，超出“仅显式依赖文件”的范围；这是当前明确采用的协作策略。
- 记录每个任务的真实 `base_sha`、`head_sha`。
- 修改范围和 diff 均相对本任务起点计算，覆盖 worker 自行提交、未提交、未跟踪及提交后恢复的修改。
- 检查版本继承关系，防止 worker 重置旧历史、丢弃前置成果。
- 修正中文、空格和重命名路径的解析。
- 整合失败时停止后续层，保留已接纳成果及失败证据。
- 保留现有单写者限制：两个任务即使有依赖，也不能写同一文件。只调整了 E013 的提示文字。

原因：原先虽然会等待前置任务完成，但所有工作目录仍从原始基线创建，后续任务实际读不到前置修改。“等待完成”和“取得成果”需要分别实现。

当时验收：166 项全套测试通过，其中新增 15 项。

详细记录：[第二步依赖成果传递](第二步_依赖成果传递.md)。

## 第三步：让成功判定有可靠证据

主要涉及模块：`orch.verifier`、`orch.worktree`、`orch.runner`、`orch.cli`、`orch.dispatch`；新增 `orch.verification`。同时调整后端比较、成本统计脚本的成功口径。

具体改动：

- 实际退出码与预期退出码比较，支持“预期返回非零”的正确行为。
- 输出匹配使用完整 stdout，stderr 单独保存；摘要截断仅用于展示。
- 修正验收命令中引号、逗号、分号的解析。
- 区分断言失败、启动失败、超时、无法判定、模型验收异常和验收期间修改产品。
- 在独立目录、独立分支整合，保留用户原目录的分支和未提交内容。
- 新增维护者控制的固定整体验收配置 `verification.json`。
- 保护固定检查文件，防止 worker 放宽自己的最终标准；运行中修改配置不会改变已加载标准。
- 验收后检查保存版本未被改动，并固定检查工具路径，避免产物中的同名程序替代检查工具。
- 报告和统计脚本统一采用整体结果。

当前成功条件是：

任务全部通过 → 整合全部成功 → 固定整体验收通过。

原因：每个任务分别通过、Git 合并成功，仍可能组合后不能工作；worker 自写的测试也可能遗漏需求或被放宽。

当时验收：197 项全套回归通过，后续补充专项通过；第三步结束时共有 200 项不同测试用例。不能把这些批次混称为单次 200 项全套运行。

详细记录：[第三步可信验收与整合](第三步_可信验收与整合.md)。

## 第四步：让失败、资源和中断得到控制

新增模块：`orch.control`、`orch.recovery`。扩展执行、路由、后端调用、验收、命令行及后台队列；新增 `tests.test_execution_recovery` 和执行配置样例。

具体改动：

- 有限返工：将失败判据和修改证据传给下一次独立尝试，每次从当前层的已接纳起点开始。
- 合格替补：只能在满足原任务能力、文件数和判据要求的候选中接替。
- 有限重新规划：完整的 `dispatch` 入口支持有上限的重新规划，规划和执行共享资源。没有新增单 Agent 降级。
- 人工澄清：worker 用明确的 `needs_input` 格式暂停；回答追加保存，后续中断和返工持续携带，原需求不覆盖。
- 独立执行策略 `execution.json`：限制失败尝试次数、外层 provider 调用次数、验收命令数、总时长及重规划次数。
- 持久保存资源计数和截止时间，恢复不会清零。
- 增加取消、进程监视、进程树终止请求和系统文件锁，防止同一运行重复启动。
- 按层保存恢复点，核对计划、基线、固定检查及后端配置；已接纳成果跳过。
- 已成功运行恢复时复用结果，避免重复执行和合并。
- 不确定合并、未确认停止的子进程、配置变化等现场拒绝自动继续。
- 后台队列支持遗留认领恢复；每次尝试和每轮规划分别留存证据。
- 补严后端报错后的修改审计，并修复失败反馈被仓库说明截断、澄清在再次中断后丢失的问题。

新增操作包括 `--execution`、`--resume`、`cancel`、`answer`。默认仍为每任务单次尝试，候选切换和额外重规划默认关闭，需要明确配置。

原因：只有顺利路径的框架无法可靠运行；失败恢复需要边界，重启不能刷新预算，重复执行也不能重复接纳成果。

## 接手时必须保留的边界

- 任务字段、schema、E/W 错误码及静态校验规则保持兼容，不能通过放宽检查来让运行通过。
- 固定整体验收由维护者控制，不能让 Planner 或 worker 自动降低标准。
- 恢复粒度是已接纳的层，未接纳工作可能重做；不承诺全系统“恰好一次”。
- 调用限制统计外层 provider 调用，不能代表 CLI 内部全部 API 请求或真实金额；尚未实现精确美元熔断、CPU 或内存配额。
- 固定检查保护和版本审计属于工程完整性措施，不能当作操作系统安全隔离。
- 每步说明中的“尚未实施后续步骤”是当时范围记录；当前能力以第四步说明及当前代码为准。
- 修改前副本用于比较，不能覆盖已经更新的工作区。
- 此前实施没有为框架自身初始化 Git 仓库，也没有发送实际通知或开展语言学实验。
