## 1. 梳理：改哪些地方，为什么改

| 位置 | 本轮改变 | 必要性与验收 |
|---|---|---|
| 新增 `orch/control.py` | 独立执行配置、持久资源计数、取消、进程监视和系统文件锁 | 并发任务也必须共享一个上限；恢复不能清零。两线程争抢最后一次调用只能有一个成功；同一次运行只准一个执行者 |
| 新增 `orch/recovery.py` | 保存恢复点、计划与配置指纹、尝试编号、失败次数、待回答问题与回答 | 重启必须知道哪些成果已经接纳；修改计划后不能冒用旧成果；回答追加保存，原始需求不覆盖 |
| `orch/runner.py` | 有限尝试、失败证据反馈、候选后端接替、按层恢复、独立尝试档案 | 第一次失败第二次成功应有两份证据；已接纳层不再调用 worker 或重复合并；范围违规等不能自动返工 |
| `orch/worker.py` | 明确的 `needs_input` 返回格式；审计失败保留原始输出 | 信息不足时暂停，不靠模型猜用户决定；审计失败不能当成普通任务失败无限再试 |
| `orch/providers.py`、`orch/workers.py` | 合格候选链；执行时严格读注册表 | 替补必须满足原任务全部能力、文件数和判据要求；失效配置不能静默换成默认注册表 |
| `orch/planner.py` | 受控命令行调用、非零退出报错、每轮规划原始输出及提示存档、清空上次 token 统计 | 后端报错不能冒充正常回答；重新规划不能覆盖前一轮证据；取消时处理整个进程树 |
| `orch/verifier.py`、`orch/verification.py` | 任务检查与固定整体验收都消耗同一个命令上限；模型验收也消耗调用上限 | 不能只限制 worker，却允许检查或验收模型无限运行；达到上限不能报告整体成功 |
| `orch/worktree.py` | 提交和整合前检查停止状态，Git 操作设置等待上限 | 取消后避免继续接纳新成果；Git 中断有不确定性时保留现场，拒绝猜测恢复 |
| `orch/cli.py`、`orch/status.py` | `--execution`、`--resume`、`cancel`、`answer` 及相应状态 | 用户能明确停止、回答、继续；状态须区分失败、等待、取消和资源耗尽 |
| `orch/dispatch.py` | 前台/后台/队列统一传配置、共享预算、有限重新规划、认领恢复、完成结果复用 | 后台重启不应把旧任务当新任务；规划与执行不能各用一份新预算；恢复成功记录不重复运行或重复通知 |
| 新增 `examples/execution.example.json`、`tests/test_execution_recovery.py` | 配置样例与故障注入测试 | 除顺利执行外，还要验证上限、取消、暂停、后端失效和中断现场 |

保留前三步的成功条件：任务通过 → 独立整合成功 → 用户固定整体验收通过。自动返工不会修改固定验收配置、任务写入范围或能力要求。本轮没有改变任务字段、schema 或 E/W 错误码。

## 2. 你需要讲清楚的概念

**尝试与返工。** 一次尝试是一次独立的任务执行目录，例如 `t01-a1`。普通验收失败后，把失败判据和修改摘要交给下一次尝试，要求它在原范围内修复，这才形成返工反馈。每次从当前层的同一个已接纳起点开始，不继承失败目录里的任意改动。第一版反馈使用失败摘要及最多 6000 字符的 diff 尾部；完整 diff 留在档案中，反馈不保证包含全部长 diff。反馈单独传入，不受仓库说明的 1500 字符展示上限截断。

**重试与重新规划。** 重试保留原任务契约，再做同一个任务；重新规划重新拆整项需求。这里选择路线中的“有限重新规划”，没有新增单 Agent 降级。只有 `dispatch` 入口拥有从规划到执行的完整循环；`run` 执行已有计划，不擅自重新拆任务。一次 `plan_run` 原有最多 3 次计划校正；`max_replans` 控制用完这一轮或执行失败后，最多再开几轮。全程共用调用及总时限上限。

**合格替补与异构。** 不同后端有不同能力和调用方式。替补来自已经通过路由筛选的候选链，不能因为更贵或“更强”就获得它没有的能力。`switch_after=1` 表示每次尝试向后换一个合格候选；链用尽后，在剩余尝试次数内留在最后一个候选。没有合格替补时，最多原后端有限重试，绝不派给不合格后端。

**恢复点。** 它记录已接纳的层、整合版本、任务结果和下一层位置。崩溃后先核对计划、仓库起点、规格、固定检查、执行参数及后端配置，再决定能否继续。已经接纳的成果跳过；中断时尚未接纳的同层工作可能重做，调用资源仍计入。第一版恢复粒度为层，不承诺从模型生成到一半的位置接着生成。

**幂等性。** 再次恢复一个已成功的运行，应返回先前已核验的结果，而不是再生成、再合并一次。它不等于保证全系统“恰好一次”：通知发送和落盘之间仍可能崩溃；外部副作用也不在 Git 恢复点的保证范围内。

**取消、超时和资源耗尽。** 取消是用户主动请求；单次调用超时是一个后端或检查等太久；总时限耗尽是整项运行没有剩余时间。它们有不同状态。取消先落一个请求文件，执行者轮询检查；不是直接删除目录。进程树表示模型 CLI 及其启动的测试等后代进程，只停止父进程可能留下仍在运行的子进程。

**澄清。** worker 明确返回 `{"status":"needs_input","question":"…"}` 才暂停。回答按运行、任务和问题编号追加关联，恢复时送回 worker，并在该任务后续中断恢复和返工时持续携带。没有新回答不会重复调用；暂停本身不占普通失败次数，但每次真实调用都计入资源上限。当前识别依赖明确格式，不能保证模型总能正确发现信息缺口。

## 3. 资源上限与配置

独立的 `execution.json` 属于执行策略，不塞入每个任务的契约。默认读取运行目录里的配置；也可用 `--execution <路径>` 指定。显式指定的文件不存在或内容无效时阻断。

| 字段 | 默认值 | 含义 |
|---|---:|---|
| `max_attempts` | 1 | 每个任务最多允许多少次普通失败尝试；1 保持原有单次行为。人工澄清或中断后的物理尝试编号可以更大 |
| `switch_workers` | false | 是否使用合格候选链接替；需要 `--workers` 注册表 |
| `switch_after` | 1 | 每个候选占用多少个尝试编号再向后切换 |
| `max_calls` | 100 | 编排器对 provider 的 `complete()` 调用上限，含规划、worker 和模型验收 |
| `max_commands` | 1000 | 编排器启动的任务验收与固定整体验收命令上限 |
| `total_timeout` | 3600 | 从资源控制启动起的总秒数；人类等待和停机时间也计入 |
| `max_replans` | 0 | `dispatch` 额外重新规划的次数，默认不开启 |

具体启用示例见 `examples/execution.example.json`：3 次失败尝试、允许候选接替、30 次 provider 调用、60 条检查命令、1800 秒总时限、最多额外重规划 1 轮。

限制在动作开始前预扣，并发共享；已经启动后失败的调用也计数。恢复延续已有计数和绝对截止时间，不通过重启获得新预算。取消后显式恢复会归档旧取消请求，保留计数。

这些不是精确费用限制：CLI 内部可能调用模型多次，也可能自己运行许多工具，外层目前看不到其全部活动。`max_calls` 不等于实际 API 请求数，`max_commands` 不包含 CLI 内部工具或 Git 管理命令。任务 `budget`、注册表价格估算和可解析的 token 信息仍不能代表真实账单；实际金额未知，不宣称实现美元熔断、内存上限或 CPU 配额。

受控 CLI 和检查命令可轮询取消并请求终止进程树。自定义的纯 Python provider 需要自行遵守传入的 timeout；编排器不能强行杀死同一 Python 进程里的任意函数。Git 检查及清理有独立等待上限，因此总时限表示停止新业务动作的期限，不保证程序在同一毫秒退出。

## 4. 操作方式

以下在 `orchestrator` 目录执行。将 `RUN_ID` 替换为已有运行标识；恢复时沿用原后端、检查和参数。需要先按第三步准备固定 `verification.json`。

```powershell
# 执行已有计划；异构候选由注册表提供
python -m orch run RUN_ID --workers workers.json --verifier codex --execution examples/execution.example.json

# 取消：只记录请求，由执行者响应
python -m orch cancel RUN_ID

# 回答某个暂停任务；仅保存，不自动启动
python -m orch answer RUN_ID t01 "采用 JSON 格式"

# 明确继续，保留已花资源；参数与原执行一致
python -m orch run RUN_ID --workers workers.json --verifier codex --execution examples/execution.example.json --resume

# 完整的规划—执行—有限重新规划入口；--no-notify 避免对外发送
python -m orch dispatch "用户的完整原话" --repo C:/目标仓库 --workers workers.json --execution examples/execution.example.json --foreground --no-notify

# 完整入口的既有运行恢复，按原始参数补齐 --verification 等
python -m orch dispatch --job RUN_ID --workers workers.json --execution examples/execution.example.json --resume --no-notify
```

同一运行使用系统文件锁互斥；命令行和后台入口也互斥。队列宿主重启后把遗留 `.running` 认领恢复为待处理项，并在已有资源账本时要求延续它。记录 `.done`、`.failed`、`.waiting`，不删除终态证据。

## 5. 恢复边界与现场

| 状态或现场 | 当前处理 |
|---|---|
| 已完成并通过固定整体验收 | 先验证配置和保存版本，再复用结果，不重新启动 worker、合并或检查 |
| 前一层已接纳，后一层取消或中断 | 跳过前层，从保存的整合版本继续；未接纳尝试可重做 |
| 等待用户回答 | 无匹配回答就继续等待；追加回答后显式恢复 |
| 同层既有等待又有终态失败 | 等回答的任务可以继续；不重做已经终止的失败任务，整次仍不能成功 |
| 普通断言失败、后端调用失败 | 在配置的失败次数及共享资源内返工；可使用合格替补 |
| 越界、保护文件修改、验收改动产品、审计失败、检查基础设施错误 | 直接失败；自动返工或重新规划不放宽限制 |
| 计划、固定检查、后端配置等指纹变化 | 拒绝恢复，另建运行 |
| 上次中断在整合阶段 | 拒绝自动重放，要求人工检查，不猜测 merge 到了哪一步 |
| 旧子进程仍存在、PID 无法确认或未确认进程树已停止 | 拒绝继续或覆盖旧执行；先检查现场 |
| 总资源或截止时间已耗尽 | 保持停止；恢复不重置。重新开始应另建运行、明确新预算 |

没有新增自动修复不确定 Git 现场的命令。拒绝恢复也属于可解释的恢复结果：安全停止比把半次合并当作完整成果继续执行更可靠。

每个运行可查看：`runtime.json`（资源与活动进程）、`checkpoint.json`（已接纳成果与恢复阶段）、`answers.json`（追加回答）、`trace.jsonl`（事件）、`artifacts/history/<execution_id>/`（每次 worker 尝试输出/diff/验收）、`planning-history/<轮次>/`（每次规划提示与原始返回）。这些包含原始需求或代码，作为本地工程记录保留。
