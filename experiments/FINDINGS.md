# 需求写法 → 计划返工次数（首批 30 条）

> 数据：`experiments/results.csv`　语料：`experiments/intents.json`
> 复现：`python scripts/run_experiments.py`（约 29 分钟）→ `python scripts/intent_features.py --runs-dir experiments/runs`

## 设计

6 个任务 × 5 档详细程度，完全平衡。**只跑 `orch plan`，不跑 worker**——测的是
"需求怎么写 → Planner 被校验器打回几次"，worker 不参与这个变量。

| 档 | 写法 | 例 |
|---|---|---|
| L1 | 只有目标，无文件、无验收 | 帮我加个持久化，别每次重启都丢数据，做好一点。 |
| L2 | 提到文件名，仍无验收 | 给 storage.py 加持久化，把任务存到 tasks.json。 |
| L3 | 说清改哪里做什么，不给命令 | 在 storage.py 加持久化：启动时从 tasks.json 读取，每次写操作后保存。 |
| L4 | 给出验收命令 | …验收：`python -m pytest -q tests/test_app.py` 退出码 0。 |
| L5 | 验收命令 + 边界条件 + 禁改范围 | …文件损坏时抛异常且不覆盖原文件…不要改动现有公开接口。 |

## 结果

| 档 | n | 平均重写次数 | 有重写的比例 | 平均耗时 |
|---|---|---|---|---|
| L1 | 6 | **1.00** | **100%** | 88s |
| L2 | 6 | 0.67 | 67% | 67s |
| L3 | 6 | **0.00** | **0%** | 44s |
| L4 | 6 | 0.17 | 17% | 42s |
| L5 | 6 | 0.33 | 33% | 50s |

逐任务看，L1 在 6 个任务上都是 1，L3 在 6 个任务上都是 0——**档位效应一致，不是某个任务带出来的**：

```
task          L1   L2   L3   L4   L5
export         1    0    0    0    0
persist        1    1    0    1    0
priority       1    1    0    0    0
search         1    1    0    0    1
softdel        1    1    0    0    0
stats          1    0    0    0    1
```

## 三个结论

**1. 不是"越详细越好"，是 U 形。**

L1 → L3 单调下降（1.00 → 0.00），但 L4、L5 又回升（0.17、0.33）。
**L3 是最优区间**：说清"改哪个文件、做什么"，但不强加验收细节。

**2. 返工的唯一机制是 E014（判据不可判定）。30 次重写，11 次拒稿，错误码 100% 是 E014。**

机制很清楚：

- L1 没给任何可锚定的东西，Planner 只能凭空编判据 → 写出"做好一点"这类不可判定的句子 → 被校验器挡回；
- L3 被迫描述具体动作，判据自然带了文件路径和函数名 → 一次通过；
- L4/L5 加了很多约束（边界条件、禁改范围），**判据条数增加**，单条写错的概率乘上去，总体出错机会回升。

可检验的推论：重写风险 ≈ f(判据是否可锚定) × 判据条数。两个因子方向相反，所以最优点在中间。

**3. 含糊的代价是双倍的。**

L1 平均 88 秒，L3 平均 44 秒——**2.0 倍**。多出来的全是重写那一轮的 LLM 调用。
所以"把需求写清楚"不是文风问题，是成本问题。

## 语言学特征与重写的相关（n=30）

| 特征 | r |
|---|---|
| 句均长 | **−0.675** |
| 模糊密度 | **+0.436** |
| 字数 | −0.430 |
| 锚点数 | −0.427 |
| 验收词 | −0.295 |
| 指称密度 | +0.214 |

**这些系数不能用。** 它们主要反映"档位"这个共同因子——L1 全是短句低锚点，L5 全是长文多锚点，
所以任何与长度共变的特征都会呈现同样的趋势。要分离出独立效应，需要**同一档位内**的方差，
而这批语料同档的文本是我一个人写的，方差太小。

诚实的说法：这 30 条证明了**档位有效**，还没有证明**哪个语言特征在起作用**。

## 第二批：回指对照（n=20，配对设计）

目的：第一批里"指称密度 +0.436"是长度共线造成的假象，这批用来分离。
做法：10 对文本，前半段完全相同（都先点名文件、建立指代对象），只操纵两处二次提及——
C 组重复文件名，R 组改用"这个模块/它"。长度拉到 100 字以上稀释差异。

| pair | C 重写 | R 重写 | 差 | 长度 C | 长度 R |
|---|---|---|---|---|---|
| p01 | 1 | 1 | 0 | 116 | 99 |
| p02 | 0 | 0 | 0 | 114 | 94 |
| p03 | 0 | 0 | 0 | 111 | 92 |
| p04 | 1 | 0 | −1 | 107 | 96 |
| p05 | 1 | 1 | 0 | 104 | 83 |
| p06 | 1 | 0 | −1 | 109 | 89 |
| p07 | 0 | 1 | +1 | 100 | 88 |
| p08 | 0 | 1 | +1 | 94 | 83 |
| p09 | 1 | 0 | −1 | 112 | 92 |
| p10 | 0 | 2 | +2 | 84 | 66 |

**C 组平均 0.50，R 组平均 0.60。配对差合计 +1，均值 +0.10。R 更差 3 对、更好 3 对、持平 4 对。**

### 结论：回指风格不驱动返工

这是空结果，而且是干净的：R 组文本比 C 组**短 16%**，按第一批的规律本该更差，
但实际没有任何系统性差异（3 : 3 : 4）。

由此排除了两个候选解释：

1. **不是"指称密度"在起作用。** 第一批里那个 +0.436 确实是长度共线造成的。
2. **也不是"文本长度"在起作用。** 短 16% 没有换来更差的成绩。

### 那第一批的 U 形是什么造成的？

本批 C 组和 R 组的锚点数分别是 4 和 2——**都还有锚点**，结果都一样好/坏。
第一批的 L1 是**零锚点**（锚点数 = 0）。

所以更像是**阈值效应而不是线性关系**：不是"锚点越多越好"，而是"**有没有**"。
零锚点时 Planner 只能凭空编判据，必然写出不可判定的句子；一旦有一个以上可锚定的名字，
剩下的波动就变成噪声了。

这条推论与第一批一致（L1 六条全挂，L2 有三条挂），但本批 n=10 不足以单独证实，
需要再补一批"锚点数 = 0 / 1 / 2"的梯度实验。

## 第三批：锚点梯度 0 / 1 / 2（n=24）

模板生成，正文和结尾逐字相同，只改开头提到的锚点数量。文本长度 117–140 字，档间差恒定 11%。

| task | A0（零锚点） | A1（一个） | A2（两个） |
|---|---|---|---|
| export | 1 | 0 | 1 |
| paging | **3（降级）** | 0 | 1 |
| persist | 2 | 1 | 1 |
| priority | **3（降级）** | 1 | 2 |
| search | 1 | 1 | 1 |
| softdel | 1 | 0 | 0 |
| stats | 1 | 1 | 2 |
| validate | 1 | 1 | 1 |
| **平均** | **1.62** | **0.62** | **1.12** |

- **A0 在 8 个任务里没有一次好于 A1**：5 次更差、3 次持平、0 次更好（单尾符号检验 **p = 0.031**）
- **A2 也从未好于 A1**：4 次更差、4 次持平、0 次更好（p = 0.062）
- **两次降级都发生在 A0**，A1、A2 全在 3 次尝试内通过
- 三档产出的任务数都是 1，所以差异不来自"拆解多少"

所以不是"锚点越多越好"，而是 **1 个最优、0 个必坏、2 个略差**。

2 个反而变差，最可能的原因是任务契约同时点了两个写入目标，Planner 要为两边各写一条判据——
**判据条数变多，单条写错的概率乘上去**。这与第一批 L4/L5 回升是同一个机制。

### 重要：第三批换了模型版本

`codex-cli 0.166.0-alpha.6` 在 16:08 自动升级到 `0.167.0-alpha.3.2`（旧版本目录被删除）。
第三批整体 E014 率明显高于前两批（连 A1 都有 5/8 出现 E014，而第一批 L3 是 0/6）。

**结论：第三批内部的对照（A0 vs A1 vs A2）有效——同版本、同模板、同一天；
但它的绝对水平不能和前两批直接比。** 要跨批比较，必须用同一版本重跑前两批的锚点。

## 第四步：版本漂移校准（n=6）

Codex 在第三批之前自动升级（`0.166.0-alpha.6` → `0.167.0-alpha.3.2`），必须确认跨版本结论还成立。
做法：从第一批原样取 L1 / L3 各 3 条（同一批原文，不重写），用新版本重跑。

| task | L1 旧 | L1 新 | L3 旧 | L3 新 |
|---|---|---|---|---|
| persist | 1 | 1 | 0 | 0 |
| search | 1 | 1 | 0 | **1** |
| stats | 1 | 1 | 0 | 0 |

- **L1 完全复现**：1.00 → 1.00，三条全中
- **L3 上移**：0.00 → 0.33（search-L3 这次被 E014 拒了一次）
- 逐对方向：2 对严格 L1>L3，1 对持平，**0 对反向**
- 耗时差距从 2.0× 缩到 1.7×（L1 100s / L3 60s）

**结论：主效应方向在新版本上稳定，但绝对水平会漂。**

这个结果决定了报告该怎么写：

> 能写「含糊需求的返工率显著高于具体需求」；
> 不能写「具体需求的重写次数是 0」——那是特定版本下的数值，不是规律。

## 三批合起来，证明了什么

74 次规划运行，**43 次拒稿，错误码 100% 是 E014**，没有出现过第二种。

1. **需求写法显著影响规划返工。** 从含糊到 L3 具体，返工 1.00 → 0.00；耗时 88s → 44s。
2. **失败机制只有一个：判据不可判定。** 43 次拒稿全是 E014。不是模型不会写代码，
   是它把需求翻译成"可验证的判据"这一步会失败。
3. **锚点数量有最优值，不是单调关系。** 0 个最差（1.62，且唯一出现降级），1 个最好（0.62），
   2 个略回升（1.12）。A0 从未好于 A1，p = 0.031。
4. **回指风格与文本长度都不独立起作用。** 配对实验里 R 组比 C 组短 16%，
   成绩没有系统性差异（3 好 3 坏 4 平）。

一句话：**写需求时给一个可锚定的东西就够了，别一个不给，也别一次给两个。**

## 局限

1. 每档 n=6~8，只能做符号检验，不能做参数检验；结论方向可信，效应量不可信。
2. 单模型、单仓库（demo/tasks_app）、单日。**第三批跨了模型版本升级**，绝对值不可与前两批比。
3. 只测了规划阶段，没测执行阶段（worker 成败、合并冲突未纳入）。
4. L4/L5 与 A 系列的句式高度一致，可能有模板效应。
5. 档位与字数共线；第二批已排除长度，但指称密度与锚点数天然共线（换掉文件名必然减少锚点），
   这一对变量在本设计下**无法分离**。

## 附录：执行阶段暴露的问题（2026-11-06 夜）

从"只测规划"推进到"测执行"时，一天内连续三次失败，**全部出在验收器，没有一次是模型的问题**。
这条值得单独记：多 agent 系统的瓶颈不在模型，在"怎么判定它做对了"。

| # | 现象 | 真实原因 | 误导性 |
|---|---|---|---|
| 1 | 任务 failed，判据全挂 | 验收器**没跑命令**：判据写作 `命令 \`pytest ...\` 退出码 0`，而识别逻辑只认裸命令开头，于是被当成"断言型"交给模型，模型看不到输出只能判 FAIL | 看起来像 worker 没做对 |
| 2 | 判据"输出受 verbose 条件控制"判 FAIL | 只给了 diff，`if verbose:` 是三行上下文之一，看不出块结构 | 看起来像代码有问题 |
| 3 | `命令 \`git diff --name-only\` 的输出仅含 X` 必然 FAIL | 只实现了"退出码 N"型，没有"命令+期望输出"型 | 看起来像 worker 多改了文件 |

三次的共同点：**验收器能力不足时，失败会伪装成"被验收者的错误"**。
如果不逐条核对证据，这些都会被记进"模型成功率"，把系统缺陷算成模型差异。

由此得到的工程要求：

1. 验收器的**能力缺口必须显式报错**（`skipped: 不支持该判据形态`），而不是静默判 FAIL；
2. 每次失败必须能回答"是命令没跑、还是命令跑了没过"——两者的修复方向完全相反；
3. 换后端做对照时，**验收器必须固定**，否则差异里混进"谁在打分"。

## 下一步

四条，按性价比排：

1. **补验收器判据类型**（必需）：支持"命令 + 期望输出含 X"。缺它会让合法判据全部失败。
2. **重写小任务集**（必需）：现有计划要求新建不存在的测试文件，两臂都挂，
   测不出差异。需要"单文件、单断言、不要求新建测试"的任务。
3. **补样本**（可选，40 分钟）：A0/A1/A2 各扩到 15 条，把 p=0.062 压到 0.05 以下。
4. **后端对照**（执行阶段）：验收器修好、任务集换掉之后再做，否则数据不可用。

## 第五批：同外壳换后端（n=36，执行阶段）

**问题**：同一个 Codex 外壳，换后端模型（OpenAI 默认 vs DeepSeek-v4-pro），
在同一批任务上，**质量与速度有没有可测差异**。

**设计**：
- 3 条中等任务（改响应结构 / 跨文件改语义 / 改排序），都要求"读懂现有代码 + 改两处 + 测试保持绿"。
- 每腿由**确定性判据**验收（`python -c` 断言行为 + `pytest` 回归），**没有任何 LLM 判分**。
- 验收器固定为同一个（OpenAI 侧），只变 worker 后端。
- 每任务重复 6 遍，共 18 对 / 36 次执行。

**结果**（剔除 1 次被机器休眠打断的运行，实际 35 次）：

| 任务 | OpenAI 中位 | DeepSeek 中位 | 倍率 |
|---|---|---|---|
| m1 响应改 `{"id": n}` | 70s | 84s | 1.20× |
| m2 delete 布尔 + rm | 91s | 164s | 1.80× |
| m3 列表降序 | 69s | 97s | 1.42× |
| **总体** | **73s** | **122s** | **1.68×** |

- **质量：18/18 vs 17/18**（那 1 次失败是被休眠打断的，不在有效样本内）。**这个难度上两者都能做对。**
- **速度：17 对里 16 对 DeepSeek 更慢**，配对差中位 +41s，单尾符号检验 **p = 0.00014**。

**结论**：在这一档任务上，换 DeepSeek **没有质量收益，只有 1.7 倍的延迟成本**。

这条对"异构协同"的意义是负面的但也重要：**如果两个 worker 做同一件事的通过率一样，
那么"按能力分派"就没有可分的差异**——差异只在成本和延迟上，而这两项用规则（配额、价格）
就能算，不需要模型去判断。

**局限**：只有 1 对后端、3 个任务；任务难度的"天花板效应"明显（都做对）；
DeepSeek 那腿的方差大（91–366s），与它可能是推理模型有关（`codex` 提示
`Model metadata not found`, 上下文与推理参数都用的是兜底值）。

## 第六批：换成 V4.1-Flash 能快回来吗（n=36）

**问题**：第五批里 DeepSeek-v4-pro 比默认 OpenAI 模型慢 1.68×。换成更轻的
**V4.1-Flash**（原生 id `deepseek-flash`，1M 上下文）能不能把这个差距赚回来？

**设计**：与第五批完全相同——3 条中等任务 × 6 遍 × 2 臂，验收器固定为 OpenAI 侧，
判据全部确定性（无 LLM 判分）。共 36 次执行，60.8 分钟。

| 任务 | OpenAI 中位 | Flash 中位 | 倍率 | （对照）pro 倍率 |
|---|---|---|---|---|
| m1 响应改 id | 72s | 126s | 1.75× | 1.20× |
| m2 delete 布尔 + rm | 98s | 120s | 1.23× | 1.80× |
| m3 列表降序 | 74s | 123s | 1.67× | 1.42× |
| **总体** | **79s** | **120s** | **1.53×** | **1.68×** |

- **质量：18/18 全过**（OpenAI 也是 18/18）。换 flash 不掉通过率。
- **速度：18 对里 14 对更慢**，差中位 +35s，单尾符号检验 **p = 0.0154**。
- 以 OpenAI 为共同基准：flash/openai = 1.53，pro/openai = 1.68 → **flash 只比 pro 快约 9%**。

**结论：换 flash 换不回速度。**

它确实没有拖垮质量（18/18），也确实比 pro 略快，但**1.5 倍仍是显著的成本**。
如果目的是"让 DeepSeek 那腿不拖慢整体"，这个方案不成立；它的价值只在**单价**上——
而单价这次没有测（需要跑前后 `/user/balance` 差值），不能凭"flash 应该更便宜"下结论。

**一个必须写进局限的观察**：两批的**逐任务倍率互相反着**——pro 在 m2 最慢（1.80×），
flash 在 m1 最慢（1.75×）。同一批 OpenAI 基准很稳（70/91/69 vs 72/98/74），
说明这不是基准漂移，而是**"任务×模型"的交互在单次测量下极不稳定**。
所以只能信总体倍率，不能信"某个模型更擅长某类任务"这种说法——至少 n=6 时不行。

## 第七批：每次任务到底花多少钱（成本实测）

**为什么单独测**：官网定价页抓不到（文档站 302、平台页 429），而且"标价"与实际扣费未必一致。
`usage` 只给 token 不给钱，`/user/balance` 是唯一权威的扣费来源。

**为什么放弃"单价 × token"**：缓存价低到测不出来。116k token 的命中价约 0.02 元/百万，
要凑出 0.01 元的余额变化得跑几千万 token。**直接测任务成本，绕开单价这一层更准。**

**方法**：读余额 → 跑 N 次真实任务 → 等结算 → 再读余额，差额除以 N。
每臂 8 次，共 16 次，62.7 分钟。

| 后端 | 次数 | 通过 | 总花费 | **元/任务** |
|---|---|---|---|---|
| codex-ds-flash | 8 | 8/8 | ¥0.31 | **¥0.039** |
| codex-ds（pro） | 8 | 8/8 | ¥1.24 | **¥0.155** |

余额 52.41 → 50.86，共 ¥1.55，与 0.31 + 1.24 完全对上（账能对平，说明测法可信）。

**关键数字：flash 比 pro 便宜 4.0 倍**（¥0.039 vs ¥0.155），而质量同为 8/8。

### 与速度并列看

| 后端 | 相对 OpenAI 的耗时（第六批 6 遍中位） | 元/任务 |
|---|---|---|
| OpenAI 默认 | 1.00×（79s） | 订阅制，无边际成本 |
| **flash** | **1.53×**（120s） | **¥0.039** |
| pro | 1.68×（122s） | ¥0.155 |

**结论修正**：

- 对 OpenAI：换 DeepSeek 仍然**更慢**（1.5~1.7×），省的是钱不是时间。
- 对 pro：**flash 全面更优**——便宜 4 倍、速度略快（1.53× vs 1.68×）、质量同为满分。

### 三条方法论上的坑（都会误导结论）

1. **余额是延迟批量入账的**：调完立刻读会是 0。实测滞后 1~2 分钟，必须等结算再读。
2. **缓存会污染冷启动测量**：同样的 prompt 第二次起全部命中，测出来的"单价"是缓存价。
   要做冷启动测量必须每次换前缀。
3. **计费口径与耗时口径不能混批比较**：第七批的中位耗时（192s / 217s）比第六批高，
   因为这一批没挂验收器、且仓库状态不同。**耗时只信第六批，成本只信第七批。**

**未测**：OpenAI 那条路的边际成本。它走的是订阅额度，单次任务的人民币成本为 0
（在配额内），所以"贵/便宜"的对比只在 DeepSeek 的两个模型之间成立。
